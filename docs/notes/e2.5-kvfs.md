# E2.5 — kvfs

`internal/adapters/outbound/kvfs`: a namespaced key-value store behind the ten
verbs. `cmd/nerved` registers it under the kind name `kvfs`, and a mount names
which part of the keyspace it holds.

## What the pattern was

The first plugin that claims a descriptor. `memfs` and `localfs` both claim
none, so everything the object-store descriptor changes is visible against them
rather than assumed.

```
$ NERVE_CONFIG=nerve.json go run ./cmd/nerved
mount / kind memfs {AppendOnly:false ReadDestructive:false ReadOnly:false Broadcast:false ObjectStore:false}
mount /sessions kind kvfs {AppendOnly:false ReadDestructive:false ReadOnly:false Broadcast:false ObjectStore:true}
mount /agents kind kvfs {AppendOnly:false ReadDestructive:false ReadOnly:false Broadcast:false ObjectStore:true}

$ curl -s localhost:7777/config | jq '.mounts[1]'
{"prefix": "/sessions", "kind": "kvfs", "settings": {"namespace": "sessions"}}
```

The plugin is written against a `Store` port — `Get`, `Put`, `Delete`, `List`
over a flat keyspace — with the keyspace in memory as one implementation. E2.8's
object-backed store is the second, which is what makes it a port rather than an
interface tax.

## What surprised me

**The descriptor did the design work.** Claiming `ObjectStore` is one line, and
it removed every question about what a directory means in a keyspace: the suite
stopped asking for `Mkdir` to make one, for `Stat` of a prefix to answer, for
`Rename` to move a subtree. Twenty-odd cases were skipped and four ran that
`memfs` never sees. That is what E2.6 promised — declaring what you are is how
you get held to it — but it reads as a smaller *implementation*, not only a
smaller test surface.

**The root is not a key, and that is a whole verb's behaviour.** Every verb
needing a key resolves the root to `fs.ErrInvalid` from one helper, which is
cheaper than the three special cases the suite actually demands (`Remove`,
`Rename`, and `Stat` by implication). `RemoveAll` is then the one verb that
deliberately ignores that error: the root has no key of its own, so there is
nothing at it to delete, only what is under it.

**A key and a prefix can share a name.** `sessions/abc` and `sessions/abc/state`
can both be stored, which no tree allows. `ReadDir` has to pick which one `abc`
is, deterministically, or the answer follows Go's map order and the test flakes
one run in ten. The key wins: it describes itself, where a prefix is only ever
described by what is beneath it. The conformance suite has no case for this, so
the plugin's own test loops twenty listings to make the map order actually get
exercised.

**Where the copy promise lives was a real decision.** "Write copies what it is
given" is a port promise with two candidate homes: clone in the plugin before
`Put`, or make the `Store` port promise value semantics. It went in the port. An
object-backed store gets it from serialising, and there is one rule to state
rather than one per plugin over a keyspace.

**The namespace is only real because the store is shared.** A factory that built
its own keyspace per mount would make `namespace` a decorative string — every
mount isolated anyway. `Factory(store)` closes over the keyspace the composition
root owns, which is where that decision belongs: two mounts, one store, no
shared keys. It also makes the empty namespace a boot failure, because a mount
that does not name its part of the keyspace holds all of it.

**A keyspace has no mode and no modification time, so the port carries both.**
`Chmod` is in the verb set, so `Value` holds the permission bits and the time,
and the store keeps what it is given. The alternative — a store stamping its own
time — reads more like an object store, but then a plugin cannot promise the port
that a write moves the time forward.

## What I would do differently

Split describing a key from fetching it. `Stat` currently reaches for `Get`,
which hands back the whole value to report a size. Over a map that is free; over
an object store it is a GET where a HEAD would do, on the verb a caller uses
most. The port should have grown a `Head` before it had a second implementation
to justify one — the cost of adding it now is that E2.8 has to change the port
rather than implement it.

Make `Rename` one call on the port. It is `Get`, `Put`, `Delete`, which is not
atomic and leaves the value at both names if the process stops in the middle.
`memfs` does the same move under one mutex. A `Move` on the `Store` port would
let a store that can do it atomically do it, and the in-memory one would keep
the three-step version behind a lock.

## What I still do not understand

Whether `Remove` of a prefix should refuse rather than report nothing there. In
a keyspace the prefix is genuinely not an entry, so `fs.ErrNotExist` is literally
true — but a caller who meant to delete a session and typed the prefix is told
nothing is there while every key under it survives. `fs.ErrInvalid` would say
"not a thing you can do to this path", which is the sentinel E2.1's note already
flagged as unsettled for a non-empty directory.

Whether `Stat` of a mount's root should answer. Everything a mount table
dispatches `Stat` to answers for its own mount point; kvfs does not, because the
root is a prefix like any other. A caller walking a mount table top-down cannot
find a kvfs mount by `Stat`, only by `ReadDir`, and it is not clear whether that
is prefix semantics being honest or the descriptor reaching one path too far.

Whether `ObjectStore` is one descriptor or two. kvfs claims it for the prefix
semantics alone: it has no large objects, no multipart, no stream. E2.4's plugin
will claim the same descriptor and mean all of that as well, and a caller cannot
tell the two apart from what they say about themselves.
