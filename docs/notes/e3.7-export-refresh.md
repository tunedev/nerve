# E3.7 — Export refresh

A mount of materialised exports: names whose content is derived from paths in another
kind rather than stored under them. The ticket's acceptance is one sentence — a stale
export is not served after its inputs change — and it is a stamp taken on every read
that carries it: the export's inputs are described, the description is compared with
the one the held content was made from, and the content is made again before the mount
answers when the two differ.

## What the pattern was

**Invalidation is pull, and it is the only thing this plugin does.** A cache that is
told when to drop what it holds needs every writer to remember to tell it, and the
writers here are whatever wrote the inputs — a different mount, a different process,
somebody's editor. So nothing is told anything. The export describes its inputs at the
moment it is read and compares that with the description it kept, which makes freshness
a property of the read rather than of anyone's diligence. E3.5's `WriteObserver` is the
push half of the same problem and does not replace this one: a push tells you sooner,
and a pull is what is true when the push was missed.

**`synth.Tree` turned out to be the substrate, not a neighbour.** The tree is a flat
read-only mount whose entries compute their content per read and report when it last
changed, which is exactly an export. Building on it means `Read`, `Stat` and `ReadDir`
all go through the same `Content`, so the refresh is not something three verbs each
have to remember — a stale `Size` in a listing is a stale export being served, and
there was never a code path where it could survive. What this package adds to the tree
is one `Entry` per export and the cache behind it. Nothing else.

**The stamp is what `Stat` says, not what the inputs hold.** An export exists because
its inputs are the large side: a day of logs answering with a line, a workspace sliced
to a Parquet file. Hashing the content to decide whether the content needs reading
would spend the cost the mount is there to avoid, so the stamp is each input's length,
modification time and existence. The hole is a write that changes neither length nor
time, which on a store with a coarse clock is a change made inside one tick; the answer
to that is a store that says it changed, not a stamp that reads more.

**Absence is a stamp value rather than a failure.** An input that is not there stamps
as absent, so removing what an export was derived from makes it stale like any other
change, and what to answer once it is gone is the materialisation's to say — `Join`
says `fs.ErrNotExist`. Refusing at the stamp would have made "the input came back"
unobservable, because the comparison that would have noticed never ran.

**Two halves, one for config and one for a build.** `Join` is the materialisation a
mount config can ask for by name, so an export over any kind is a line of config, the
way `proxyfs` made a proxy over any kind one. Anything a config cannot name — a
projection sliced by a query engine, a document rendered from a template — is a
`Materialise` handed to `New` at composition, which is where the code that does it
already lives. The registry never learns a function name.

## What surprised me

**Stamping before the materialisation is the safe order, and the obvious one is not.**
An input changed while the materialisation is reading it leaves content made from the
new inputs recorded against the old stamp — so the next read finds the stamp moved and
makes the export again, work that was not needed. Stamping afterwards looks tidier and
is wrong in the direction that matters: it records the new inputs against content that
is only partly theirs, and no later read ever notices. The whole invariant is that
error goes one way.

**The lock covers the materialisation, not the fields.** Guarding only the assignment
would let every reader that arrived at a stale export make it, each of them paying the
cost the mount exists to avoid. Holding it across means the second reader waits and
finds the first's answer already fresh, which `TestConcurrentReadersMaterialiseAnExportOnce`
asserts as a count of one. A mutex held across remote I/O reads like a mistake, and
here it is the feature.

**An export mount over an export mount had to be refused.** The inner one is stamped
against the source and the outer one against the inner, so a change reaches the outer
export only once something has read the inner — a refresh that depends on somebody
having asked, which is the thing this plugin exists to take away. `proxyfs` refuses
itself for a different reason (nothing new is behind the second one); this refusal is
about correctness rather than about pointlessness.

## What I would do differently

Declare the exports as one setting from the start. The first shape was a key per
export — `export.report`, `export.index` — which reads well in a config file and
cannot be declared public, because `Public` is a fixed list of keys fixed at
registration and an export's name is not known then. Which paths an export is stale
against is the first thing anyone asks when it looks wrong, so it has to read back;
that made it one `exports` setting carrying every declaration, and the parser is the
price of the answer.

## What I still do not understand

Whether the stamp should be reachable. It is a string nobody outside the cache can
see, so an operator asking "why did that not refresh" has the inputs' `Stat` and their
own reasoning and nothing else. A name under the export that held the stamp would
answer it, and would also be a second kind of entry in a mount whose whole shape is
that every name is an export.

Whether a failed materialisation should hold anything. It holds nothing now: the error
goes back and the next read tries again, which is right for a query engine that was
briefly down and wrong for one that will fail the same way for an hour. A breaker is
already around the source, but the materialisation is above it and is not covered by
anything.

Whether inputs should be able to name a prefix. Every input is one path, so an export
over "every log in this directory" cannot be declared — a new file appearing under a
prefix is exactly the change a projection would want to be stale against, and stamping
a directory's `Stat` is not the same thing as stamping what is under it.
