# E12.4 — Timeouts on every remote call

`vfs.WithTimeout` wraps a plugin so every verb carries a deadline, and
`Registry.Build` applies it to everything it builds. The bound comes from the
`call-timeout` setting, so changing it is a config edit rather than a recompile.

## What the pattern was

A decorator over the port, applied at the one place a plugin can enter the tree.
`Registry.Build` is the only route from a factory to a mount, so bounding there
makes "no unbounded call" a property of the route instead of a habit every
factory has to remember. A plugin author cannot forget a timeout because they
never write one.

## What surprised me

**The hard part of the ticket is already in the standard library.**
`context.WithTimeout` keeps whichever deadline comes first, so "propagate, never
extend" needs no code: a caller with thirty seconds left keeps thirty seconds
even behind a ten-minute bound. What the ticket actually asks for is not an
algorithm but a place — somewhere no call can go around. Most of the thinking
went into finding the choke point, and none into the bounding itself.

**The dispatcher defect turns up again, one layer down.** A decorator that
bounds ten verbs and forwards `AsSymlinker` unchanged leaves the optional verbs
unbounded — a hole exactly where the accessor pattern was introduced to close
one. `WithTimeout` has to re-wrap what an accessor returns, and it has to keep a
refusal a refusal: a plugin with no link verbs must still answer nil through the
wrapper, or the caller's `if link != nil` guard starts lying. Every wrapper in
this repo now owes the same two duties, forward and re-wrap.

**A stream is not a call, and the fix is two lifetimes rather than one
exemption.** The first attempt forwarded the streaming verbs untouched, reasoning
that the plugin keeps the open's context for the whole transfer, so a call bound
would cut a healthy download at `call-timeout`. That reasoning is right about the
transfer and wrong about the open: an open that hangs is an unbounded call, and
Tenet 3 admits no exception. What is actually wrong is conflating two lifetimes
in one context. The split is the ordinary one between dialling and reading, and
because the plugin gets only one context, the bound on the open cannot live in
that context's deadline: `bound.open` hands the plugin a cancellable context
derived from the caller's and arms a `time.AfterFunc` to cancel it, then disarms
the timer once the open has answered. A `timer.Stop` that returns false is an
open that overran, which reads back as `context.DeadlineExceeded`. The transfer
that survives keeps the caller's cancellation, so a cancelled request still stops
a download; only the deadline is lifted, and closing the stream releases the
context.

**Zero cannot mean "no timeout".** That is the conventional reading, and here it
is a spelling of the failure the ticket forbids, so `call-timeout` rejects zero
and negative at boot. The setting has no value that asks for an unbounded call.

## What I chose not to build

Per-mount timeouts. One bound covers every mount, which is wrong the moment a
local disk and an object store are mounted side by side — but the override
belongs in `MountSpec`, and a mount config field with no remote plugin to need
it is a guess. It lands with the first one.

The coverage check. E12.17 asserts that every outbound call is bounded; this
ticket only makes it possible to be.

Idle detection on a live stream. A transfer that stalls mid-download is bounded
by nothing here — the open answered, so the bound is lifted, and only the plugin
knows what idle means for it. That is nrv-9b3, and it is an addition to this
bound rather than a substitute for it.

## What I still do not understand

How this composes with retry (E12.3) and the breaker (E12.5), which are the same
decorator shape over the same port. The order changes the meaning: retry outside
the timeout gives each attempt its own deadline and no total bound, timeout
outside retry gives a budget the attempts share and can exhaust. Both are
defensible and only one can be the default. Whichever it is, `Registry.Build`
composing three wrappers in a fixed order is a decision that wants writing down
rather than reading off the code.

Whether one `Registry` per timeout survives. If per-mount bounds arrive, the
duration stops being a property of the registry and becomes a property of the
spec, and `NewRegistry` loses its argument again.
