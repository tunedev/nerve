# E12.16 — goleak in the test suite

`internal/leak` owns the check; each test package spends one line on
`func TestMain(m *testing.M) { leak.VerifyTestMain(m) }`, and a test in
`internal/leak` proves the check reports a goroutine parked on a channel
nobody closes.

## What the pattern was

goleak compares the goroutines alive when a test binary finishes against the
ones the testing package is expected to be running, and fails the binary on the
difference. That is per test binary, so the wiring is per package: `TestMain`
is the only hook Go gives a package to run something after all its tests.

Wrapping `goleak.VerifyTestMain` rather than calling it directly gives the
project-wide ignore list one home. There is nothing to ignore yet — no
production code here starts a goroutine — but a Postgres pool and an OTel
exporter both park background goroutines for the life of the process, and the
alternative is the same `IgnoreTopFunction` line copied into every package.

## What surprised me

**The check is vacuous until something proves it fires.** A suite with goleak
wired in and a suite with the import missing are both green, and stay green,
until a leak exists. So the deliverable is not the wiring — it is
`TestGoroutineWithNoCancelPathIsReported`, which leaks deliberately, hands
`VerifyNone` a stand-in for `*testing.T`, and asserts the report names the
goroutine. `goleak.TestingT` is one method, `Error(...interface{})`, which is
what makes watching the check fail cost four lines.

Verified the other direction too, with a throwaway test that leaks for real:

```
PASS
goleak: Errors on successful test run: found unexpected goroutines:
[Goroutine 41 in state chan receive, with
github.com/tunedev/nerve/internal/core/vfs_test.TestProbeLeak.func1 on top of the stack:
...
FAIL	github.com/tunedev/nerve/internal/core/vfs	0.448s
```

**A leak is only reported on a passing run.** `VerifyTestMain` skips the check
when the exit code is already non-zero, so a package with a failing test says
nothing about its goroutines until that test is fixed. Leaks surface one behind
the failure that hid them.

**The check costs half a second when it finds something.** goleak retries 20
times before reporting — sleeps doubling from a microsecond, capped at 100ms,
about 430ms in total — so that a goroutine on its way out is not called a leak.
That cost lands on failing runs and on the proof test, never on a clean suite.

## What I would do differently

Nothing yet, but `internal/leak` is a wrapper with no options in it. If E12.6
lands without ever needing a shared ignore, it has not earned the indirection
and each package should call goleak directly.

## What I still do not understand

Nothing forces a new package to wire the check. A package added next month
with tests and no `TestMain` is silently exempt, and the suite still looks
complete. The property "every test binary checks for leaks" is statically
checkable even though a leak is not; whether that guard belongs in a test, in
`make check`, or nowhere is open (nrv-15y).

Whether `t.Parallel` will force the per-test `VerifyNone` form anywhere. The
package-level check cannot attribute a goroutine to a test, which is fine while
a leak means a bug and not a diagnosis, and stops being fine the first time two
parallel tests both start workers.
