# E7.9 — Search routes

`search.Routes` is how a caller finds what it cannot name: `Glob` matches paths,
`Grep` matches lines, `Find` ranks entries against a question asked in the
caller's own words, and `Retrieve` returns the body behind a hit. Four verbs
over the one FileSystem the mount table presents, through the view the scope
derives, and every one of them takes the URI prefix as its first real argument.

The acceptance is that one `Find` serves memories, documents and skills by
changing the prefix, and it is asserted as one call in a loop over three mounts
holding three different shapes — flat memory files, the words an ingestion left,
and skills whose documents are directories:

```
$ go test ./internal/core/search/   # with walk not descending into directories
--- FAIL: TestOneFindServesEveryPrefix (0.00s)
    routes_test.go:113: Find("/skills", "rewrite my CV for this advert") found nothing

$ go test ./internal/core/search/   # with the scope not deriving the path
--- FAIL: TestOneFindServesEveryPrefix (0.00s)
    routes_test.go:113: Find("/memories", "will she relocate to London") found nothing

$ go test ./internal/core/search/   # with the read-destructive descriptor ignored
--- FAIL: TestTheRoutesThatReadRefuseAMountThatIsConsumedByReading (0.00s)
    routes_test.go:276: Grep = <nil>, want fs.ErrInvalid
```

## What the pattern was

`library.Registry` and `content.Reader` again — hold the tree, take a
`workspace.Scope` per call, know no plugin — with one thing moved. The root is a
parameter rather than a field. A registry is a library of one kind at one place,
so its root is what it is; routes are the same four questions asked of whichever
area a caller names, so the prefix arrives per call and one value serves every
mount. That is the whole of the routing: there is no table here saying which
area is searched how, because a prefix is served by whatever is mounted under
it.

Paths derive through `Scope.View` rather than through `Scope.Path`. E5.1 built
the view for a caller that would otherwise spell its own paths, and a search
route is exactly that caller: it walks a tree and hands back the names it found.
Through the view a name is derived on the way in and is already in the caller's
vocabulary on the way out, so nothing here ever holds a string with a user
segment in it and no caller is told which workspace answered.

Ranking sits behind a port for the reason the library's does, and `termmatch`
now serves both: the scoring was extracted to take a name and a text, `Matcher`
hands it cards and `Ranker` hands it entries. A card is a name and a description,
an entry is a path and its content, and neither the weights nor the ordering
care which they were given.

## What surprised me

**Five routes are four verbs, and the fifth is the package.** The ticket names
`find` and `search` separately. Written out, a `Search` taking a query and
returning ranked results and a `Find` taking a task and returning ranked results
are one verb with two spellings, and shipping both makes a caller decide which
one a prefix prefers — a decision with no answer. E6.5 landed the same way for
the same reason, and the resolution is the same: the routes are named in the
roadmap, the verbs are what a caller calls, and the difference gets written down
here rather than compiled.

**The descriptors turned out to be load-bearing in a way I did not expect.**
`Caps.ReadDestructive` exists so a caller knows a queue job is gone once it has
been read. A search route is the first thing that would destroy data by doing
its job correctly: a `Grep` across a prefix holding a queue answers the question
once and empties the queue doing it. So the three routes that read check the
descriptor first — `Capabilities` is not I/O, so the check costs nothing and
happens before the damage — and `Glob` does not check, because it reads nothing
and matching names over a queue is safe. Two routes, one asymmetry, and the
capability model earning its keep rather than being described.

The test double had to actually consume. A mount that merely *claimed* to be
read-destructive would pass against an implementation that ignored the claim and
read anyway; the double deletes what it read, so the job's survival is the
assertion.

**Refusing beat skipping, and it was not close.** Leaving out the entries that
could not be read without destroying them gives a short answer indistinguishable
from a complete one — `library.List` already refuses that trade for the same
reason — and the caller is about to act on the things it was not told about.

## What I would do differently

Nothing structural. The first draft had `Hit` carrying a full URI built by
joining the prefix onto the path, so a caller could hold one string. `Retrieve`
would then have had to split the prefix back off, which needs the mount table's
prefix list — the table's business and not a caller's, and not something a
`vfs.FileSystem` can be asked. The pair stays a pair: every verb takes the
prefix, and a hit names a path inside it.

`Grep` returns whole matched lines rather than offsets. A caller that wanted to
highlight the match would need the match; nothing wants that yet, and a line is
what a person reads.

Composition does not build any of this. `nerved` wires the mount table, the
library catalog, the processors and the gateway; the routes need only the table
and a ranker, so there is nothing for config to say and nothing to wire them
into until an inbound surface exists. That is now the fourth ticket to end here.

## What I still do not understand

**Whether a prefix backed by an index should be asked rather than walked.**
`Find` gathers candidates by reading everything under the prefix and handing
them to the ranker. Over a workspace's memories on a laptop that is right and
costs nothing worth measuring. Over E7.3's `vectorfs` it is exactly wrong: the
mount holds an index built to answer this question, and walking it reads the
corpus to avoid using it. The fix is either a descriptor saying "this prefix
ranks itself" or an accessor returning a narrow searching interface, and which
one it is depends on what E7.3 finds a vector mount actually looks like through
the verbs. Deciding it here would be deciding it without that.

**The unit is the file, and a skill is a directory.** `Find` over `/skills`
answers `tailor-cv/SKILL.md`, not `tailor-cv`. That is honest — the routes work
in the tree's vocabulary and the tree's unit is a file — and it means the caller
that wants documents uses `library.Registry.Search`, which already ranks cards.
Two ways to search skills, answering at two altitudes, and nothing yet says
which one a retrieval layer should reach for.

**Term frequency is dropped, and these are not descriptions.** `termmatch`
counts each word once, which is right for a one-line card: saying "CV" twice
makes a description longer, not the skill more relevant. Over a document's whole
text it means a page mentioning queues throughout ranks with one mentioning them
once. It may not matter before the embedding ranker replaces it, which is the
reason it was left rather than an argument that it is correct.
