# E9.3 — kinds and roots come from config

`library.Catalog` is the libraries a process was configured with, one per kind,
reached by the kind's name. It is built from `library.Spec` values — a `Kind` and
a root — which `config.Config.LibrarySpecs` derives from a `libraries` array in
the config document, and `cmd/nerved` wires it over the mount table with the
matcher this build has.

The acceptance is a test at the composition root: a config document naming
`{"kind": "checklist", "file": "CHECKLIST.md", "root": "/checklists"}` produces a
working library of a document kind no line of Go in this repo names, on whatever
storage the same document mounted at that root.

## What the pattern was

The mount table's shape, one level up. `vfs.Registry` turns a `MountSpec` into a
plugin behind a prefix; `library.NewCatalog` turns a `library.Spec` into a
registry behind a kind name. Both stop at the first spec they cannot honour,
both refuse a duplicate name with `fs.ErrExist`, and both report an unknown name
with `fs.ErrNotExist` listing what the process actually has. A reader who knows
one knows the other, which is worth more than a cleverer lookup.

Validation stayed where the rule already lives. `config.Validate` says nothing
about libraries: `NewRegistry` already refuses a kind that cannot name its own
file and a root that is not rooted and clean, and spelling the flat-segment rule
a fourth time in `config` is exactly what E9.1's note complained about. The cost
is that a bad library line surfaces when the catalog is built rather than in
`Validate`'s joined list — the same place a bad mount surfaces, which is what
makes it a precedent rather than an exception.

## What surprised me

**The extraction had already happened, and the ticket's real content was the
wiring.** E9.2 had to generalise the registry to prove its own acceptance, so
"extract the kernel" arrived spent. What was left was the half the acceptance
actually names: a third kind needed a `Kind` value written in Go and a root
chosen by hand. The kernel that came out is two fields and a map — no new
abstraction was available to find, and inventing one to justify the ticket would
have been the overengineering the tenets forbid.

**"Fail loudly at boot" has a boundary, and the mount table draws it.** A library
whose root has nothing mounted under it is not refused. `MountTable` is built for
mounts arriving while it is read, so a root is a promise about a prefix rather
than a claim that something answers for it yet; until something does, the tree
says `fs.ErrNotExist` and the library is empty. Refusing that at boot would
outlaw a case the storage layer deliberately supports.

**The two ways two libraries can collide want opposite answers.** Two kinds under
one root stay legal — E9.2 tested it and it works, because `List` passes over a
directory holding no file of this kind. Two libraries of one kind are refused,
because the collision there is in the lookup: which registry `Open("skill")`
returns would depend on the order the operator wrote the config in. The tree
tolerates ambiguity that a name cannot.

## What I would do differently

Nothing structural. If the config had been designed here rather than followed,
`file` might have been `filename` to match `Kind.Filename`; `file` won because a
config document is read by an operator and the JSON keys are already short.

## What I still do not understand

**One matcher ranks every library.** The composition root passes a single
`termmatch.Matcher` to the catalog, so a build that wants embeddings over skills
and term overlap over checklists has nowhere to say so short of a second
catalog. Whether the matcher belongs on the `Spec` — a per-kind choice, named in
config like the root — or stays one decision per process is open, and E7 is
where the second implementation arrives to decide it.

**Nothing consumes the catalog.** `Open` has no caller outside tests, so its
signature is a guess: an error naming the configured kinds is right for an
inbound route reporting a misspelled kind to an agent, and heavier than a
lookup that only ever asks about kinds it just read back from `Specs`. E9.6 or
whatever inbound surface arrives first is where that is settled.

Carried from E9.2 and still open: whether a `Kind` stays a filename and a label,
or the first kind wanting a second frontmatter key turns kinds into plugins.
