# E5.1 — path derivation in one place

`internal/core/workspace` holds `Scope` and one method, `Path`. It is the only
place the layout of a scoped path is written down.

## What the pattern was

Namespacing rather than multi-tenancy, which is the refusal E5.2 records: the
Forge is one tenant, so a workspace is a subtree and isolation is a property of
the paths that name it. `Scope{User, Workspace}.Path(root, rest)` derives
`/root/user/workspace/rest`, and the same scope derives the same suffix under
every area root — the files mount, the key space, the queue — which is what
lets E5.3 create or delete a workspace across all of them without any of them
knowing the layout.

The one function is the deliverable, not an implementation detail of it. A
second place that spells the layout is a second place that can spell it
differently, and that difference reads as one user's data appearing inside
another's.

## Which layer contains a path

Derivation and enforcement are two layers, and this package is only the first.
`Path` returns a string: it clamps a `rest` that climbs, refuses a segment that
is not a name, and guarantees two users' paths never nest. All of that is
lexical and settled before any syscall. Containment beneath the derived path
belongs to the plugin, at its own boundary — `localfs` holds an `os.Root` so the
kernel refuses an escape no string can see, and a plugin mounted under a scope
owes the equivalent in whatever backs it.

That is the localfs lesson rather than a distinction for its own sake. `localfs`
handled paths correctly, passed the whole conformance suite, and was still
exploitable through a symlink the kernel resolved long after the string was
clean (nrv-9bj). Mount a plugin under a user scope without containment of its
own and this derivation is the only guard left, which is the state `localfs` was
already in while looking finished.

E5.4's cross-user isolation test therefore has to say which layer it exercises.
Written against `Path` alone it shows that two scopes derive paths that do not
nest, and nothing about whether the store behind them keeps them apart; read as
isolation, a green run would be a lexical result standing in for a backend one.
The enforcement half is the conformance suite's escape case (nrv-4r3), which
every host-backed plugin inherits rather than rediscovers.

## What surprised me

**Containment and validation are not the same rule, and they wanted opposite
answers.** A `rest` that climbs is clamped: `path.Join("/", rest)` resolves it
against the scope root first, so `../../etc/passwd` lands on `/files/alice/cv`
rather than above it. A `user` or `workspace` that carries a separator is
refused with `fs.ErrInvalid`. The difference is who wrote the string. A rest is
a path a caller asked for inside a scope it already has, so the honest answer is
"that is what your scope holds"; a segment is the scope's own identity, and
cleaning `alice/../bob` into a scope for bob would hand out a scope nobody
authorised. Clamping is right for one and silent privilege escalation for the
other.

**The clamp is the repo's existing pattern, not a new one.** `localfs.rel` and
the mount table's `rooted` both resolve against `/` for the same reason, so the
containment rule here reads the same as the two already in the tree. The
segment rule is `version.ValidateRefName`'s rule verbatim — a name that is not
flat leaves the place it was written into — which is a sign the rule belongs to
names in this system rather than to refs.

**User scope came out of the nesting for free.** The ticket asks for workspace
*and* user scope, and the first sketch had two functions. They are two depths of
one path: a scope with a user and no workspace is the subtree holding that
user's workspaces, which is exactly the path E5.3's `list` reads. One function
covers both because the empty segment simply does not appear.

## What I would do differently

Name the type before writing the package. `Scope` is right, but it sat in a
package called `scope` for a while, and `scope.Scope` was a bad enough name to
be worth the rename to `workspace`, which is what E5.3's lifecycle verbs belong
next to anyway.

## What I still do not understand

Whether `Path` should be handed the root at all, or whether a scope should be
turned into a mount and the root disappear. E11.3 wants a process inside a
workspace to be unable to address a path outside it, and a mount whose "/" is
the scope root enforces that by construction where a derived string only enables
it. Against that: every area root would then be a separate mount per workspace,
and the mount table is not built for a mount per user. The shape of E11.3 should
decide it, not a guess made here.

Whether the areas themselves should be named here. `Path` takes any root, so
"/files" and "/kv" are still spelled at call sites, and E5.3 will spell all of
them in one place when it deletes a workspace. If a second caller needs the same
list, the list is what belongs in this package next — not another path rule.
