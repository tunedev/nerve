# E4.2 — the RefStore port

`internal/core/version` holds `ID`, `ErrConflict`, `RefStore` and the ref-name
rule. `internal/adapters/outbound/localrefs` satisfies the port by keeping one
file per ref under a directory of a mounted tree.

## What the pattern was

A port where a second implementation is nameable, which is the calibration rule
this repo applies before abstracting anything. The second one is a Postgres refs
table, and naming it is not decoration: it is the only implementation that can
answer a race between two processes truthfully, which is what decided the shape
of the local one.

Every write is a compare-and-set. There is no verb that sets a ref without
saying what it expected to find, because that verb is the one that silently
overwrites the commit another writer just made.

## What surprised me

**"Local" turned out to be about agreement, not about disks.** The obvious
reading was "on this machine", and it led straight to writing the store over
`os` again next to `localfs`. The reading that survived is "one process agrees
on who won": the store is built over `vfs.FileSystem`, so memfs is the test
substrate and localfs is the laptop, and the compare-and-set is a read and a
write under one mutex. That is atomic for this process and for no other, and
saying so is the argument for the Postgres implementation rather than an
apology for this one.

**An unset ref stands for the zero ID, and that one sentence settled three
signatures.** Creating a ref is expecting the zero ID, so `Set` needs no
separate create verb. `Set` refuses the zero *next* ID, because a name that
resolves to nothing is a name that should not be listed. And `Delete` expecting
the zero ID is not a lost race but a missing ref, so it answers `fs.ErrNotExist`
where every other mismatch answers `ErrConflict`.

**The name rule belongs in the core, not in the store.** Refs are flat names —
no separator, not `.` or `..`. Put that rule in `localrefs` and the Postgres
store is free to accept `refs/heads/main`, and a ref that exists in one store
cannot be created in the other. In the core it is one rule, and it also keeps a
name from reaching the tree as a path.

## What I would do differently

Scoping. `E5.1` wants every workspace and user path derived in one place, and a
scoped ref store here is the same store over a different root — which is why ref
names stayed flat instead of growing a namespace segment. If that turns out to
be wrong, it is wrong in the direction of one more `New` call rather than a
parsing rule inside every implementation.

## What I still do not understand

Whether `List` should say what each ref stands for. It returns names, and every
caller that wants the versions then resolves each one — a loop over remote calls,
which is the exact fallacy Tenet 5 forbids. Against that: `Versioner.list_versions`
(E4.3) is the caller, and it may want the object behind each ref rather than the
ID. The shape of that verb should decide this, not a guess made here.

Whether the store should hold a mount or a mount plus a root at all. It bounds
nothing itself: the timeouts and retries around its calls are the registry's,
wrapped around the `vfs.FileSystem` it was handed. That is the right layering
today, and it means a ref write inherits whatever policy the refs mount was
configured with rather than one the ref store chose. Nothing has tested that
seam under a mount that fails.
