# E6.1 — Resource routes

`resource.Store` is what a workspace uploads: `Create` declares a resource and
reserves its name, `Upload` streams the bytes in, `Complete` finalises them
under their own digest, `SignedDownload` hands out a grant, `Download` redeems
one, and `Delete` removes the lot. Five verbs and the redemption of the fifth,
over the one FileSystem the mount table presents, at paths derived from the
scope that owns them.

The acceptance is that large content streams and finalises separately, and both
halves of it are asserted rather than described. Every case runs over a tree
whose whole-content `Read` and `Write` are refused on a resource's content, so
an implementation that buffered a file it was asked to stream fails:

```
$ go test ./internal/core/resource/    # with Upload buffering through Write
--- FAIL: TestLargeContentStreamsInAndFinalisesSeparately (0.01s)
    store_test.go:107: Upload: upload resource "transcript.txt": write
    "/resources/ada/hunt/transcript.txt/content" whole: content moves in pieces

$ go test ./internal/core/resource/    # with Complete hashing through Read
--- FAIL: TestLargeContentStreamsInAndFinalisesSeparately (0.01s)
    store_test.go:113: Complete("transcript.txt"): complete resource
    "transcript.txt": read ".../content" whole: content moves in pieces
```

## What the pattern was

`library.Registry` and `kv.Space`, again: hold the tree and a root, take a
`workspace.Scope` per call, derive every path through `Scope.Path`, know no
plugin. A reader who has read either has read most of this. "Routes" in this
roadmap have twice now landed as a core verb set rather than as handlers, and
this is the third — the inbound surface does not exist yet, and a verb set is
what it will call.

Streaming is reached the way the settled decision says: `AsStreamer()` on the
dispatcher, with nil refused as `fs.ErrInvalid`. A store whose whole promise is
a file larger than memory cannot keep one on a mount that has to hold it, so it
says so rather than buffering — which is also what makes the refusal test
possible.

`cas.ComputeFrom` was added so the digest spelling stays in one place. A store
that formatted `"sha256:" + hex` itself would be a second answer to what content
is called.

## What surprised me

**The staging file was designed, then deleted, and deleting it removed a
question nothing could have answered.** The first shape wrote uploads to
`incoming` and renamed it onto `content` at completion, so a reader could never
see a half-uploaded file. Then: which order, rename-then-meta or
meta-then-rename? Both leave a state a crash can strand, and tolerating either
one costs a branch in `Complete`. The question dissolved once the gate was
named: `Upload` refuses a completed resource and `SignedDownload` refuses an
incomplete one, so content is only ever written while nothing can read it. The
rename was defending against a reader that cannot exist. One content file, no
ordering, and `Complete` is idempotent because hashing the same bytes twice
computes the same digest.

**Verifying the signature before parsing the payload changed what an error
means.** A token with a good signature and unreadable claims is `fs.ErrInvalid`;
one with readable claims and a bad signature is `fs.ErrPermission`. Checking in
that order means unauthenticated bytes never reach `json.Unmarshal`, and it
cost a test case: `"eyJ9.beef"` was written as a malformed token and is in fact
a forged one, which the suite said before I did.

**Delete does not revoke a grant, and that is the honest answer.** A signed
token outlives what it names, and nothing tracks the ones handed out. Redeeming
one after the resource is gone reports `fs.ErrNotExist` — the same thing a
holder would learn from a resource that never existed. Revocation would need a
list of live grants, which is state a store deliberately does not keep; the
short ttl is the whole mechanism.

## What I would do differently

Nothing structural, but the first draft asked the mount how big the content was.
`Complete` took the size from `Stat` and the digest from a separate streamed
read: two answers, taken at two moments, and an upload still running underneath
would have them describe different bytes. The length now comes from the pass
that hashed it, which is one fewer call over a mount that may be remote and one
fewer way for a resource to disagree with itself.

## What I still do not understand

**Where the signing key comes from.** Tenet 6 says secrets are not config, and a
`Signer` refuses to exist without a key, so the composition root has to hand it
one from somewhere that is not the config document. Nothing wires the store yet
— no resources root, no key — which is where `kv.Space` also stands, and the
answer is likely the same decision made once for both.

**Whether `ContentType` belongs here at all.** It is recorded and never read:
nothing in this package acts on it, and a processor in E6.3 will sniff the bytes
rather than trust a declaration. It is kept because an upload that cannot say
what it is uploading makes the caller store that fact somewhere else, which is
the second spelling of a layout this package exists to prevent.

**The flat-segment rule is now written five times.** `workspace.validSegment`,
`version.ValidateRefName`, `library.validName`, `kv.validSegment` and this one.
E9.1 filed the extraction and it is still open; writing the fifth copy was a
scope call rather than a judgement that five is fine.
