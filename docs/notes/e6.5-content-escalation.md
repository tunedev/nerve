# E6.5 — escalating through a document

`content.Reader` is what a caller reads of a document it has already found:
`Stat` says what stands and which rungs it could climb to, `Abstract` hands back
the cheapest thing this build says about the document, `Level` climbs to any
rung by name, `Read` returns the words extraction left, and `Download` signs a
grant for the file itself. Five routes, four verbs and one ladder — the same
`[]ingest.Level` the summarisation stage was built with, so a rung a caller can
ask for is a rung something writes.

The acceptance is that retrieval is handed L0 and pays for nothing above it
until it asks, and that is asserted over a tree that writes down every read
rather than over what came back:

```
$ go test ./internal/core/content/    # with Abstract also reading the words
--- FAIL: TestRetrievalIsHandedTheAbstractAndEscalatesOnlyWhereItHasTo
    reader_test.go:163: Abstract read [text abstract], want [abstract]

$ go test ./internal/core/content/    # with any sidecar readable as a rung
--- FAIL: TestASidecarThatIsNotARungIsNotAnEscalation
    reader_test.go:256: Level("embedding") = <nil>, want fs.ErrInvalid

$ go test ./internal/core/content/    # with Stat listing what stands rather than where a caller may go
--- FAIL: TestStatSaysWhichRungsStandWithoutReadingOne
    reader_test.go:207: Levels = [abstract detail overview text],
        want [abstract overview detail text]
```

## What the pattern was

`library.Card` and `library.Document` one altitude up, which E9.1's note said
this ticket would want before the ticket was read: choosing needs what a
document says about itself, using it needs what it says, and a caller escalates
only where it has to. What is new is that here the rungs between those two
answers are **data on the read side as well as the write side**. E6.4 made the
ladder a value the stage is given; a reader that named `Abstract`, `Overview`
and `Detail` as three methods would have taken that back, because the fourth
rung a build adds at composition would have had no route.

So the ticket's five routes are four verbs. `overview` is `Level` with a
different rung, and the note that explains it is this one. `Abstract` survives
as its own verb not because L0 is special but because *cheapest* is a role: the
caller that wants the smallest true answer must not have to know which rung is
smallest, and on a ladder composition changed it is a different rung.

**The package boundary was settled by a compile error, not by taste.** The rung
names live in `ingest`, and `ingest` imports `resource`, so the escalation verbs
cannot be methods on `resource.Store` without a cycle. That turned out to be the
right line anyway — the store is the upload lifecycle and this is the read side
— but it was found rather than chosen, which is worth writing down.

## What surprised me

**"Escalates only where needed" cannot be asserted from a return value.** A
reader that read all four rungs and returned the abstract satisfies every
assertion about what came back. The tree had to be made to write down what it
read. That is `noWholeContent` from the resource suite one property along: that
one refuses what must never happen, this one records what did — and the second
is what a test about cost needs, because reading a rung you were not asked for
is not an error, only waste.

**`Stat` wanted a verb the store did not have, and the alternative was a stat
that moves content.** Asking each rung whether it exists is one read per rung
over a mount that may be remote, and each one pulls the body to find out the
body is there. `resource.Store.Derivations` is one `ReadDir` with the two files
a resource is made of dropped, which only the store knows the names of.

**Filtering that listing through the ladder changed what `Stat` means.** Left
raw it lists whatever stands beside the document — an embedding, a projection,
whatever a later stage leaves — and a caller reading it would try to escalate to
something that is not a summary. Intersected with the ladder it answers "where
can you go from here" rather than "what files are here", and it comes back in
escalation order without sorting anything.

## What I would do differently

Nothing structural. The first draft had a `Levels()` accessor returning the
ladder, so a caller refused a rung could find out what the rungs are; nothing
called it and no case asserted it, which makes it a method that exists because
it might be wanted. It is gone. `Stat` already says where a particular document
can be climbed to, which is the question a caller actually has.

Composition still does not build any of this — `nerved` has no resources root
and no signing key, so the reader stands where the store and the pipeline stand,
exercised by tests and wired by nothing. Three tickets have now ended there.

## What I still do not understand

**Whether `read` should be the words or the file.** It returns what extraction
left, so a document this build cannot read has no `read` at all and its only
rung is `download`. That is either exactly right — there are no words, and
inventing some would be worse — or a hole where "give me whatever you have"
belongs.

**Whether the ladder should say what a rung costs.** Nothing here says a detail
is dearer than an abstract; the caller knows only the order, and infers cost
from it. Over a mount where L2 is a megabyte and L0 is a line that inference is
right; it is a convention rather than something the ladder states, and a caller
budgeting a context window is the one who will find out whether that is enough.

**Whether an abstract is allowed to be a sentence of the overview.** E6.4 left
this open at the port and it arrives here as a caller's problem: something that
shows L0 and then escalates to L1 shows one sentence twice with `termsum` and
never with a model. Escalation does not rely on it, but a display built on top
of escalation might.

**Whether `Stat` should also say where ingestion stands.** A document with no
rungs is one whose pipeline has not run and one whose pipeline ran over a format
nothing could read, and telling those apart means also asking E6.6's ledger.
Joining them would put the ledger in this package for one field; leaving them
apart means a caller asks two things to answer one question.
