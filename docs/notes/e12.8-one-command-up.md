# E12.8 — One command up, one command down

`make up` starts Postgres, RabbitMQ and Ollama and waits until each one answers;
`make down` stops them and keeps the data; `make clean` deletes it. `make status`
and `make logs` answer "is it running" and "why is it not" without recalling any
`docker compose` invocation. Published ports and the URLs derived from them live
in `.env`, which both `make up` and `make run` read.

## What the pattern was

The acceptance is about recall, so the test is not "does a command exist" but
"does the command work on a machine that is not empty". Running it was the whole
increment: everything below was found by `make up` failing, not by reading it.

## What surprised me

**`make up` did not work, and the Makefile had claimed it did since the
scaffold.** Ollama's port was already taken by a host-native Ollama, and
`docker compose up` failed after Postgres and RabbitMQ had already started:

```
failed to bind host port for 0.0.0.0:11434:172.25.0.3:11434/tcp: address already in use
```

A target that has never been run is a claim, not a command.

**Hardcoded ports are a Tenet 6 violation hiding in a file nobody calls config.**
The only way past that failure was to edit `docker-compose.yml` — a versioned
file, changed for a reason local to one machine, in a way that would be committed
by accident or re-fixed by every checkout. `${NERVE_OLLAMA_PORT:-11434}` moves the
decision into `.env`, which is ignored, and leaves the default identical.

**`--wait` was lying about Ollama.** A service with no healthcheck is "ready" as
soon as its container is running, so `make up` returned success while the Ollama
API was not yet answering — the exact failure mode the flag exists to prevent.
`ollama list` is the healthcheck and needs nothing installed in the image.

**`make clean` could not delete the data it claimed to delete.** The stack
bind-mounted `./.data`, so Postgres and Ollama wrote files owned by the container's
user, and `rm -rf .data` failed on every one of them:

```
rm: cannot remove '.data/ollama/id_ed25519': Permission denied
```

Teaching `clean` to `sudo` would fix one command and leave the ownership problem
everywhere else. Named volumes remove the cause: the data never lands in the working
tree, `down -v` deletes it, and `clean` no longer needs a `rm` at all. `.gitignore`
lost its `/.data/` entry with it.

**`gofmt -l .` was walking that data directory too.** After `make up`, `make check`
printed `open .data/postgres: permission denied` — the gate still passed, because
the error goes to stderr and the target tests stdout, which is a gate passing for a
reason unrelated to what it checks. It now names the Go trees instead of `.`.

**`.env` reached Compose but not the binary.** Compose loads `.env` on its own;
the process does not, and `internal/config` reads `os.LookupEnv`. So `.env.example`
documented a `NERVE_POSTGRES_DSN` that `make run` never saw. `make run` now sources
the file, which is what a reader already assumed was happening.

**A port is spelled once because `.env` interpolates for both consumers.** Compose
resolves `${NERVE_POSTGRES_PORT}` inside `.env`, and so does `sh` when `make run`
sources it, so `NERVE_POSTGRES_DSN` can be written in terms of the port rather than
repeating it. Changing a port is one edit; the two consumers cannot drift.

## What I would do differently

Add the healthcheck when the service is added rather than when `--wait` is found to
be wrong. Two of the three services had one; the third was the one that broke.

Reach for a named volume first. The bind mount bought one thing — `ls .data/postgres`
— that the container's own permissions made impossible anyway.

## What I still do not understand

Whether `make up` should also start the binary. "One command up" reads like the
whole system, but `nerved` has nothing wired yet, and the moment it does it wants
a foreground process with logs rather than a fourth container. E12.10's health
endpoint is probably where that decision has to be made, because that is the first
point at which "up" has an answer that is not "the containers exist".

Whether the app should read `.env` itself instead of `make run` sourcing it. The
Makefile doing it keeps the file layer out of `internal/config`, where `NERVE_CONFIG`
already names a JSON file and a second file format would be a second thing to
explain. But it also means `./bin/nerved` and `make run` see different environments,
which is a surprise waiting to happen.
