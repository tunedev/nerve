# E8.5 — Commit: batched category deduplication

A restated fact does not become a second memory. Two pieces:

- `internal/core/memory/dedup.go` — what makes two facts the same claim, and one
  pass that filters a whole batch against what a workspace believes.
- `memory.Store.Add` — applies it. A fact restating a currently believed memory is
  not written, so `Add` can answer with less than it was given.

`internal/core/commit` gains no code. It already calls `Add`, and the rule belongs
to the log rather than to the pipeline in front of it.

## What the pattern was

The ticket reads as a pipeline stage — "Commit: batched category deduplication",
the same shape as E8.4's "Commit: transcript compression" — and it is not one. A
stage sitting in `Commit` between extraction and `Add` would hold an invariant of
the log outside the log: `Add` would still accept a duplicate, and every writer
added after this one would have to remember not to write it. E8.4 put the rule
in `archive` and had `commit` compose it, for the same reason. Here the rule's
home is the store, and the pipeline gets the behaviour by already calling it.

Both halves of the ticket's title do real work in `fresh`:

- **Category.** The claim is `(kind, body)`, not `body`. "use tabs" as a
  preference and "use tabs" as an instruction are a habit and an order, and a
  workspace asked for its instructions must not answer with something nobody told
  it to do.
- **Batched.** One index of claims is built once from what the workspace believes,
  and the whole batch is checked against it — not one comparison per fact against
  the log, and not one read of the log per fact. The batch is also checked against
  itself, so a transcript that said something three times is one memory even on a
  workspace that held nothing before it.

Only currently believed memories go into the index. A memory something superseded
is a belief the workspace gave up, and stating it again is that belief returning;
folding it into the memory that no longer stands would make the log say the
workspace never changed its mind. `Current` already answers exactly this set, so
the temporal work E8.8 landed is what makes the dedup correct rather than merely
plausible.

## What surprised me

**"Batched" is what tempted me into a sixth gateway capability.** Batching only
buys something when the per-item cost is a round trip, so the word reads as an
argument for `llm.Deduplicator` with one call per category. I nearly built it. The
laptop implementation of that port would have been string equality wearing a
chain, a timeout and a circuit breaker — and a build with no model would then have
had no committer, which is a regression against the plane test. Batching also buys
something when the per-item cost is a read of the whole log, which is the cost that
was actually there.

**The dedup and the reconciliation are the same call if dedup is semantic.** If
E8.5 asked a model "do these two sentences say the same thing", E8.7 would ask a
model "do these two sentences disagree", and one endpoint would answer both from
the same comparison. Keeping E8.5 mechanical is what leaves E8.7 a ticket of its
own: restatement is a property of the text, contradiction is a property of the
meaning, and only the second needs a model.

**Validation has to come before the filter, and it does so by accident of order.**
A batch of `[restatement, invalid fact]` must still be refused whole. It is,
because `fresh` keeps the first statement of every claim — the invalid fact is
never a restatement of a stored one, since nothing invalid was ever stored — so it
survives the filter and `write` refuses it. That is a real dependency between two
functions that do not mention each other, and it now has a case standing on it.

**Superseding deliberately does not dedup.** `Supersede` names the memory it
replaces; a caller doing that has stated its intent, and silently dropping the
replacement because it restates something else believed would leave the named
memory closed against nothing.

## What I chose not to build

No `llm.Deduplicator` and no gateway capability. See above.

No paraphrase matching. Two facts are the same claim when their kinds and bodies
match read as text — case-folded, runs of space collapsed — and no further. The
next rung is stripping punctuation, and the rung after that is judging meaning,
which is E8.6 and E8.7. A filter in front of every write is the wrong place to put
a judgement that can be wrong.

No re-ranking. A fact restating a believed memory at a different priority is
dropped along with the rest, so a hedge later stated firmly does not raise the
memory's priority. Raising it means writing a memory that supersedes the old one,
which is a decision about a claim's standing rather than about its text, and it
belongs with E8.7.

No dedup across workspaces or against the archive. The index is one workspace's
believed memories, which is what `Current` answers.

## What I still do not understand

Whether the first statement or the last is the one to keep. The filter keeps the
first, so a memory names the conversation a claim was first made in and the fact
that the user said it again three months later is nowhere in the log. That is the
right answer for "when did this become true" and the wrong one for "is this still
live", and the second question is exactly the one a caller with limited room asks
when it decides what to drop. Recording a restatement without writing a memory
would need somewhere to record it, and every candidate is a write to a memory
already written.

Whether case-folding is a normalisation or the start of one. It is defensible on
its own — no two different claims differ only in capitalisation — but the argument
that admits it is the same argument that admits stripping a trailing full stop,
and then stemming. The line I drew is "what was typed" versus "what was said", and
I do not know that it holds under a real extractor rather than under `cuefact`,
which returns sentences the user wrote verbatim.
