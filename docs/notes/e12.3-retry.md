# E12.3 — Retry with explicit retryable versus fail-fast classification

`vfs.Classify` sorts an error into `Retryable` or `FailFast`. `vfs.WithRetry`
wraps a plugin so a repeatable call whose failure was retryable is attempted
again, and `Registry.Build` applies it outside the timeout, so every attempt is
a call with its own deadline. `retry-attempts` and `retry-backoff` are settings.

## What the pattern was

The same decorator over the same port as the timeout, with the interesting part
outside it. Tenet 3 says classification is the half people skip, so the
classifier is exported, takes no policy and holds no loop: a caller can ask what
an error is worth without retrying anything, and its test is a table rather than
a stopwatch.

Fail-fast is the zero value of `Class`. An error nobody has classified is not
retried, so a plugin opts in to retrying by wrapping `ErrTransient` around what
its driver returned — the same translation at the plugin's edge that turns a
driver error into an `io/fs` sentinel. The classifier knows no driver, and
nothing in `internal/core` has to.

## What surprised me

**Idempotency is a property of the path, not of the verb.** The first cut
listed the safe verbs: `Read` and `Stat` are reads, `Write` and `Chmod` are
assertions of a final state, `Remove`, `Rename` and `Symlink` are the three that
report a different failure the second time. Then `Caps` answered the question
the list could not. A queue's job path is read-destructive, so a `Read` that
took an entry and failed to deliver it loses that entry on the second attempt; a
log path is append-only, so a `Write` that landed and failed to say so appends
the same bytes twice. Same method, same plugin, different path, opposite answer
— which is exactly what the descriptors were introduced for, one altitude up.
They were written to answer "what does this verb mean here" for callers, and
they answer "may this call be repeated" for a wrapper that was not imagined when
they were written.

**The wrapper needs the plugin's `Capabilities`, and the streamer needs it
too.** `retryingStreamer` carries the function rather than the plugin, because
an open is repeatable on the same terms as the verb it stands in for. That is
the third wrapper in this repo to owe the accessor duties — forward, re-wrap,
and keep a refusal a refusal — and the first to need something from the plugin
other than the verb it is wrapping.

**The order question from E12.4 has one defensible answer.** The bound goes on
first and the retry outside it. The other order hands the attempts one deadline
to share, and the first attempt that hangs spends all of it, so the retries that
follow expire on arrival — a policy that does nothing precisely when it is
needed. Retry outside timeout costs a worst case of attempts times the bound,
which is what `retry-attempts` is for, and the sequence is still bounded by the
caller: attempts run on the caller's context and the waits between them end when
it does.

**A cancelled caller is fail-fast; a call out of time is not.** They look like
one class and are two. `context.Canceled` means the caller has gone and nothing
is waiting for the answer. `context.DeadlineExceeded` reaches the wrapper from
the bound on one attempt, which is exactly the transient failure retrying
exists for — and when it is the caller's own budget that expired, the wait
before the next attempt ends immediately and no attempt is made.

## What I chose not to build

Per-mount policies. One policy covers every mount, which is wrong the moment a
local disk and an object store are mounted side by side — and, like the
per-mount timeout, the override belongs in `MountSpec` and lands with the first
remote plugin that needs it.

A retry budget across calls. Attempts are bounded per call, not per process, so
a dependency that is failing for everyone gets attempts times the callers. That
is what the breaker is for, and it is E12.5.

Retrying a transfer. Only the plugin knows how far a stream got, and re-reading
from the start is the caller's decision.

Classification of real driver errors. There is no plugin yet. The first one
wraps `ErrTransient` at its edge, and the first thing that will be worth testing
is that it wraps the right ones.

## What I still do not understand

Where the breaker goes in the stack. Outside the retry it short-circuits before
any attempt and counts a retried sequence as one failure; inside it sees every
attempt and trips faster, and the retry then has to classify a broken circuit —
which is fail-fast, and would be the first error class that is neither the
plugin's nor the context's. Three wrappers in a fixed order at `Registry.Build`
is now a composition worth a spec rather than a reading of the code.

Whether the fail-fast default asks too much of a plugin author. A plugin that
never wraps `ErrTransient` is never retried, and nothing fails: no test goes
red, no log line appears, and the symptom is a resilience feature that quietly
does nothing. The alternative — retry unless told otherwise — fails the
acceptance criterion of this ticket, so the default is right; what is missing is
a way to notice. A counter of retryable versus fail-fast per mount would show it
in one glance, and that is E12.6 and E12.7 territory rather than this ticket's.
