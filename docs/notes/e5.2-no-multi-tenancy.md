# E5.2 — Refuse multi-tenancy

Nerve has no tenant identifier and will not grow one. `internal/core/workspace`
keeps two segments, user and workspace, and every scoped path in the system is
derived from them.

There was nothing named `tenantId` to delete. `grep -rni tenant` over the tree
finds the word in three places, all of them prose already saying the Forge is
one tenant: the roadmap line for this ticket, the `workspace` package comment,
and the E5.1 note. So the ticket is not a removal — it is the decision not to
add the field, written down where the next person to reach for it will be
standing.

## What was refused, and what it is not

Multi-tenancy in the sense a SaaS platform means it: a tenant identifier
threaded through every port, key, queue entry and mount prefix, with a claim
that one tenant cannot address another's data.

The two things that get conflated here are multiple users and multiple tenants,
and only the second is refused. Multiple users is real, built, and a correctness
requirement rather than a feature — someone else's CV and salary expectations
live in this system, so E5.1's derivation and E5.4's isolation test are load
bearing today. Tenancy is a different claim: separate administrators, separate
lifecycles, separate deletion obligations owed to someone who is not the
operator. Nerve has one of each.

## Why a spare segment is worse than none

A tenant segment is cheap to add and impossible to remove, because `Scope.Path`
is what names data on disk. Add it and it appears under every area root, in
every key, in every queue entry, in every mount prefix — and then it is written
into paths that outlive the decision. Removing it later is a migration of every
stored path, not an edit to one function.

What it would buy in the meantime is a field with exactly one value forever.
That is not a namespace; it is a namespace-shaped string that isolates nothing
while making every path in the system look as though it does. Real tenancy is
not a segment — it is separate administration, separate erasure, separate key
material — so a `tenantId` gives the topology of tenancy with none of the
enforcement, which is the failure mode the Forge's refusals table exists to
avoid: copying a shape and learning to cope with it rather than building the
thing that holds.

## What stays

Path-prefix namespacing, unchanged: a workspace is a subtree, `Scope{User,
Workspace}.Path` is the one place its layout is spelled, and isolation is a
property of the paths that name it. The obligation this refusal does not touch
is the one the Forge constraint states — a bug in one user's workspace must not
be observable from another's — which is E5.4's test and the plugin containment
the conformance suite inherits, not something the refusal weakens.

## The evidence that would reopen it

Not more users; the user segment already answers that. Three things would:

- a second administrator, so "one tired person operates it" stops being true
- an erasure obligation Nerve owes a party who is not its operator
- running Nerve for someone who must not see the operator's own data

Reversing costs one function and a migration of stored paths, which is the
honest price and the reason to pay it late rather than early.

## What surprised me

The refusal was already recorded before the decision ticket ran. The `workspace`
package comment states it and E5.1's note states it, both written by the ticket
that needed the answer rather than by the ticket that owned it. That is the
right way round: a refusal that lives only in a decisions file is one nobody
reads at the moment they would violate it, and the package comment is exactly
where someone adding a third segment is looking.

## What I would do differently

Sequence the refusal before the ticket that depends on it. E5.1 derived a
two-segment path by assuming this answer, and it assumed correctly, but it was
assuming rather than citing. A decision ticket that lands after the code it
governs can only ratify.

## What I still do not understand

Whether this refusal has anywhere that enforces it, or only places that state
it. Nothing fails if a `Tenant` field appears on `Scope` tomorrow. The
architecture boundary in E12.14 can be a `depguard` rule because an adapter
import is a dependency edge a tool can see; "the scope has two segments" is not
an edge, and a test asserting a struct's field count is friction pretending to
be a boundary. So this one is held by the package comment and by review, and I
do not know whether that is sufficient or merely the only thing available.
