# E12.7 — Traffic accounting surfaced through a server-info mount

`vfs.Traffic` counts calls and failures per mount and is a `Recorder`, so the
accounting reads the report a call already makes rather than adding a wrapper
of its own. `vfs.Recorders` is the fan-out that lets the registry hold the
exporting recorder and the tally at once. `serverinfofs` grows a `traffic`
entry: one heading and one tab-separated line per mount, read through the tree
like every other thing the process says about itself.

## What the pattern was

The second consumer of E12.6's port, and the one that proves the port was worth
having. Nothing about counting reached into `WithTelemetry`, the registry or a
plugin: a call already announces itself and says what it returned, and a
different reader of that announcement is a new type in the core and one line at
the composition root.

`Recorders` is the same shape as the `fanout` handler the log already uses —
a slice, because the composition is the same for two as for any number. Its one
subtlety is direction: the context threads forward through `Begin`, so a
recorder that opens a span hands it to the recorders after it and to the call
itself, and the `Done` functions run backwards, so what began inside something
ends inside it.

Why a tally at all when the histogram already carries a count: the collector is
optional and empty by default. `telemetry-endpoint` unset is the laptop, and on
the laptop the OTel count exists only inside a no-op meter nobody can read. The
tally is the number that survives having no collector, and it is read through
the tree rather than over a port, so anything already reading the tree can ask.

Copy-on-write rather than a lock, because E12.11 already measured this exact
choice on this exact access pattern one layer up. The mount set is not known
when the tally is built — mounts arrive as calls do — so the map is written on a
path every call takes. Written the way `MountTable` is, first sight of a mount
takes a mutex and replaces the map, and every call after that loads one pointer.

## What surprised me

**`errcheck` fails a type assertion, which ruled out `sync.Map`.** The first
draft was `sync.Map` keyed by mount, which is exactly the read-mostly structure
it is built for. Three `held.(*counter)` assertions, three lint failures — and
the linter is right for a reason bigger than the rule: this repo's whole
capability story is that type assertions are how you interrogate the wrong
object. Being pushed off `any` and onto `atomic.Pointer[map[string]*counter]`
produced the typed version of the same structure and the one the repo already
argued for.

**Counting at `Begin` rather than at `Done` is the more useful number, and it
took writing the test to see why.** Counted at the end, a mount whose calls all
hang reads as a mount nobody is using — the precise failure the counter would
be consulted about. Counted at the start, `Calls` includes what is still in
flight, which is what "asked for" means.

**The entry counts the read of itself.** Reading `/serverinfo/traffic` is a call
on the serverinfo mount, and the recorder is outermost, so the count increments
before the content is computed and the answer includes the asking. That reads as
a bug for about a minute and then stops: the tally is of what the process was
asked for, and this was one of the asking. Suppressing it would need the counter
to know which mount is reading it, which is a mount knowing about a mount.

**A per-verb tally was the first design and it is worse.** Verb, path and
duration are already in the span, where cardinality is free. Per verb, per
mount, as text, is a forty-line table for a process with six mounts, and the
question it is read for — which mount is this process spending itself on — is
harder to answer from it than from four columns.

## What I would do differently

Write the composition-root test first. The unit tests all passed against a
`Traffic` nothing was wired to; the test that mattered was the one that puts a
call through the table and reads the count back through the table, and it is
the one that would have caught the fan-out being wired wrong.

## What I still do not understand

Whether bytes belong here. "Traffic accounting" reads like bytes, and there are
none: `vfs.Call` names a verb and a path and deliberately carries no payload,
and the streaming transfers are not measured at all — the same gap E12.6 left
at `Close`. Adding bytes means widening the port for every recorder to serve
one, which is a decision the streaming question should make, not this one.

Whether the counters should survive a restart. They are since-boot, which makes
them useless for anything but the process in front of you, and that is the
right scope while there is no way to read them but in-process. It stops being
right the moment something scrapes them.

Whether this should have waited for a transport. There is no inbound way to
read the tree yet, so "readable" today means readable by code holding the table
and by the tests. The counters are correct and wired; what is missing is the
door, and E12.2's open question — whether the operator surface should be HTTP
at all — is now sharper rather than answered, because `/config` and
`/serverinfo/traffic` are the same kind of answer reached two ways.
