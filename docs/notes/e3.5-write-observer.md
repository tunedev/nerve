# E3.5 — WriteObserver

The push half of keeping something derived from the tree in step with it. A write goes
through an observer on its way out, and what the observer is told is a path — never
content, never a verb. The acceptance is one sentence, indexing triggers on write rather
than on the caller remembering to ask, and it is satisfied by a decorator over the mount
table plus one implementation of the port that publishes to the queue already there.

## What is not wired

`cmd/nerved` installs no observer. No mount a running process serves is wrapped,
so a write to one queues nothing, and the acceptance above is true of the code
and not yet of the binary. That is a staging decision, not an omission.

It waits on `nrv-4jwb`, which composes the pipeline in one go: the resources root
and download signing key `nrv-amti` carries, this decorator over a
`queuefs.Emitter`, the queue mount the emitter publishes to, and a
`queuefs.Worker` on a goroutine the process owns and cancels. Installed on its
own the observer would queue work nothing takes off the tree, and an emitter
pointed at a mount that is not a flat key space queues nothing and says nothing —
`observed.report` drops what the observer answers, by design. Which mounts are
observed is a config surface that does not exist, and choosing it is the open
question this note ends on.

## What the pattern was

**The event is a path and nothing else.** Everything else that was tempting — the bytes
that were written, the verb that wrote them, when — is a claim about a moment that has
already passed by the time a worker reads it. A path is the one thing still true later:
the worker roots the key it was told and reads what is there now. This is the work bus's
own bargain, where the notification says a message exists and the tree hands it over,
applied one layer up. It also means a removal needs no special event — the indexer is
told the path, finds nothing, and drops what it held.

**The path has to be the tree's, so the observer goes over the table and not under it.**
A plugin sees its own vocabulary: an observer beneath the mount table would report
`/report.txt` for something a caller can only reach as `/docs/report.txt`. Wrapping the
dispatcher is what makes the reported path the same string an indexer can read back, and
it is the same reason the port carries `Capabilities` and the accessors.

**A path a read consumes is never reported, and that one rule does two jobs.** An indexer
told about a queue path would claim the message — the watcher becomes the reader, and the
queue drains into whatever was supposed to be observing it. The same rule is what stops an
emitter that publishes into the tree it observes from feeding itself, so the recursion
guard is a capability question rather than a list of prefixes to skip. `Caps` varying per
path inside one mount is what makes it expressible at all.

**The write's result belongs to the plugin.** An observer that cannot be told does not
fail the write. The write happened; a caller told otherwise makes it again, which on an
append-only path means twice. The queue already made this trade one level down, where a
broker that is not there does not fail a write the journal has recorded, and the failure
mode is the same shape: a lost notification, never lost data. E3.7's export is the pull
half — a stamp read at read time — and is what is true when a push was missed.

**One job per path, for free.** The queue keys work by the path it is about, and recording
replaces what is pending under a key. So a document written ten times before an indexer
gets to it is one job, and the indexer pays for one read of what is there now rather than
ten reads of versions nobody wants. The debounce that Tenet 3 asks for came out of the key
space rather than out of a timer.

## What surprised me

**The classification test is the whole of the design decision.** Which verbs change
something is not derivable — no reflection can tell you whether `Chmod` is worth an
event — so it is a list, and a list rots. Splitting the port's own context-taking methods
into "changes something" and "does not", and failing when the two halves do not add up to
the port, turns a new verb into a test failure that asks the question rather than a verb
that quietly reports nothing. `Chmod` is in the changing half on the grounds that what
`Stat` says is part of what a path holds, and only a listener knows whether a mode matters
to it.

**A streamed write is one write and it happens at `Close`.** Reporting at the open would
name a path whose content is still arriving, and a stream that failed halfway would have
been announced anyway. This is the same split `WithTimeout` makes between bounding the
open and leaving the transfer alone, arrived at from the other direction: there, the open
is the discrete call; here, the close is.

**`Rename` is two events, and the obvious one is the wrong one.** Reporting only the
arrival leaves an index serving the departure for as long as it lives. The rule became
"report every path whose content is now different", which is two paths for a rename and
one for a symlink, whose old name is not touched at all.

## What I would do differently

Call it what it reports. `WriteObserver.Wrote` is told about a removal, a rename away from
a name and a mode change, none of which anyone would call a write in conversation; the
port is really "this path changed". The name is the ticket's and the code follows it, which
is the right call for one increment, but every doc comment underneath it has to spend a
clause undoing the word.

## What I still do not understand

Where a dropped report should go. Nothing in this repo logs, so an observer that could not
be told is silent, and the only thing that notices is a pull-side stamp somewhere else.
The honest answer is probably that the observer itself should hold the failure — a count,
a last error, something the operator surface can read — rather than the decorator growing
a second dependency to hand it to.

Whether `RemoveAll` should report what was under it. It reports the path it was given, so
an indexer holding a thousand entries beneath a deleted prefix has to work out for itself
that they are gone. Listing the subtree to report each one would mean listing it after it
stopped being there, so the alternative is not obviously available, but "a path changed"
means something different for a subtree than for an entry and nothing in the event says
which one it was.

Whether the observer should be a mount setting rather than a composition. It wraps the
whole tree today, which is the shape that made the recursion guard structural, but "only
these subtrees are worth indexing" is exactly the kind of thing Tenet 6 says an operator
changes in config. A per-mount observer would need the mount's prefix to name what changed,
which is the reason it is not one yet.
