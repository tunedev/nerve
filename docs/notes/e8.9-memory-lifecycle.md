# E8.9 — Memory lifecycle routes

Archived memory is recoverable, not deleted. Two pieces:

- `memory.Store` gains `Archive`, `Restore` and `Archived`. A memory moves to an
  `ARCHIVE` directory beside the log, keeping the sequence it was written under.
- `internal/core/lifecycle` — the four verbs a caller curates through: `Archive`,
  `Restore`, `Consolidate` (the E8.6 stage, reached through a consumer-declared
  interface), and `Lineage`, the temporal graph query.

## What the pattern was

`session.Store.Archive` already answers "how does this repo forget something
without deleting it": rename the cold entries into an `ARCHIVE` directory beside
the live ones, keep their sequences, and offer one verb that reads them back.
Memory archival is that, minus the summary — a session retains one because a
transcript is a narrative with a hole in it once the first half moves, and a
memory log is a set of independent claims where a missing one leaves nothing to
explain.

The move buys the property that mattered most: **no reader changed.** `List`,
`Current`, `AsOf`, dedup, `consolidate` and the search routes all read the log
directory, so archiving takes a memory out of every one of them at once. The
alternative — an archived flag, or a second log of archive events that every
reader consults — is the shape the global rule about fix placement warns about:
it would have taught six readers to tolerate a new state instead of restoring
the invariant that what is in the directory is what the workspace holds.

## What surprised me

**Archival is the retraction `Supersede` refuses, and it is not in the log.**
E8.8 refused a supersession with no replacement facts because it would write a
memory that reads as a retraction, and that argument held. So a caller had no
way to say "stop believing this, nothing replaces it" — which is exactly what
`Archive` is. It is not a log entry at all: the log records what was believed,
and archival records what a caller no longer keeps. Keeping them apart is why
the archive needed no new decode path and no new field on `Memory`.

**Two things break the moment a memory leaves the directory, and both are
invisible until the archive holds something.** The sequence counter reads the
directory, so archiving the whole log restarts numbering at one and hands a
sequence out twice:

```
$ go test ./internal/core/memory/ -run TestTheLogCountsPastWhatIsArchived  # counting the live log only
--- FAIL: TestTheLogCountsPastWhatIsArchived/tree (0.00s)
    archive_test.go:70: Add after archiving the whole log wrote [{Seq:1 ...}], want one memory at 3
```

And `closeIntervals` fails the whole listing on a supersession naming a memory
it cannot find, so archiving a memory something had already replaced would break
every read of that workspace. Both are fixed the same way: the log and its
archive are read together and split afterwards, so a supersession reaching
across them still describes an interval.

**Archiving rewrites the as-of answer, and that is the honest reading.** A
memory set aside is out of `AsOf` as well as `Current`, so a past moment now
reconstructs without it. The alternative is timestamped archival intervals, so
that as-of answers include what was archived later — which is a second temporal
axis over the one E8.8 built, for a curation act the caller can already undo.
What the ticket asked for is recoverability, and `Archived` plus `Restore` is
that. The lineage query is where an archived memory stays visible.

## What I would do differently

`Routes.Archive` and `Routes.Restore` are one-line delegations to the store, and
a reader could fairly call the type a facade over three packages. It earns its
place as the surface an inbound adapter will hold — the ticket asks for routes,
and `Lineage` is real work that belongs in neither the store nor the merging
stage — but if a transport never lands on it, the honest move is to delete it
and let callers hold the store.

## What I still do not understand

Whether `Lineage` should be bounded. It walks the whole connected component of
the supersession graph, which for a workspace that has been consolidated a few
dozen times could return most of the log. A hop limit is the obvious bound and
`graphfs` already has one for expansion; I did not add it because no caller has
asked yet, and a limit chosen without one is a number in a config file that
nobody can justify.
