# E9.4 — Relations

`relation.Graph` is a workspace's curated graph: `Link`, `Unlink` and `List` over
edges someone asserted between two resources, on the one FileSystem the mount
table presents. An edge is a subject, a predicate and an object, and the whole of
it is its address on the tree — `<root>/<user>/<workspace>/<kind>/<name>/<predicate>/<kind>/<name>`,
holding no bytes.

The acceptance is that curated edges are distinct from extracted ones, and the
test that says so is `TestNothingIsDerivedFromWhatWasLinked`: link `a uses b` and
`b uses c`, and `List(a)` is `a uses b` and nothing else. No inverse edge, no
transitive one. An extractor is free to produce both; this is the store where
nothing appears that nobody stated.

## What the pattern was

`kv.Space` with a wider key. Both hold the tree and a root, take a
`workspace.Scope` per call, derive every path through `Scope.Path`, refuse user
scope, refuse a name that is not one flat segment, and know no plugin. Every
verb is asked over `memfs` and over `kvfs` for the reason E9.7 gave: the two
storage shapes disagree about whether the thing above a written name is a
directory. Dropping `Link`'s `Mkdir` leaves every keyspace case green:

```
$ go test ./internal/core/relation/ -count=1     # with the Mkdir removed
--- FAIL: TestLinkAndListRoundTrip/tree (0.00s)
    graph_test.go:96: Link(skill/tailor-cv uses blueprint/cover-letter): link skill/tailor-cv
        uses blueprint/cover-letter: write "/ada/hunt/skill/tailor-cv/uses/blueprint": file does not exist
```

`Unlink` is `Remove` tolerating `fs.ErrNotExist` rather than `RemoveAll`, which
is E9.7's finding applied rather than rediscovered, and it has E9.7's test:
`RemoveAll` on a keyspace takes out whatever else on the mount is stored beneath
the edge's key.

## What surprised me

**The path is the whole record, so there is nothing to race on.** The obvious
shape for "the edges out of a subject" is one file per subject holding a list,
which makes `List` one read instead of a walk. It also makes `Link` a
read-modify-write, and two agents curating one subject at the same time lose an
edge with no error anywhere — the failure `version.RefStore` exists to prevent.
Spending reads to keep every assertion its own key was the whole design decision
of this ticket, and it is only affordable because an edge has no body.

**Filtering by `IsDir` is what keeps a stray file from failing the whole call.**
`List` descends three levels, so anything that is not a directory where a
predicate belongs would be read as one; on a tree that is an error, on a keyspace
it silently is not. Passing over it is `Registry.List`'s rule — something else
standing under a mount is not a broken one of these — and without it
`TestListPassesOverWhatIsNotAnEdge` fails on the tree and passes on the keyspace,
which is the same asymmetry as the `Mkdir`.

**Neither end of an edge is checked for existence.** Refusing an edge to a
document not written yet would make the order things were created in part of the
model, and it would need the graph to hold a catalog — a core package reaching
sideways into another one to validate a name. The graph asserts about names.

## What I would do differently

Nothing structural. `List` taking the subject rather than answering with the
whole workspace's edges is the one call I would defend rather than repeat by
reflex: it is the curated half of E7.5's single-hop expansion, which is the shape
the retrieval layer will want beside it.

## What I still do not understand

**How the reverse question gets answered.** "What is related to this" is a
second index written on `Link` and `Unlink`, and a second index is a second thing
that can disagree with the first. Whether it belongs here, in a projection
(E10), or in the graph backend E7.6 picks is open, and nothing should build one
until something asks the question.

**Unlinking leaves empty directories on a tree.** The predicate directory of a
withdrawn edge stays; on a keyspace the prefix goes when the last key under it
does. It is invisible through the port — `List` reports no edges either way — so
pruning would be extra calls and a race for tidiness. It becomes real if some
kind ever charges for an empty directory.

**Nothing consumes the graph.** Like `kv.Space` and `workspace.Lifecycle`, it is
wired nowhere: the composition root names no relations root, so no config key
for one exists. Deletion already works when it does — a relations root is another
area a `Lifecycle` is configured with, and the same scope derives the same suffix
under it.

The flat-segment rule is now written five times, which is `nrv-e6y` and still
open. The fifth copy was a scope call, the same one E9.7 made.
