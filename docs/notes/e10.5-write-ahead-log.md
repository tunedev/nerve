# E10.5 — Scheduler with a write-ahead log

A projection run is minutes of CPU that no caller is waiting for, and the queue
that delivered the job has already handed it over: `queuefs` claims a message
before the handler sees it, and a broker with destructive reads and no replay
cannot be asked for it again. So `schedule.Scheduler` writes the job down before
it runs it and clears the note when the run says it is done. Whatever the log
still holds is work that was owed, and the next process runs it.

The acceptance is asserted against a run that is killed rather than failed — a
panic, because that is what a lost host looks like from inside the package: the
run does not return, nothing after it runs, and nobody is told.

```
$ go test ./internal/core/schedule/    # with the note written after the run instead of before it
--- FAIL: TestAnInterruptedJobIsRecoveredByTheProcessAfterIt (0.00s)
    schedule_test.go:79: recovered = [], want [{Scope:{User:ada Workspace:hunt} Name:sales}]
--- FAIL: TestAJobIsWrittenDownBeforeItRuns (0.00s)
    schedule_test.go:127: owed while running = [], want [{Scope:{User:ada Workspace:hunt} Name:sales}]

$ go test ./internal/core/schedule/    # with a failed run clearing its note too
--- FAIL: TestAFailedRunStaysOwed (0.00s)
    schedule_test.go:149: owed = [], want [{Scope:{User:ada Workspace:hunt} Name:sales}]
```

## What the pattern was

The log is a tree of one note per job, not a file of appended lines. The verb
set has no append and an object store cannot add a line to anything, so a log
that only a disk could hold would not be a log every mount can keep. `Write` and
`Remove` are enough, because the only question ever asked of it is whether this
job is owed.

The note stands at `Scope.Path(root, job.Name)` and is read back with
`workspace.Locate`, which is what stops the package spelling the layout a second
way — the same move `ingest` made. Recovery therefore descends until it finds
files rather than knowing the depth is three.

A job is the work rather than a run of it, so beginning it twice replaces the
note instead of adding one. That is what keeps a backlog from growing a row per
attempt, and it is the seam E10.6 needs: single-consumer exclusion is a claim on
one note, not a rewrite of the log.

## What surprised me

**Returning `ctx.Err()` from a run is not an interruption.** The first draft
modelled the dying process with a cancelled context, and the test passed with
the write-ahead ordering removed: an error still returns through `Do`, so the
code after the run still executed and wrote the note it was supposed to have
written first. Only a run that never returns discriminates. The panic is not
theatre — it is the smallest faithful model of the failure the package exists
for.

**A failure and a death are the same thing to the next process.** Both leave
nobody to say what happened, so a run that returned an error keeps its note and
is recovered like one that was killed. That makes the contract on `Run` explicit
rather than implied: a job must be safe to run again, because recovery cannot
tell the two apart and re-runs from the beginning. E10.4's convergence proof is
what will make that true for a projection.

**Refusing an unreadable note is the safe direction.** A file standing where a
note belongs and failing to decode is refused with `fs.ErrInvalid` rather than
skipped. Skipping it drops a job silently, which is the one outcome the log
exists to prevent.

## What I would do differently

The first shape was a durable queue: `Schedule` records a job as owed and
`Drain` runs the backlog. It is a nicer story — recovery stops being a separate
verb — but it is a second durable queue in a repo that already has `queuefs`
with a journal and an outbox. Keeping the scheduler to "write it down, run it,
clear it" leaves the queue owning delivery and this owning only the window the
queue cannot cover.

## What I still do not understand

**Nothing schedules anything yet.** E10.1 through E10.4 are open, so there is no
manifest to name and no materialisation to run; the handler is supplied at
composition and the composition root has nothing to supply. The tests drive the
real log over a real mount, so what is unproven is the wiring rather than the
recovery.

**Two processes recovering the same log will both run the job.** Nothing here
excludes a second one, and re-running is only harmless because the work is meant
to converge. E10.6 is that ticket, and whether the exclusion is a lease on the
note or a claim on the Parquet it writes is still open.

**Whether a job that fails every time should stay owed forever.** It is
recovered at every start, fails, and stays. That is correct while the failure is
a dependency being down and wrong while it is a malformed manifest, and the log
cannot tell those apart — which is E12.3's classification, not this package's.
