# E1.5 — the plugin registry

`Registry` in `internal/core/vfs`: kind names mapped onto factories, and
`Table` turning a list of `MountSpec` into a mounted `MountTable`. `mounts` in
the config file is that list; `Config.MountSpecs` maps it into the domain's
vocabulary, and `cmd/nerved` registers the kinds a build has and mounts whatever
the config asks for.

## What the pattern was

The third altitude of the thesis: one interface, a mount table, and
implementations named by data. E1.4 made the table dispatch to a plugin. This
makes the plugin arrive from a config document, so a new mount is a line of
JSON and not an edit to a switch.

Nothing in the registry knows a concrete plugin, and nothing in `internal/core`
imports one. Registration happens at the composition root, which is the only
place that does.

## What surprised me

**A settings map is the whole reason this is not a factory.** Every kind needs
different things and the registry cannot know what, so settings are
`map[string]string` and the plugin parses what it needs where it is built. The
alternative — a typed settings struct per kind — puts the kinds back into the
core, one field at a time.

**A mount table is a list, and the config layers are not.** Defaults, file,
environment and flags each name a setting; only the file layer can carry a list
at all. Mounts therefore come from the file alone. That asymmetry is honest
rather than a gap: an operator changes the tree by editing the document the
environment names.

**Adding a slice to `Config` made it non-comparable.** Three existing tests
compared configs with `!=` and stopped compiling. `reflect.DeepEqual` is the
fix, and the compile failure was the right place to find out.

**The unknown-kind error is an operations surface.** A misspelled kind is the
boot failure this ticket makes possible, so the error names the kinds the build
actually registered. `fs.ErrNotExist` carries it, matching the sentinel the
table already uses for a path no mount holds.

## What I would do differently

Nothing yet, though `config.Mount` and `vfs.MountSpec` are the same four fields
spelled twice, joined by a mapper. Go would decode straight into `MountSpec`
without tags, and the duplication would go. It stays because the JSON spelling
is a wire concern and the core does not carry one — the same rule that keeps
`*sql.Tx` out of a port. Worth revisiting only if a third vocabulary appears.

## What I still do not understand

Whether `Table` should stop at the first bad spec or report every problem the
way `Config.Validate` does. Stopping keeps a process from booting on half a
table and avoids building plugins that would be thrown away, but an operator
fixing three bad mounts pays three restarts. When plugins hold real resources
there will be a `Close` to answer to, and that is when the trade changes.

Whether the acceptance criterion is fully demonstrable yet. Config reaches the
registry with no recompile — the binary proves that by failing on a kind it does
not have — but the mount that succeeds only exists in tests, because the first
plugin is E2.1. The end-to-end run is that ticket's evidence to produce.
