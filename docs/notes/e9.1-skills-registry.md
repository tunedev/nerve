# E9.1 — skills registry

`skills.Registry` is a workspace's skill library: list, create, get, delete,
search, tree, bundle and copy over the one FileSystem the mount table presents.
A skill is a directory — `SKILL.md` saying what it is for and how to do it, and
whatever files it needs beside it — so which storage kind a library sits on is a
mount rather than a decision inside the registry.

## What the pattern was

A core package over the uniform interface, which is the shape
`workspace.Lifecycle` and `version.Versioner` already have. Nothing here knows a
plugin: every path comes from `workspace.Scope.Path`, every read and write is a
port verb, and the eight verbs are arrangements of `Mkdir`, `Write`, `Read`,
`ReadDir`, `Stat` and `RemoveAll`.

The verb list itself argues for two shapes rather than one. `list` and `search`
answer "which skill", `get` and `bundle` answer "what does it say"; so `Card` is
what a skill declares about itself and `Skill` is a card with the instructions
behind it. That is the L0/L1 escalation E6.5 will want, arrived at from the verb
list rather than from the ticket that names it.

Ranking is a port. `Matcher.Rank(ctx, task, cards)` is the only thing standing
between a task and the library, and the second implementation is the reason it
exists: term overlap over the cards today, an embedding matcher over E7.2's
provider next. The registry holds a `Matcher` and learns neither.

Be plain about what shipped: **the laptop matcher is lexical, not semantic.**
`termmatch` scores a card by the share of the task's vocabulary it uses,
weighting a word by how few cards use it, so a rare word decides the order and a
word every card shares decides nothing. It answers the acceptance test — a task
phrased in the caller's words returns the skill for it first — and it will not
match a task to a skill that says the same thing in different words. The port is
what makes that a swap rather than a rewrite.

## What surprised me

**Versioning arrived by composition and cost nothing.** The sequencing says E9
needs E4, and the honest reading of that turned out to be "E4 must exist", not
"E9.1 needs version verbs". A skill library is a subtree of a mount, so
`version.NewVersioner(treecopy.New(table, library, state), objects, refs)`
commits, diffs and restores skills with neither package importing the other.
`version_test.go` commits a library, edits it, commits again and restores — and
exists to make a version verb added to the registry visibly redundant.

**A length filter is a second, dumber stopword filter.** `termmatch` dropped
words under three letters, which is the textbook move, and it deleted `cv` — the
word the whole job-hunt domain turns on. The acceptance test failed on a task
that named the thing it wanted. Inverse document frequency already demotes words
every card shares; the length cut was a filter that could not know that, applied
on top of one that could. Two letters stay now, because that is what a domain's
acronyms are.

**`List` wants opposite answers about two failures that look identical.** A
directory in the library holding no document, and a document that will not
decode, are both "no skill here" at the call site. The first is not a skill and
is passed over: a tree under a mount is a tree, and something else standing in it
is not a broken skill. The second fails the whole call, for the reason
`Lifecycle.List` fails — a short list of skills is indistinguishable from a
correct one, and the caller is about to choose from the ones it was not told
about.

**Overloading one path derivation to also mean "the library" put the one invalid
name through the one path that did not check it.** `dir(scope, ".")` was how
`List` reached the library root, so `.` had to be exempt from the name rule, so
`Create` with the name `.` wrote the library's own document. The refusal test
caught it. Root cause was one function answering two questions; `library(scope)`
and `dir(scope, name)` answer one each, and the name rule now has no exemption.

## What I would do differently

Not overload the path helper, which is the same lesson as above stated before the
test rather than after it. Beyond that: the flat-segment name rule is now written
a third time — `workspace.validSegment`, `version.ValidateRefName`, and
`skills.validName` — each with a comment noting it is the same rule as the last
one. Three copies is where a shared rule earns its place. Filed rather than
folded into this ticket, because it touches two packages that are done.

## What I still do not understand

**Whether the matcher should be handed the cards or an index.** `Rank` takes the
whole card set per call, which is right for term overlap and wrong for
embeddings: the named second implementation would re-embed every card on every
search unless it kept a cache the port cannot see. The honest shapes are a port
that indexes on write and queries on read, or a matcher over `vectorfs` where
the index is a mount and `Rank` is a read. E7.3 and E7.9 will decide it, and the
signature here is the thing most likely to change when they do.

**Whether `Copy` across users is a question the registry should be answering.**
It takes two scopes and will happily move a skill from one user's workspace to
another's. Nothing above it checks that today because nothing is above it yet.
Cross-user isolation is a correctness requirement, and this is the first verb in
the system that spans two scopes on purpose.

Nothing consumes the registry yet — there is no inbound surface for it, the same
place `workspace.Lifecycle` is in. The composition root does not wire it, so
`nerved` does not name a skills mount, and E9.6's filesystem routes or whatever
first inbound adapter arrives is where the areas, the root and the matcher get
chosen from config.
