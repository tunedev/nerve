# E12.9 — Refuse the Kubernetes writer/reader split

Nerve runs as one process, `nerved`, and will not be split into writer, reader
and indexer deployments. `cmd/nerved` is the only binary, and its `main.go`
composes both ends in one process: the admin and API servers answer reads,
and `consuming.start(ctx)` runs the ingest worker beside them on the same
context and stops before the mounts are released.

This agrees with the Forge refusals table (writer/reader/indexer fan-out:
single process, revisit on evidence) and with the roadmap row: one process
until it demonstrably hurts.

## What was refused

A topology in which uploads land on writer pods, queries go to reader pods and
ingestion runs on indexer pods, each a separate deployment of a separate role
that scales on its own. It is the shape a platform takes when read load, write
load and indexing cost differ by orders of magnitude and are owned by different
teams. Nerve has one operator and none of those ratios measured.

Identical replicas are not what is refused. The ingest worker joins the
`ingest` consumer group (`cmd/nerved/ingest.go`), so a second `nerved` shares
the queue rather than repeating it, and `schedule.ErrHeld`, backed by the
`pglease` adapter, lets a second process pass over a job another is running. Those are Tenet 2's scalability and they
stay.

## What it would cost here

Not a new `cmd/` directory. The cost is the in-process state that assumes the
reader is also the writer:

- `graphfs` loads its graph once, in `Open`, and serves every read from memory
  under its own mutex (`internal/adapters/outbound/graphfs/graphfs.go`). A
  reader pod would answer from the graph it loaded at boot and never hear what
  the writer added. `cmd/nerved/hybrid.go` already names this failure — "a
  graph mount two graphs" — as the reason a fusion reads through the shared
  table instead of building its own copy.
- `localrefs` is "the ref store for a single nerved": its compare-and-set is a
  mutex, atomic for this process and no other. The Postgres ref store that
  would give a second process a truthful answer is named in its package
  comment and not built: `internal/adapters/outbound` has `localrefs` and
  nothing else implementing refs.
- The ingest worker writes the ledger and derived levels through the same mount
  table the servers read. A separate indexer turns that shared table into a
  network contract between deployments.

Every one of these would need a shared backend or an invalidation channel
before the split could run correctly. That is new code in the adapters, not
config.

## What stays

One binary, every role in it, and more copies of it when the queue needs them.
The seams a split would cut along already exist as ports — the queue between
upload and ingest, and `RefStore` and `WorkingCopy`, whose comments name the
Postgres implementation for "a workspace more than one process opens" — so
reversing this is composition in `main.go` plus the shared backends above, not
a redesign.

## The evidence that would reopen it

Not "more users" or "more documents". Any one of these, measured:

- API read latency in `nerve.mount.call.duration` degrading during ingest
  bursts, where adding identical replicas does not recover it because the
  contention is inside each process.
- Indexing that needs a footprint the serving process must not carry, such as
  an in-process model needing a GPU or several gigabytes of memory. Today every
  model call goes through the gateway to a remote endpoint, so this is not true.
- A format processor crashing the process and taking reads down with it,
  observed rather than hypothesised.

## What enforces it

Nothing. A second directory under `cmd/`, or a role flag that skips
`consuming.start`, compiles, passes lint and passes every test. No `depguard`
rule can see a deployment topology. The refusal is held by this note, the
roadmap row and review.

## What surprised me

The first cost in the list above is not a cost of the split alone. `graphfs`
and `localrefs` also make two identical replicas unsafe, since each replica
would hold its own graph and its own mutex. So "one process" is not only a
refusal of topology. Today it is a correctness condition for any build that
mounts a graph or keeps refs locally.

## What I still do not understand

Whether the config should refuse a second replica when those single-process
mounts are configured, the way it already refuses a queue without an ingest
root. Nothing detects two `nerved` processes opening the same graph blob, and I
have not decided if that belongs to this refusal or to `graphfs`.
