# E6.3 — a format is a package

`ingest.Processor` reads one family of formats and returns text. `ingest.Registry`
maps a media type onto the package that reads it. `ingest.Extraction` is the
stage that looks up the type a resource declared, runs what it finds and writes
the words beside the content. `textproc` and `pdfproc` are the two packages.
Adding a third is a package and a line in `registerProcessors`.

E6.2 left the seam open — "a per-format processor is not obviously one of these
stages; it may be a stage that dispatches, or the list may become
per-content-type". It is a stage that dispatches. The list stays flat, so
summarising and indexing come after extraction for every format rather than once
per format.

The acceptance is asserted at both ends:

```
$ go test ./cmd/nerved/           # what a build can read is what registered
--- FAIL: TestRegisterProcessorsDeclaresTheFormatsThisBuildReads
    processors_test.go:25: MediaTypes() = [text/markdown text/plain], want [application/pdf text/markdown text/plain]

$ go test ./internal/core/ingest/ # with the format packages swapped for each other
--- FAIL: TestASecondFormatIsASecondRegistrationAndNothingElse
    extract_test.go:59: text of transcript.txt = "tfard tsrif a", want "A FIRST DRAFT"
    extract_test.go:62: text of mirror.bin = "A FIRST DRAFT", want "tfard tsrif a"
```

## What the pattern was

The same three parts as `vfs.Registry`, one altitude down: a name registered at
composition, a lookup that fails naming what the build has, and nothing in the
core that knows a concrete implementation. Storage kinds arrive by config
because an operator picks them; formats arrive by media type because the upload
picks them. That is the only difference, and it is why a processor takes no
settings map.

`resource.Store` grew two pairs rather than one. `Content` is the read a stage
makes of the resource it was handed — a grant is for whoever is outside the
process, and minting a token to hand straight back to the same store would be a
signature checking itself. `Derived`/`SetDerived` are sidecars beside the
content, named by kind, and they are general rather than text-shaped so that
E6.4's L0, L1 and L2 are three more kinds instead of three more methods.

The sidecar write goes through the same observed tree the upload did, and queues
a job like everything else. It does not queue a second ingestion, because
`Store.Resolve` answers only for a resource's meta file — the gate E6.2 put there
for the content file turns out to cover every derived file too, at no cost.

## What surprised me

**A format this build cannot read must not be a failure.** The first draft
returned the registry's `fs.ErrNotExist` from the stage. One PNG then does this:

```
$ go test ./internal/core/ingest/
--- FAIL: TestExtractionLeavesAFormatThisBuildCannotRead
    extract_test.go:78: Run: handle "resources/ada/hunt/diagram.png/meta.json":
        ingest "diagram.png": stage "extract": no processor for "image/png";
        this build reads text/plain: file does not exist
```

The worker's rule is that a handler failure ends the run, so an upload nothing
can read stops every job behind it, forever, however many times it is retried.
It is the fourth do-nothing branch of the same shape the pipeline already has.
A processor that could not read a file of its own format is the opposite case
and does fail: a corrupt PDF was meant to become searchable and did not.

**The PDF parser reports malformed input by panicking.** `rsc.io/pdf` and the
fork of it in use both call a helper that panics, and it is reached from
ordinary files — a cross-reference offset naming the wrong byte is enough:

```
$ go test ./internal/adapters/outbound/pdfproc/   # with the recover removed
panic: loading {1 0}: found pdf.dict instead of objdef [recovered, repanicked]
	github.com/ledongthuc/pdf.(*Reader).resolve(...)
```

Recovering belongs in `pdfproc` and nowhere else: it is the only place that
knows the panic is a parse failure rather than a bug. A recover in the stage
would swallow real defects in every processor.

**A PDF cannot be streamed.** The cross-reference table is at the end of the file
and names offsets into the rest of it, so the parser wants random access and the
package reads the whole upload into memory. That sits oddly beside a store whose
whole shape is "content larger than memory arrives in pieces", and it is the
format's constraint rather than a shortcut: there is no reading a PDF front to
back.

**`go mod tidy` moved ten OpenTelemetry modules out of the indirect block.** They
are direct imports of `internal/adapters/outbound/telemetry` and had been
labelled indirect since they arrived. Unrelated to this ticket and left
corrected rather than reverted.

## What I would do differently

The first draft of the sidecar pair was `Text`/`SetText` on the store. It made
E6.3 shorter and E6.4 longer, and it put "what ingestion produces" into the
vocabulary of the thing that stores uploads. A kind parameter costs one argument
and is the same code.

## What I still do not understand

**Whether a processor should return more than a string.** PDF page boundaries
are real information and this throws them away, joining pages with a newline.
L2 detail may want them back. The guess is deliberately the smaller one: a
string is what summarising, embedding and indexing all take, and nothing
downstream exists yet to say otherwise.

**Which library reads PDFs in the end.** `github.com/ledongthuc/pdf` is a fork of
`rsc.io/pdf` with plain-text extraction on top: pure Go, no dependencies, and an
untagged version. The alternatives are nameable — `rsc.io/pdf` with the line and
word-spacing heuristics written here, or `pdfcpu` — and the choice is inside one
file, which is the whole point of the package boundary. What is not yet known is
how it does on PDFs that were not built by the test.

**A resource whose declared type is a lie.** Nothing sniffs content. A `.pdf`
uploaded as `text/plain` comes back as its own bytes rendered as text, and a
text file uploaded as `application/pdf` fails the run. Sniffing is a decision,
not an omission, and it belongs with whatever E6.6 reports.
