# E11.4 — The escape suite, and the one attempt that does not fail

Three attempts, made by the party the mount exists to contain: a process holding
nothing but a path inside it. Path traversal, symlink escape and handle reuse
each fail and each is asserted, in
`internal/adapters/inbound/fusefs/escape_test.go`.

A fourth thing is asserted there too, and it is the finding: a symlink planted
behind the mount, standing inside one scope and pointing at another, is
followed. `nrv-aeyc`.

## The store is a host directory, and that is the whole design of the suite

E11.3's composition cases run over `memfs`. A tree in memory resolves a name the
same way the derivation already did, so a case over one fails only when the
derivation fails — which makes it a good case for the derivation and a blind one
for everything below it.

`localfs` resolves through `os.Root`, and the kernel follows a link inside the
syscall, long after any name could have been cleaned. Over a real store the
derivation layer and the store layer give different answers, and only then can a
case tell them apart. Every case here is over one.

## The three attempts

**Traversal.** The spellings are the layout's own — `files/bob/cv/secret` and
its neighbours — because those are the only ones that reach Nerve. They are run
twice: through an ordinary path, and through a root held on the mount, where
`os.Root` resolves with `RESOLVE_IN_ROOT` and gives a process the resolution
rules `pivot_root` would. The climbs are asserted only in the second, because in
the first they are not Nerve's to refuse.

**Symlink.** Every target a caller could name freely if the verb existed: the
host root, a climb out of the mount, and the neighbour's subtree spelled as the
layout has it. All refused with `ENOTSUP` — the mount serves no link verbs at
all — and nothing stands at the link name afterwards. A hard link is refused
beside them, and `readlink` of an ordinary entry is `EINVAL`: there is no target
in this mount for the kernel to resolve in the host's vocabulary.

**Handle reuse.** A descriptor whose copy is already taken, across the removal of
the path it was opened through. The read afterwards fails, and the second half of
the case is where the content of a *dirty* one lands: at the path the descriptor
was opened through, inside the scope, resurrecting the removed entry.
`close(2)` reports success, which is what a caller sees for a write to a path
that is gone.

## What surprised me

**The handle case fails because of a setting made for a different reason, and I
had it backwards.** E11.2 item 5 measured a handle outliving a revocation and
concluded that revocation is a statement about what a *new* open can reach. Here
the old handle reads nothing either — and not because the descriptor is
revoked. Nothing is cached, so the kernel revalidates before the read, the
revalidation is a `Getattr` on a path that is gone, and the read fails before
the open copy is ever consulted. Item 8 predicted exactly this in its last
sentence and I did not connect the two until the port log showed a `Stat` where
I expected a `Read`. The containment is real and it is rented: it lasts until
somebody sets an entry timeout for speed.

**A traversal table written from outside the mount passes against a filesystem
with no containment in it.** My first draft asserted the climbs. Five passed and
`files/../../../../../../etc/passwd` read the host's password file, which is not
a hole — the climb is resolved above the mount point and the filesystem is never
asked. E11.2 wrote that down and I wrote the table anyway, because the entries
*look* like the attack. The suite now asserts that premise
(`TestAClimbSpelledFromOutsideAMountNeverEntersIt`) rather than leaving it in a
comment, since a silent premise is what let me write the wrong table twice.

**`filepath.Join` cleans, so it answers the case before the kernel sees it.** The
climbs went in through `filepath.Join(dir, spelling)`, which resolves the `..`
lexically in Go and hands the kernel a path that never mentioned the mount. A
traversal case has to concatenate. This is the same shape as the finding above
one layer up: the layer that resolves a name is the layer that can be fooled by
one, and here the layer was the test.

**The escape is planted, not spelled.** I expected the symlink case to be about
what a process inside could create, and that half is closed tight — `ENOTSUP`
from the mount, a derived target through the view. The hole is a link that is
already there. `os.Root` contains `localfs` to the *area*, the scope subtree is
inside the area, and a link from one scope to another never leaves the root the
kernel is checking against. `isolation_test.go` already asserts this leak for a
caller holding the mount table and concludes "so the containment is the view's".
The view does not hold it either, and no case had asked.

## What I would do differently

Log the port before writing the assertion. Both of the surprises above came from
wrapping the filesystem in twenty lines that print every verb it is asked for.
The handle result was a mystery for as long as I was reading exit codes and
obvious the moment I could see that the port was never called. That wrapper
should have been the first thing written, not the thing I reached for when an
assertion disagreed with me.

## What I still do not understand

**Where the sub-root verb goes, if `nrv-aeyc` is fixed the way it should be.**
Making the scope subtree the plugin's own containment root is the fix that
restores the invariant at the source, and it wants an accessor —
`Sub(name) (FileSystem, error)`, `localfs` implementing it with
`os.Root.OpenRoot`. `MountTable`'s accessors take no path and are table-wide,
which is the documented shape that already forced the keyspace area out of the
conformance suite. A sub-root reached through a table has to answer per path or
it is the wrong verb, and that is a change to the settled accessor rule rather
than a use of it.

**Whether a mount namespace belongs to E11 at all.** The traversal case is run
against `os.Root` because that is `RESOLVE_IN_ROOT` for three lines instead of a
namespace, and it is honest about testing the kernel. A real process confined by
`pivot_root` is still nobody's ticket. E11.2 left this open, E11.3 left it open,
and this ticket needed it and worked around it.

The finding, through a real mount over `Lifecycle.Open(alice)`, with the link
planted by a caller holding the table:

```
plant  /files/alice/cv/peek -> /files/bob/cv
cat $mnt/files/peek/secret  -> "bob's salary expectations"

```

The handle case, with every port verb logged, showing what refuses the read:

The `Stat` is the revalidation. There is no `Read` after the removal: the open
