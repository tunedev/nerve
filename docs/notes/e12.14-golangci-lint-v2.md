# E12.14 — the golangci-lint v2 config

`errcheck`, `staticcheck` and `depguard` named explicitly under `version: "2"`,
with their options under `linters: settings:` and the architecture rule that
E1.6 extends living in the `depguard` block.

## What the pattern was

One config file as the home for every mechanical rule the tenets claim. The
linters are named rather than left to `default: standard`, so the file says what
it enforces instead of deferring to whatever a release decides `standard` means.

## What surprised me

**`golangci-lint run` does not notice a v1 config.** Written with `version: "2"`
but the settings under a top-level `linters-settings:` — the v1 key — the run
reports `0 issues` and exits green. The depguard rules are simply not loaded.
Nothing fails; the boundary just stops existing. `config verify` is the only
command that catches it:

```
jsonschema: "" does not validate with "/additionalProperties":
additional properties 'linters-settings' not allowed
```

So `make lint` runs `config verify` before `run`. The ticket's acceptance is
that the config loads under v2 nesting, and until that line existed the
acceptance was unfalsifiable — a silently-dead config and a correct one produce
identical output. CI already had this by accident: `golangci-lint-action` runs
`config verify` on its own unless told not to.

**`check-type-assertions` is an architecture rule, not a style one.** errcheck
leaves `x.(T)` alone by default. The settled decision in `CLAUDE.md` is that
capability is reached through an accessor and never through `fs.(Symlinker)` —
the unchecked single-value form is exactly the move being forbidden, and this is
the one line that makes a linter say so.

**The CI pin is load-bearing, not hygiene.** `version: latest` was resolving to
a binary that happens to be built with go1.27. v2.3.0 is not, and against a
go.mod targeting 1.27 it refuses to start:

```
can't load config: the Go language version (go1.24) used to build
golangci-lint is lower than the targeted Go version (1.27)
```

A moving `latest` means the config's ability to load is a property of whatever
was released this week. Pinned to v2.13.1.

## What I would do differently

`staticcheck` runs the default check set with `-ST1000` lifted, so a package
without a package comment fails. Every package here already has a `doc.go`; the
rule only keeps that true. The other five style checks the default suppresses
stay suppressed — E12.13 gives formatting opinions to `gofmt` alone, and
reopening ST1003 or ST1020 would take that back.

## What I still do not understand

Whether `files: ["**/internal/core/**"]` is the right anchor for the depguard
rule. It matches today and the probe proves it, but it is a path glob standing
in for an architectural fact. E1.6 has to add the adapter denial to this same
block, and a rule keyed on import path rather than file path may read better
once there are two of them.

Whether the `_test\.go$` exclusion for errcheck survives real tests. It predates
this increment and no test yet ignores an error that matters.

## Blocked

Unchanged from E1.1: the installed `golangci-lint` is v1.64.8 and cannot read
this file (nrv-9hz). Verified instead against a v2.13.1 binary — the version now
pinned in CI — which reports `config verify` clean, `run` clean, and fires all
three linters when probed. The fix is an install, not a code change:

```
go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.13.1
```
