# E3.2 — streamfs

A mount of append-only streams, each a ring buffer of the most recent bytes. The
ticket's acceptance is one sentence — a reader observes writes without polling the
whole file — and it is the `Streamer` accessor that carries it: `OpenRead` hands
back what the ring holds and then waits for what is appended.

```
$ go test ./internal/adapters/outbound/streamfs/ -run TestConformance -v | grep -c '^    --- PASS'
30
$ go test -race ./internal/adapters/outbound/streamfs/ -run 'TestAReader|TestEveryReader|TestConcurrent' -v | grep '^--- '
--- PASS: TestConcurrentAppendsReachAFollowerOnce (0.00s)
--- PASS: TestAReaderReceivesAnAppendMadeAfterItOpened (0.00s)
--- PASS: TestEveryReaderReceivesEveryAppend (0.00s)
--- PASS: TestAReaderEndsWhenTheCallerIsDone (0.05s)
--- PASS: TestAReaderEndsWhenNothingIsAppended (0.02s)
```

## What the pattern was

**Three descriptors at once, and the suite reads the plugin against all three.**
`AppendOnly`, `Broadcast` and `ObjectStore`. Append-only because a write adds;
broadcast because every reader receives every append; object store because a
stream name is a name and not a path through directories. Thirty cases run and
eight skip, and the eight are the ones that would have asked a stream to be
replaced, cut, or walked.

**`Broadcast` had no case in the conformance suite and still does not.** The suite
says why: the port has no second reader identity, so it cannot tell readers that
each receive an append from readers that take it from one another. Two followers
in this package's own tests can, because they are two `io.ReadCloser`s the case
holds at once, and that is where the claim is asserted.

**Offsets are absolute, counted from the first byte ever written.** A reader's
position stays meaningful after the bytes under it are dropped, which is what
lets an overrun be noticed rather than guessed at: `since(offset)` compares the
reader's position with the oldest byte still held and fails with `ErrOverrun`
instead of handing back what is left. A follower that silently jumped to the
window would report a gap in a log as an absence in one.

**The wake-up is a channel the append closes**, taken by the reader while it holds
the ring's lock and waited on after it lets go. A `sync.Cond` is the shape this
wants, and cannot be selected on alongside a context and a timer.

## What surprised me

**A following reader breaks the conformance suite unless the wait is bounded.**
`OpenRead streams the content` calls `io.ReadAll`, which never returns against a
reader that waits forever for the next append. That is not the suite being wrong:
a reader with no bound is a mount that holds a connection open until something
else times out. So the wait has two ends — the caller's context, and the mount's
`follow` — and the suite runs with `follow` at zero, which is a reader that ends
as soon as it has caught up. The bound the test needed turned out to be the bound
Tenet 3 wanted anyway.

**`OpenWrite` does not buffer here, and the port's wording had to give.** The port
says the write is not complete until `Close` returns nil, and `memfs` honours that
by holding the payload until then. A stream mount that did the same would keep the
bytes from the very reader it exists for, so each piece is appended as it arrives
and `Close` adds nothing. `AppendOnly` had already made "replaces the content"
untrue of this kind; this is the second half of the same departure.

**`Create` is not a truncation.** The port says it truncates what is already there.
Under `AppendOnly` nothing is ever shortened, so `Create` of a stream that exists
leaves it. No conformance case caught this either way — `Create truncates what is
already there` is gated on `replacing` — which is exactly why it is asserted here.

## What I would do differently

Decide the namespace shape before writing a walk. I started to mirror `memfs`'s
tree and stopped: a stream mount has no directories to make, and `kvfs`'s flat
keyspace with the key-over-prefix listing rule is the shape that was already in
the repo for exactly this. The listing fold is `kvfs`'s, deliberately.

## What I still do not understand

Whether `follow` belongs to the mount at all. It is per-mount configuration today,
so one operator's choice governs every reader of every stream on it; a caller that
wants a snapshot passes no deadline it can express, it just gets `Read`. The
alternative is a per-read bound, and the port has nowhere to put one that is not a
context — which a caller can already set, and which is the other end of the wait.
Two knobs where one might do.

Whether an overrun should end the reader or restart it at the oldest byte. It ends
it now, because a caller that was told it fell behind can decide; but the caller
that most wants to follow a log is the one least able to keep up, and it will meet
`ErrOverrun` and have to reopen. A reader that reported the gap and carried on
would need somewhere to put "you missed N bytes", and `io.Reader` has nowhere.
