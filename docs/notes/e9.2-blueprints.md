# E9.2 — blueprints on the identical shape

A blueprint is a directory holding `BLUEPRINT.md` and whatever files it needs
beside it, listed, created, got, deleted, searched, walked, bundled and copied by
the same registry that serves skills. `skills.Registry` became
`library.Registry` over a `library.Kind`, and the kind is the only thing that
differs between the two.

## What the pattern was

The kind is data handed to the registry, not a type the registry knows:

```go
type Kind struct {
	Name     string // "skill", "blueprint"
	Filename string // "SKILL.md", "BLUEPRINT.md"
}
```

`library.Skills()` and `library.Blueprints()` are the two there are today, not
the two there can be. `kind_test.go` runs every verb over three kinds, and the
third is invented in the test file — the package has never heard of a checklist
and answers for one anyway. That is the acceptance: no verb was added, no branch
was taken on which kind is being served, and no route logic exists to change.

The generalisation was almost entirely subtraction. The frontmatter format, the
card-and-body split, the scope-derived paths, the mount root and the `Matcher`
port were kind-neutral already; the diff to the verbs is `Document` the constant
becoming `r.kind.Filename` and the error strings learning to say which kind they
are about. What a skill and a blueprint declare about themselves is the same
declaration, so one decoder reads both.

The package was renamed because a package named `skills` holding blueprints is a
lie, and the entity type `Skill` became `Document` for the same reason. The
constant named `Document` had to give the name up: a document is the thing, not
the file it is written in.

## What surprised me

**The kind is not the root, and nothing had to be taught that.** Two libraries
can share one mount — `TestALibrarySeesOnlyItsOwnKind` puts skills and
blueprints under the same prefix — because `List` already passes over a directory
that holds no file of this kind. That was E9.1's "a tree under a mount is a tree,
and something else standing in it is not a broken skill", written for scratch
directories, and it turned out to be the rule that makes a second kind free.
Where a library sits stays a mount; what it holds is the kind; the two are
independent.

**The extraction landed here rather than in E9.3, and it had to.** E9.3 is
"extract the kernel from what E9.1 and E9.2 actually needed", so the expected
shape of this ticket was a second registry to extract from later. But a second
copy of 300 lines would have proved the shape does *not* generalise, which is the
one thing this ticket's acceptance asks. The work E9.3 names in its own
acceptance is untouched: a third kind today needs a `Kind` value written in Go at
a composition root that does not exist yet, and E9.3 is where that value comes
from config instead. `nrv-mq4` carries this.

**A kind that cannot name its own file is a startup failure, not a search that
finds nothing.** `Kind{Name: "checklist", Filename: "docs/CHECKLIST.md"}`
describes documents two directories deep, which `List` never walks: it would
answer "no checklists" forever, correctly and uselessly. `NewRegistry` refuses it
where it refuses a nil matcher and an unrooted root. The rule is `validName`, the
one the document names already use, rather than a fifth spelling of the
flat-segment rule.

## What I would do differently

Name the entity `Document` from the start. `Skill` was right for one kind and
wrong the moment there were two, and the rename cost a pass over every comment in
the package.

## What I still do not understand

**Whether a kind will stay this thin.** A kind is a filename and a label because
that is all the second kind needed. The first kind that wants a second
frontmatter key — a blueprint declaring what it produces, say — makes `Kind`
carry a decoder, and then it is not data any more. Whether E9.3's config can
declare that, or whether it is the point where kinds become plugins, is open.

**Whether two kinds under one root is a configuration anyone should be allowed
to write.** It works, and it is tested, and it means a single directory can be a
skill and a blueprint at once with nothing saying which it is. Today the answer
is that roots are config and config is the operator's problem; that is an answer,
not a good one.

Carried over from E9.1 and still true: nothing consumes either registry, so the
composition root names no library mount, and `Copy` still spans two scopes with
nothing above it checking that the two belong to the same user.
