# E4.4 — the working copy

`version.WorkingCopy` is the port the versioner now holds instead of a
`vfs.FileSystem` and a root: the content at a copy's paths, and the version it
was taken from. `treecopy.Copy` is the implementation over the mutable tree —
the content is the tree under one root of a mount, where it stands is one file
beside it.

```
$ go test -count=1 -v ./internal/core/version/ ./internal/adapters/outbound/treecopy/ | grep -c '^--- PASS'
28

$ go test -race -count=1 ./...
(all packages ok)

$ make lint
0 issues.
```

The acceptance — reconcile resolves divergence between working state and refs —
is one test with two copies over one set of refs. The second copy is taken from
a version, the ref moves off it, the copy edits its own tree, and both kinds of
divergence are then true at once. It discriminates in both arms. With `Commit`
reading the ref instead of where the copy stands:

```
--- FAIL: TestReconcileResolvesDivergenceBetweenTheCopyAndTheRef
    working_test.go:45: committing from a copy the ref moved under returned <nil>, want version.ErrConflict
```

and with `Reconcile` restoring content without moving the copy:

```
--- FAIL: TestReconcileResolvesDivergenceBetweenTheCopyAndTheRef
    working_test.go:68: commit after reconciling: ref "main" stands for "sha256:4f31c37...", not "": ref moved under the write
```

## What the pattern was

**A port earns itself by the state it carries, not by the verbs it wraps.** A
working copy that was only `Walk`, `Write` and `Remove` would be `vfs.FileSystem`
renamed — three verbs forwarded and nothing gained. What makes it a port is
where the copy stands. A tree alone can only say how its content differs from a
ref; a tree that remembers what it was taken from can also say the ref moved
underneath it, and that is the difference between a commit that refuses and a
commit that silently drops a version nobody saw.

**The second implementation is nameable, which is the calibration rule's test.**
The tree under a mount with where it stands beside it, for a single nerved; the
same tree with where it stands in the Postgres table that holds the refs, for a
workspace more than one process opens. That is the split E4.2 made for
`RefStore`, for the same reason — a copy and the refs it is compared against
have to agree about who won a race.

**Compare-and-set from where the copy stands is what makes a conflict real.**
E4.3's `Commit` read the ref, walked the tree, and set the ref from what it had
just read, so the losing window was microseconds wide and the test for it needed
a ref store that lied about `Resolve`. Taking the expected value from the copy
instead makes the window as wide as the copy's life: two copies, one commits, the
other is told. That test now uses two real copies and no fault injection.

**`Restore` is content, `Reconcile` is content and position.** In E4.3
`Reconcile` was `Restore` after a `Resolve` and nothing else, which made it an
alias. Splitting them gives each a job: restoring an older version leaves the
copy standing where it stood, so committing the older content records a revert
onto the version the copy is already on rather than colliding with it;
reconciling puts the copy back on the ref, which is what makes the refused
commit land afterwards.

**Where a copy stands is kept beside the copy, not in it.** A state file inside
the root would be content the copy holds: every version would record it and every
diff would report it changing on each commit. `TestWhereACopyStandsIsNotContentOfIt`
is what keeps that true, and with the state path joined under the root it says
`the copy holds [a.md versions/base], want only what was written to it`.

## What surprised me

**Making the base the expected value quietly removed branching, and the fix was
one line rather than a weaker rule.** With `expected` always the copy's base, a
copy standing at a version cannot be committed onto a ref that stands for
nothing — the compare-and-set demands the new ref already stand where the copy
does. That broke `TestPurgeRemovesAVersionNoRefLeadsTo`, which commits one copy
to `main` and then to `scratch`, and the failure was right about the mechanism
and wrong about what should happen: a ref standing for nothing has no version to
protect, so nothing is lost by creating it. `point` is where that lives, and the
strictness is kept everywhere it means something.

**A sweep can strand a working copy, and the refs are no longer the only roots.**
`Purge` computed reachability from every ref. A copy stands on a version that a
ref may since have been deleted from or moved off, and that version is still the
one every verb comparing against the copy has to read — so it is a root of the
sweep. That also changed what the old purge test was demonstrating: the copy is
left standing on the abandoned version by the commit that made it, and it takes
a `Reconcile` to move off before the version is unreachable at all.

**The versioner stopped importing `internal/core/vfs` entirely.** That was not
the goal and it is the clearest evidence the port is in the right vocabulary:
nothing left in the versioner is spelled in the mount table's terms, and the
`path.Join(root, ...)` that used to appear in `apply`, `walk` and the
constructor now appears once, in the adapter.

## What I chose not to build

**A verb for asking whether the copy has diverged from the ref.** `Status`
answers content and `Commit` answers position by refusing, which is enough for
every caller that exists. A `Diverged` verb would be a third way to ask a
question two verbs already answer.

**Merging.** `Reconcile` still resolves one way: the ref wins and what comes back
is what the copy gave up. The copy now remembers what it was taken from, which is
what a three-way merge needs, so this is no longer blocked by a missing fact —
only by nobody needing it. E4.3 said resolving it any other way "needs a working
copy that remembers which version it was taken from, and there is no such thing
to ask yet". There is now.

**A compare-and-set on `SetBase`.** A copy has one holder. Two writers racing on
one working copy is not a race the versioning layer can referee, and the ref is
where racing is decided.

**Wiring.** Still nothing in `cmd/nerved` builds a `Versioner`, for E4.3's
reason: there is no route that would call one until the resource surface exists.

## What I still do not understand

Whether the base belongs in the refs rather than beside the copy. A base is a
name standing for a version, which is exactly what a `RefStore` holds, and
putting it there would make a copy's position visible to `List` and reachable to
a sweep for free — no `roots` helper, no extra port verb. It would also mean
every copy's position is a ref in a flat namespace shared with the refs a person
names, and a hidden naming convention to keep them apart. I took the file
because the convention is the part that would be hard to remove later, but the
sweep needing to be taught about a second kind of root is the cost of that
choice and it showed up immediately.

## On `nrv-30c` — the second consumer of `RefStore`

The mayor's ruling on `version.ID` versus `cas.Digest` asked the next caller to
hold both vocabularies to name a second consumer of `RefStore` that is not a
version, or say that none was found.

**None was found, and the working copy is the near miss that makes the case
stronger.** It is genuinely a second consumer of the ref vocabulary: `Base` and
`SetBase` are a name standing for something, read and written exactly as a ref
is. But what it stands for is a version, so it is a second consumer of the same
concept rather than evidence the concept is generic. Every consumer of a ref
that now exists points at a version, and this ticket is the one that would have
found the exception if there were one.

**One conversion was added, and it is the unchecked kind.** `versioner.go` still
converts at the six sites the bead counted. `treecopy` adds a seventh: it writes
an ID's bytes to a file and reads them back as an `ID` with nothing checking
that what came back was ever a digest, which is the second package to construct
one that way after `localrefs`. So the copy's base can be a string that is not a
digest, and the error surfaces in `Purge` or `Status` when someone reads it —
exactly the late failure the bead was filed about, now on a second path. E4.5
has not been written yet.
