# E11.3 — One workspace, one mount, and the root that is not storage

E11.1 mounted a `vfs.FileSystem` and left the question of what to hand it open:
one mount per area, or one for the workspace. It is one. `Lifecycle.Open(scope)`
returns the whole of a workspace as a single `FileSystem` — every area the
lifecycle covers standing at its own name, and nothing beside them — and
`fusefs.Serve` takes it unchanged.

The composition is `vfs.MountTable` with `scope.View(fsys, area)` mounted at each
area, and a synthetic root under all of them. Nothing about containment is new
here: each area is the view E5.1 already proved, and this ticket only makes them
siblings. What is new is the root, and the root is where the enforcement this
ticket is named for actually lives.

## Why the areas needed a root at all, and what it refuses

`MountTable` holds no path that no mount claims, so a table of four areas answers
`fs.ErrNotExist` at `/` and a process inside it cannot list the tree it is
standing in. `areaRoot` is the ground: it answers `Stat` and `ReadDir` for `/`
with the area names, and nothing else.

It refuses every mutating verb with `fs.ErrPermission`, and that is a boundary
rather than a convenience. A name made beside the areas would be a name the
scope derives nothing for — there is no `Path` that reaches it and no area that
holds it — so a workspace whose top could grow a name would have a place in it
that no plugin owns.

| Path | Answered by | What it is |
|---|---|---|
| `/` | `areaRoot` | the list of areas |
| `/files/...` | `scope.View(fsys, "/files")` | the scope's subtree of that area |
| everything else | `areaRoot` | a name no area holds |

That last row is the enforcement. `/files/../../bob/cv/secret` is cleaned by the
table before it is dispatched, lands on `/bob/cv/secret`, matches no area, and is
answered by a filesystem that has no storage behind it. The climb never reaches
a view, and there is nothing for it to reach.

## The two vocabularies a process can try, and why only one of them is ours

The port-level cases run every spelling the layers below are held to, and a
second set this layer needs. They are different shapes and only the second is
about the mount.

**A climb is cleaned before it is dispatched.** `path.Clean` is `MountTable`'s,
and it happens once at the top of the workspace rather than per area.

**A spelling of the layout is an ordinary name.** A process that guessed the
tree it stands in would send `files/bob/cv/secret`, which has no separator to
clean and no `..` to resolve. It reaches the files view and derives
`/files/alice/cv/bob/cv/secret`, which is a path inside alice's own workspace
that happens not to exist. This is the spelling the FUSE cases use, because it
is the only one the kernel forwards.

That is the reason `..` is absent from the mounted cases. E11.2 measured that a
path spelling `..` produces zero `LOOKUP` calls: the kernel resolves it against
its own dentry tree, so a case built on one asserts Linux and not Nerve. What
arrives at a FUSE node is a single component at a time, and the layout spellings
above are exactly the components a process would send.

## What surprised me

**The read-only claim was nearly true, and the suite is what found the gap.**
`areaRoot` began with `vfs.NoAccessors` and `Caps{ReadOnly: true}`, which reads
as consistent. `vfstest` at `/` disagreed: a workspace answers `AsStreamer`
whenever *any* area does, so a root path reaching the accessor is dispatched to
the root regardless, and `NoAccessors` there had `MountTable` answer "this mount
has no streaming verbs" — `fs.ErrInvalid`. The descriptor promises
`fs.ErrPermission` from every mutating verb *including the ones reached through
an accessor*, so the claim was false by one hop. The root now answers all three
accessors and refuses through them. Declining a verb set and refusing a verb are
different sentences, and only one of them is a boundary.

**The same table-wide accessor is why the keyspace area cannot run the suite.**
`vfstest.Run` at `/kv` asks a keyspace for the streaming its neighbour has and
gets `fs.ErrInvalid` ten times. That is `MountTable`'s documented shape — an
accessor takes no path — rather than anything this composition introduced, and
the area answers the suite through its own view in `view_test.go`. It is the
cost of areas of different kinds being siblings, and it is paid in ergonomics
rather than in containment.

**Mounting the whole tree fails every case, which is the reassuring part.**
Replacing `Open` with `return l.fsys` — the plausible "the mount table is already
the containment" mistake — failed eight cases at the port and five through a real
mount, including `files/bob/cv/secret` reading bob's content first try. The
climbing spellings caught none of it. The cases that discriminate at this layer
are the ones with no `..` in them, which is the opposite of where I started.

## What I would do differently

Write the layout spellings first. I reused E5.4's climb table because it was
there and it is the right table one layer down, and every one of them passed
against an implementation with no containment at all — because the workspace
table cleans them into names no area holds before any derivation happens. A
case that cannot fail against the broken version is not yet a case, and reusing
a table from the layer below is a good way to write several.

## What I still do not understand

**Whether the areas should come from the lifecycle or from a caller.** `Open` is
on `Lifecycle` because that is the one place the area list is written down, and a
second place would be a second answer to "what is a workspace". It also means the
process handed a mount gets every area, including ones it has no business in. A
subset is a different verb and nothing needs it yet.

**What a read-destructive area is through a mount.** `/queue` is an area like any
other and `Caps` says its job path is consumed by reading, but the mount reads
`Caps` nowhere: two descriptors on one path get two different jobs. E11.1 left
this open and composing the areas did not close it.

**Where the mount point goes.** The host directory a workspace is served at is an
ordinary path, and whatever can read it is inside the workspace. That is E11.2's
item 4 and it belongs to whoever lays out the runtime — `nerved` still mounts
nothing, for E11.5's reason.

## What is deliberately not here

**No process boundary.** FUSE is a data boundary. Confining a process so that its
root *is* the mount is `pivot_root` in a mount namespace, and this ticket does not
attempt it. Every case here therefore tests what the filesystem is asked for, not
what the caller can address at the host.

**No name rewriting at a mount point.** `Stat("/files")` reports `Name: "/"`,
because `MountTable` hands the plugin its own root and the plugin answers for it.
That is a pre-existing violation of the port's "final element" rule rather than
this composition's, it is invisible through a mount because `READDIRPLUS` carries
the name, and it is filed as `nrv-v4ar`.
