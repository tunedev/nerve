# E12.10 — Health and liveness endpoints

The admin surface answers `GET /livez` and `GET /readyz`. Both read one boolean
held in memory. Neither has a handle on Postgres, the broker or Ollama, so
neither can dial one.

## What the pattern was

`Handler` takes `config.Effective` by value and `*admin.Health` by pointer, and
that split is the whole design. Config is resolved once at boot and cannot
change, so it is a copy. Health is the one thing on this surface that changes
while the process runs, so it is a pointer to an `atomic.Bool` the composition
root also holds.

The composition root owns the drain because it owns the signal handler. On
`SIGTERM` it calls `health.Drain()`, holds the listener open for `drain-delay`,
then `Shutdown`s.

## What surprised me

**Two endpoints only earn their keep because of the drain.** Written without
it, `/readyz` is `/livez` under a second name — two URLs answering `200` for
the same reason. The transition is what makes them different questions:
readiness starts refusing, liveness keeps passing.

**And the drain flip is unobservable without a delay.** The first wiring was
`Drain()` immediately followed by `Shutdown`, which closes the listener. Nothing
can probe a closed listener, so readiness went from `ready` to connection
refused and never once said `draining` on the wire — the exact outage the
endpoint exists to avoid. `drain-delay` is the fix, and it is a setting rather
than a constant because the right value is the probe period of whatever is
routing traffic, which this process cannot know. Its default of `1s` is short
enough that a local `Ctrl-C` still feels immediate; `0s` is a legitimate value
and validates, unlike `call-timeout`, where zero would ask for the unbounded
call the setting exists to prevent.

**Liveness must survive the drain.** Failing `/livez` while shutting down gets
the process killed for doing what it was told, and turns a clean drain into a
`SIGKILL` halfway through the requests still in flight.

**`/livez` and `/readyz`, not `/healthz`.** One endpoint called "health" has to
answer both questions at once, and whichever meaning the operator picks, the
other is wrong. Splitting the names is what makes "restart me" and "stop
routing to me" separable decisions.

## What I would do differently

Nothing here. The next question is whether readiness stays a boolean. It is a
boolean because there is nothing yet that can be unready except a drain — no
pool to fill, no migration to run. The first dependency that has a warm-up will
want `Ready()` as well as `Drain()`, and that is a method, not a redesign.

## What I still do not understand

Whether readiness should ever consult a mount. The rule "a probe touches no
dependency" is right for liveness and mostly right for readiness, but a process
whose every mount is unreachable is arguably not ready for work even though it
is alive. The honest version of that is a cached verdict a background check
writes and the probe only reads — never a dial inside the handler — and it is
not worth building before there is a mount kind that can fail.

Whether `drain-delay` belongs to this process at all. It is really a property
of the thing routing traffic, and duplicating it here means two places to keep
in step: a Deployment's `periodSeconds` and this setting. E12.8's `make` targets
have no balancer in front of them, so there is nothing yet to disagree with.

## Evidence

```
$ ./bin/nerved --admin-addr 127.0.0.1:7912 --drain-delay 3s \
    --postgres-dsn 'postgres://nerve:hunter2@203.0.113.1:5432/nerve'
nerved dev (go1.27.0)
admin http://127.0.0.1:7912/config
admin http://127.0.0.1:7912/livez
admin http://127.0.0.1:7912/readyz

before TERM: readyz 200 livez 200
draining +1: readyz 503 livez 200   {"status":"draining"}
draining +2: readyz 503 livez 200   {"status":"draining"}
draining +3: readyz 503 livez 200   {"status":"draining"}
exit 0
after: refused
```

Postgres is at `203.0.113.1`, in TEST-NET-3, which routes nowhere. Both probes
answered in about 0.3ms throughout. A probe that dialled it would have spent its
dial timeout instead, which is what `TestProbesAnswerWithoutTouchingADependency`
asserts.
