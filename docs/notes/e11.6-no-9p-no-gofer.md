# E11.6 — Refuse 9P and the gVisor gofer wrapper

Nerve serves a workspace to a process one way: `internal/adapters/inbound/fusefs`,
over `github.com/hanwen/go-fuse/v2`. It will not grow a 9P server beside it, and it
will not become a gVisor gofer.

There was nothing to remove. `grep -rniE '9p|gvisor|gofer|runsc'` over the tree
finds the words only in prose — the roadmap row, the plan export, and the E11.2 and
`nrv-sd43` notes that already cite this refusal — plus base64 noise in `go.sum`
hashes. No module in `go.mod` speaks either protocol.

## What was refused

Two ways of serving the scoped VFS to a sandbox that are not a kernel mount:

- **A 9P server.** A second inbound adapter answering 9P2000.L over a socket, so a
  client that speaks 9P reads the tree without `/dev/fuse` on its side.
- **A gVisor gofer.** Nerve as the process `runsc`'s sentry asks for file
  operations, so a gVisor sandbox reads the workspace straight from Nerve instead
  of from a host path. The gofer no longer speaks 9P: gVisor replaced it with
  lisafs, enabled by default in `runsc`. A wrapper would implement a protocol owned
  by another runtime's internals.

Both are how a fleet serves filesystems to sandboxes on nodes it schedules but does
not own. The Forge has one node and one operator, which is the "managed cloud
fleet" force the Forge refusals table names as one it does not have.

## What it would cost here

**A second inbound adapter with no caller.** `fusefs.Serve` has no production
caller today — `grep -rl fusefs` finds only the package itself, and `cmd/nerved`
does not mention it. A 9P or lisafs adapter would be a second unwired surface over
the same `vfs.FileSystem`, which is the "interface per platform" row of the Forge
table: add a surface when someone will use it.

**The escape surface, measured again from zero.** E11.2's ten items were measured
against the kernel's FUSE path, and `fusefs/escape_test.go` asserts them there. The
central finding — `..` never reaches the filesystem because the kernel resolves it —
is a property of FUSE. A 9P server receives walk requests with names in them, so
traversal becomes Nerve's to refuse again, and the suite has to be rebuilt per
protocol.

**A listener where there is none.** FUSE's entry check is the kernel's uid check.
A 9P server is a socket, so authentication at every hop (Tenet 5) becomes Nerve's
code rather than the kernel's.

## What stays

- `fusefs` as the only data surface, with containment in `workspace.Scope.View`.
- `nrv-sd43`'s contract: a container closes the process boundary, and the runner
  binds the mount in. A kernel-boundary runtime such as `runsc` replaces the runtime
  under that same contract; its own gofer serves whatever host path is bound,
  including the FUSE mount. That swap needs no Nerve code — reasoned, not measured,
  like the rest of `nrv-sd43`.

## The evidence that would reopen it

Not more users or more workspaces. These would:

- The runner that must be used cannot see a FUSE mount at all. `nrv-sd43` names the
  hosted free tier as possibly granting no `/dev/fuse`; if that is confirmed and the
  runtime there speaks 9P, a 9P server needs no kernel privilege on the serving side.
- A measurement, on a real workload, that the double hop under `runsc` — sentry to
  its gofer to the host kernel to `fusefs` — dominates latency.
- A client that must read a workspace from a machine with no FUSE and a 9P client.

## What enforces it

Nothing. `.golangci.yml`'s `depguard` rules are scoped to `internal/core` and deny
none of these modules. A repo-wide deny on `gvisor.dev/gvisor` and the known 9P
libraries would catch the obvious route and not a hand-rolled server, which needs no
import. The refusal holds only where it is stated: here, the roadmap row, and the
two notes that cite it.

## What surprised me

The refusal was already cited twice before this ticket ran, in E11.2 and `nrv-sd43`,
both to say what it does not cover: it refuses a transport, not a runtime. Choosing
`runsc` later is untouched by it.

And the "9P" half of "the gVisor gofer" is out of date: the gofer moved to lisafs.
The roadmap row names two things that have since become separate.

## What I would do differently

Record the refusal before E11.2. The FUSE choice assumed this answer, and a decision
ticket landing after the code it governs can only ratify.

## What I still do not understand

Whether the hosted prod stack can mount FUSE at all. That is the one input that
would turn this from a refusal into a live question, and nobody has measured it.
