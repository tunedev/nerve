# E6.2 — Async pipeline consuming the queue

Finalising a resource writes one small file and returns. The tree that write
went through publishes the path that changed; a worker claims that job later
and hands it to `ingest.Pipeline`, which loads the resource and runs the stages
over it. Nothing the caller waited for did any of it.

The acceptance is asserted at both ends of the same run:

```
$ go test ./internal/core/ingest/    # with the pipeline running on any path inside a resource
--- FAIL: TestIngestionRunsOncePerResourceAndNotOncePerWrite (0.00s)
    pipeline_test.go:187: stages ran = [extract extract extract], want [extract]

$ go test ./internal/core/ingest/    # with the completeness gate removed
--- FAIL: TestPipelineLeavesAResourceThatHasNotBeenFinalised (0.00s)
    pipeline_test.go:203: stages ran = [extract], want none for a resource still arriving
```

## What the pattern was

There was no new mechanism to build. `vfs.WithWriteObserver` and
`queuefs.Emitter` were delivered in E3 and wired to nothing: a write to an
observed tree becomes a job under a queue mount, and `queuefs.Worker` takes it
off the tree by reading the path it was told the key of. E6.2 is the handler on
the far end and the two path functions that let it recognise its own work.

`workspace.Locate` is `Scope.Path` read backwards, and it is in `workspace` for
the reason `Path` is: a caller that took a scope out of a path its own way would
be the second place spelling the layout. `Store.Resolve` is `Store.dir` read
backwards, on top of it.

The pipeline itself is four branches, three of which do nothing: a path that
declares no resource belongs to somebody else on the same bus, a resource that
is gone was deleted between the write and the claim, and a resource that has not
been finalised is one whose content is still arriving. None of them is an error,
because a notification outliving what it is about is the ordinary case — the
same bargain `Worker.take` already makes with a key that has nothing under it.

## What surprised me

**One upload queues three jobs, and the gate that makes exactly one of them
ingestion belongs to the store rather than the pipeline.** `Create` makes the
directory, `Upload` closes a stream, `Complete` writes the meta file, and every
one of those is published. `Resolve` answers only for a resource's meta file:
content changing is not a resource arriving, and only what a resource says about
itself can say the finalising call has happened. Widening it to any path inside
a resource runs the stages three times, which is the first failure above. The
gate is also what makes an early claim free — a worker that takes the meta job
between `Create` and `Complete` finds an unfinalised resource and does nothing,
and completion queues that key again.

**A jobs mount that cannot hold a key loses the work and says nothing.** The
first test wired the emitter to a `memfs`, which refused
`/queue/jobs/resources/ada/hunt/transcript.txt/meta.json` because its parents do
not exist. `observed.report` drops what the observer says by design — a write
that happened must not be failed by a notification that did not — so the jobs
simply were not there, with no error anywhere. A queue mount is a flat key
space, the test now uses one, and whoever wires this into a running process has
a way to configure it silently wrong.

## What I would do differently

The first draft gave `Pipeline` the resources root and had it take paths apart
itself. That is two places that know where a resource stands, and they would
have disagreed the day one of them changed. Moving the inverse into
`workspace.Locate` and `Store.Resolve` left the pipeline holding no path
knowledge at all — it is handed a changed path and asks the store what, if
anything, it declares.

## What I still do not understand

**Nothing runs this yet, and the missing pieces are one decision.** A running
pipeline needs a resources root and a signing key (nrv-amti), a mount actually
wrapped in an observer (nrv-d4b), and a queue mount with a listener and a worker
goroutine the composition root owns. The tests drive the real emitter, the real
worker and the real store, so what is unproven is the wiring rather than the
loop.

**What a failed stage should leave behind.** The run stops and names the stage,
and nothing records that it stopped. E6.6 is where a caller learns a document
did not become searchable; until then a failure is visible only in the worker's
error, and the worker's own rule is that a handler failure ends the run.

**Whether stages stay a flat ordered list.** E6.3 makes a format a package, and
a per-format processor is not obviously one of these — it may be a stage that
dispatches, or the list may become per-content-type. The seam is deliberately
the smaller of the two guesses.
