# E11.2 — The FUSE library, and where the sandbox boundary is not

`github.com/hanwen/go-fuse/v2`, at `v2.11.0`. The mount is an **inbound**
adapter: the kernel is the caller, `internal/adapters/inbound/fusefs` is where
it lands, and the node it serves wraps a `vfs.FileSystem` — in practice the one
`workspace.Scope.View` hands back, so containment stays where E5.1 put it.

The second half of the ticket is the half that matters. FUSE is a **data**
boundary, not a **process** boundary. E11.4 names three attempts — path
traversal, symlink escape, handle reuse — and only the middle one is the
filesystem's to refuse.

## The candidates, measured 2026-09-01

| Library | Import path | cgo | Latest tag | Last push |
|---|---|---|---|---|
| hanwen/go-fuse | `github.com/hanwen/go-fuse/v2` | no | `v2.11.0`, 2026-07-20 | 2026-08-03 |
| jacobsa/fuse | `github.com/jacobsa/fuse` | no | never tagged | 2026-07-03 |
| bazil.org/fuse | `bazil.org/fuse` | no | never tagged | 2023-12-20 |
| winfsp/cgofuse | `github.com/winfsp/cgofuse` | yes | `v1.6.0` | 2026-05-31 |

Four things decided it, in this order.

**cgo removes one candidate outright.** E12.12 wants the same source to produce
the same binary on a clean checkout, and the Forge is Go end to end. `cgofuse`
puts a C toolchain and libfuse headers between the checkout and the binary. It
is the only cross-platform option and the only one that reaches Windows, and it
is still out.

**A tag is what a pin pins to.** `jacobsa/fuse` has never cut one, so depending
on it means a pseudo-version off an untagged branch — which is a pin to a commit
somebody may rebase, not to a release. gcsfuse, its largest consumer, does
exactly that: `github.com/jacobsa/fuse v0.0.0-20260630194014-a124548f6da7`.
`hanwen/go-fuse` cuts semver tags and cut one six weeks before this was
written.

**Staleness removes another.** `bazil.org/fuse` has not been pushed since
2023-12-20, measured 2026-09-01. Its API is the ancestor of `jacobsa/fuse`'s.

**Footprint decided the rest.** Building `fs` and `fuse` adds exactly one module
to Nerve's build graph, and it is `golang.org/x/sys`, which `go.mod` already
carries indirect at `v0.47.0`. `godebug` and `moby/sys/mountinfo` are in
go-fuse's `go.mod` but not in the import graph of the two packages Nerve needs.

What that buys, against what it costs: go-fuse tracks the FUSE wire protocol far
ahead of the alternatives and its `fs` package is inode-based, so a node can be
built over any tree rather than over a host directory. It is also the least
documented of the three, and its maintainer states plainly that they own no Mac
and take macOS patches rather than testing them. On Linux — which is where
`kind`, Docker and every Forge dependency already run — that is not a cost.

## The escape surface

Written as the ticket asks: what a process inside the mount can reach that is
not inside it, and who can close each one. Every item below was produced against
`v2.11.0` on Linux 6.8 on 2026-09-01; the transcripts are under Evidence.

**1. A symlink target the filesystem serves. This is the only escape Nerve
emits.** The kernel resolves the bytes `Readlink` returns, in host vocabulary
and not in the mount's: an absolute target lands at the host root, and a
relative target that climbs enough lands above the mount. Both read a file
outside the mount, first try. `workspace.View.from` already refuses to hand back
a target standing outside the scope, and `nrv-9bj` recorded why `localfs` writes
its links relative. The FUSE node must go through the view for `Readlink` and
never around it — this is the one place where an adapter bug is a containment
bug.

**2. `..` is not on this surface, and E11.4's path-traversal case as usually
written tests the kernel.** The VFS resolves `..` against its own dentry tree
before any request is generated. A filesystem receives single-component
`LOOKUP`s and never sees a separator: reading `mnt/sub/../../secret` from
outside the mount produced **zero** `LOOKUP` calls and read the host file.
Traversal becomes Nerve's problem only when the sandboxed process's own root is
the mount, which is `pivot_root` or a mount namespace — not something a
filesystem can do for it.

**3. Who may enter is a mount option, and the default is right.** The kernel
records `user_id=1000,group_id=1000` and applies `nosuid,nodev` to a user FUSE
mount, so only the mounting uid gets in. `AllowOther` widens that to every user
on the host and additionally needs `user_allow_other` in `/etc/fuse.conf`,
which is commented out on the Ubuntu host this was measured on. Nerve should
never set it. Root is inside regardless.

**4. The mount point is an ordinary host path.** Whatever can read that path is
inside the workspace. Where `nerved` puts it, and with what mode, is a boundary
decision that belongs to whoever lays out the runtime — the same place
`nrv-9bj` left the bind-mount question.

**5. An open handle outlives the path it was opened through.** After the
filesystem removed an entry and notified the kernel, `stat` returned `ENOENT`
while the already-open descriptor kept reading the content. This is E11.4's
handle-reuse case and it is a property of every Unix filesystem rather than a
FUSE defect. Revocation in Nerve is therefore a statement about what a *new*
open can reach; a descriptor already handed out is closed by closing it.

**6. An open handle also blocks the unmount.** `Server.Unmount()` returned
`Device or resource busy` with one descriptor open, the process then exited, and
the mount stayed in `/proc/self/mountinfo`. That is E11.5's orphaned mount,
produced without trying to produce it.

**7. A dead server leaves a mount, not a hang.** With the server SIGKILLed, the
mount entry remained and reads through it failed immediately with
`transport endpoint is not connected`; `fusermount3 -u` reclaimed it. The hang
case is the other one — go-fuse documents that a caller holding a file in a
wedged filesystem blocks until `/sys/fs/fuse/connections/$ID/abort` is written.
Cleanup on crash is an external step. No in-process `defer` can promise it.

**8. The kernel holds a second copy of every answer, and the documented default
is not the one Nerve will get.** `fs.NewNodeFS` sets a one-second entry and
attribute timeout *only when it is passed a nil `Options`*. Pass an `Options` —
which every real caller does, if only to name the mount — and both timeouts are
nil, `setEntryOutTimeout` sets neither, and the kernel caches nothing: five
`stat` calls on one path produced five `LOOKUP`s. That is the safe direction and
the slow one. It also means item 5's prompt `ENOENT` was free rather than earned,
and that the revocation window this item warns about opens the day somebody sets
a timeout for speed.

**9. Verbs the port has no vocabulary for.** The kernel may ask for extended
attributes, file locks and hard links; `vfs.FileSystem` has none of them.
`DisableXAttrs` makes the answer `ENOSYS` so the kernel stops asking, and locks
stay off unless `EnableLocks` is set. `Link` is the one to refuse on purpose: it
would give one inode two paths, which is a second spelling of a location, and a
second spelling is what `workspace.Scope.Path` exists to prevent.

**10. Mounting is a privilege, and containers do not grant it by default.** The
default path shells out to the setuid `fusermount3` helper; `DirectMount` calls
`mount(2)` instead and needs `CAP_SYS_ADMIN`. A `kind` node needs `/dev/fuse`
exposed and a device rule either way. This is the first thing that will fail on
a clean machine, and it fails at mount rather than at build.

## What surprised me

**The escape I expected to be the hard one is not mine to refuse, and the one I
expected to be easy is the only one I emit.** I went in assuming path traversal
was the centre of E11.3 and symlinks were a corner. It is the reverse: `..`
never reaches the filesystem, and the symlink target does, because it is the one
value the filesystem *authors* rather than resolves. `nrv-9bj` found the same
asymmetry a layer down — lexical cleaning was never the hole; the kernel
resolving a link was — and it turns out to be the same shape here for the same
reason. The layer that resolves a name is the layer that can be fooled by one.

**A test written from outside the mount does not test the mount.** All my first
probes ran as the host user with the host root, spelling paths at a mount point.
Under that setup the interesting refusals come from the kernel and the
filesystem is never asked, so a test suite built that way would pass green
against a filesystem with no containment in it at all. E11.4 has to run the
attempts from a process whose root *is* the mount, or it is testing Linux.

**Unmount fails busy, and nothing retries it.** I did not go looking for this:
the first probe left a real orphaned FUSE mount on my machine because
`Unmount()` returned an error the program printed and then ignored. That is
E11.5's entire failure mode reproduced by accident, and the lesson is that
unmount is a fallible operation with a live blocker, not a teardown line.

**The documentation's default is not the caller's default.** "Default timeouts
are 1 second for both attribute and entry caches" is true of `fs.NewNodeFS` and
false of every program that configures anything, because the sentence is about
the nil-`Options` branch and the branch is invisible from the prose. I had
already written item 8 from the documentation before the probe contradicted it.
A number read out of a doc comment is a claim about one code path, and which
path is the reader's to establish.

**Zero is the interesting measurement.** The `..` finding is a count of calls
that did not happen. It only reads as evidence because the same probe shows
non-zero counts for the paths that do reach the filesystem in the same run — a
`LOOKUP` log that was empty throughout would prove the log was broken.

## What I would do differently

Reach for the mount earlier. This is a decision ticket and the ticket's own
acceptance is prose, so it could have been answered by reading; seven of the ten
items above came from three short programs that mount a filesystem and ask it
questions, and item 6 came from a bug in one of them rather than from a
question I thought to ask. A decision about a boundary should be made with the
boundary running.

## What I still do not understand

**Whether the FUSE node should serve `vfs.FileSystem` or `files.Tree`.** The
port is the smaller surface and the view is already the containment. `files.Tree`
has `Walk`, `Glob`, `Grep` and `Find`, none of which the kernel can ask for, and
lacks streaming, which it certainly will. I think the answer is the port plus
`AsStreamer`, but E11.1 is the ticket that finds out.

**What the process boundary is, given that this is not it.** E11.6 refuses 9P
and the gVisor gofer as fleet-scale machinery, and it is right about that, but a
mount namespace with `pivot_root` is not fleet-scale and is what items 2 and 4
are asking for. Whether E11 owns that or whether it belongs to whatever runs
user code is not settled anywhere I can find.

**Whether a workspace gets one mount or one per area.** Nerve has files, a key
space, a queue and a stream, all reached through the same `Scope`. A single
mount presenting them as sibling directories is one answer; four mounts is
another, and it changes item 6 from one busy unmount into four.

5. what the mount looks like to the host
   / /tmp/nerve-probe-599177400/mnt rw,nosuid,nodev,relatime shared:1076

   / /tmp/nerve-probe2-1762101105/mnt rw,nosuid,nodev,relatime

The mount left behind by the failed `Unmount()` in the previous transcript was
still listed when this one ran, and needed the same `fusermount3 -u` by hand.

Item 8, the timeout default and what a caller actually gets:

```
fs.Mount(..., nil)                             5 stats -> 1 LOOKUP
fs.Mount(..., &fs.Options{})                   5 stats -> 5 LOOKUP
fs.Mount(..., &fs.Options{EntryTimeout: 10s})  5 stats -> 1 LOOKUP
```

The middle line is the one Nerve is on. Counting every `LOOKUP` rather than
only the ones for the path under test gave 3, 7 and 3, because the desktop trash
daemon walks each new mount — the same visitor as in the first transcript, and a
reminder that a count taken at a mount point includes callers you did not write.

## The evidence that would reopen the choice

- Nerve has to mount on macOS or Windows, where the maintainer tests neither and
  `cgofuse` is the only answer for the second.
- `hanwen/go-fuse` stops cutting tags, which removes the reason it beat
  `jacobsa/fuse`.
- The kernel's FUSE passthrough or `io_uring` paths become the thing worth
  having, and one library gets there first. That is a performance argument and
  Nerve has no measurement yet, so it is not one today.

## What this ticket does not change

No dependency is added. `go mod tidy` removes a module nothing imports, so
`github.com/hanwen/go-fuse/v2` enters `go.mod` with E11.1's first node and not
before. The probes above live outside the repository for the same reason.
