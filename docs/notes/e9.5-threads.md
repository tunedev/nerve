# E9.5 — Threads

`thread.Log` is a workspace's record of what its agent runs produced: `Start`,
`Append`, `Finish`, `Fail`, `Get`, `Read`, `List`, `Delete` on the one FileSystem
the mount table presents. A thread is one run — a directory holding a `RUN`
record and one file per appended output.

The ticket's acceptance is one sentence, and it is one test:

```
$ go test ./internal/core/thread/ -run 'Connection' -v -count=1 | grep '^ *--- '
--- PASS: TestOutputSurvivesTheRequestingConnection (0.00s)
    --- PASS: TestOutputSurvivesTheRequestingConnection/tree (0.00s)
    --- PASS: TestOutputSurvivesTheRequestingConnection/keyspace (0.00s)
--- PASS: TestARunEndsAfterTheConnectionHasGone (0.00s)
    --- PASS: TestARunEndsAfterTheConnectionHasGone/tree (0.00s)
    --- PASS: TestARunEndsAfterTheConnectionHasGone/keyspace (0.00s)
```

The context that asked for the run is cancelled mid-run, and a caller holding a
context of its own reads back everything the run produced and is told whether
there is more coming.

## What the pattern was

`library.Registry` and `kv.Space` again: hold the tree and a root, take a
`workspace.Scope` per call, derive every path through `Scope.Path`, know no
plugin, refuse user scope. A reader who has read either has read this. Every
verb is asked over `memfs` and over `kvfs`, because a thread is a directory on
one and a prefix on the other.

`Read` answers with the run and the entries in one value and never with the
entries alone. That is the acceptance made structural rather than documented: a
caller that was not there when the output was made has no other way to tell
output that stopped from output that is still coming, and the wrong guess is a
truncated result reported as a whole one.

## What surprised me

**`AppendOnly` is not the same property as durable, and reaching for it would
have lost the result.** A thread is an append-only log, so the obvious shape is
one path per thread with `Write` adding to it, gated on `Capabilities(path).AppendOnly`.
Only `streamfs` and `streamrotatefs` claim that descriptor, and `streamfs` is a
ring buffer that drops its oldest bytes. Requiring the descriptor would have
excluded every tree mount — which is where durability actually lives — while
admitting the one mount that throws the result away. One file per entry needs no
capability branch, never reads a written entry back to rewrite it, and a run
interrupted between two appends has lost the entry it was making and nothing
else.

**Two mechanisms for ordering meant one was dead, and the test could not tell.**
Entry names were padded to ten digits so the listing order would be the append
order, and `readDir` also sorted the decoded sequences numerically. Replacing
the padded name with `%d` left the suite green, which is the suite saying the
padding was decorative. The numeric sort is the one the code rests on, so the
padding went; the ordering test now discriminates against dropping the sort, and
what it catches is not a jumbled read but a lost write — `Append` takes the next
sequence from the last element, so an unsorted listing puts the thirteenth entry
over the tenth:

```
$ go test ./internal/core/thread/ -run TestAppendsComeBackInOrder   # sort removed
    --- FAIL: TestAppendsComeBackInOrder/tree (0.00s)
        log_test.go:165: read 10 entries, want 12
```

**`library.List` filters on `IsDir` for a reason I had to break the build to
see.** I left the filter out, reasoning that a child holding no record already
reports `fs.ErrNotExist` and that one mechanism beats two. A plain file standing
where a thread would be disagrees across the two mounts — `fs.ErrNotExist` on a
keyspace, where a name is a prefix and there is always something under it, and
`fs.ErrInvalid` on a tree, where a file has nothing under it — so the single
mechanism failed the whole call on a tree and passed on a keyspace:

```
$ go test ./internal/core/thread/ -run TestListPassesOverWhatIsNotAThread   # IsDir filter removed
    --- FAIL: TestListPassesOverWhatIsNotAThread/tree (0.00s)
        log_test.go:366: List: list thread "loose.md": read "/ada/hunt/loose.md/RUN":
            "loose.md" is not a directory: invalid argument
```

Both filters are needed and neither subsumes the other. Being the only caller
doing something a particular way was the signal, not the cleaner approach.

## What I would do differently

Write the stray-plain-file case at the same time as the stray-directory case.
The directory case passed under both shapes and made the missing filter look
like a simplification for as long as it was the only case there.

## What I chose not to build

**A follow verb.** `Read` answers with what is there now; a caller wanting the
output as it arrives polls, or reaches the `Streamer` accessor of a mount that
has one. Live tailing is `streamfs`'s subject and a thread is the durable record
beside it, not a second one.

**A lease or heartbeat.** A run that dies without saying so leaves `Running`
standing forever, and the log cannot tell that from a run still working. Nothing
here expires it. That wants a clock and a lease, and both want the ticket that
has a use for them.

**Reading a thread from a sequence onward.** `Entry.Seq` is there so a caller can
say how much it has already seen, and no verb takes it yet. The argument for
adding one arrives with the caller that reconnects to a long run, which is the
inbound surface's ticket.

## What I still do not understand

**Whether `Append` should cost three round trips.** It lists the thread, reads
the record and writes the entry — the listing to find the next sequence, the
record to refuse a run that has ended. The alternative is a handle caching the
next sequence, and it was rejected because a handle dies with the connection this
ticket exists to outlive. Over a remote mount that is n listings across a run,
and whether it matters depends on how chunky a run's output actually is, which
nothing here yet produces.

**Nothing consumes the log.** It is wired nowhere, alongside `library.Registry`,
`kv.Space` and `workspace.Lifecycle`: the composition root names no thread root,
so no config key for one exists. Who names a thread — the caller, or the surface
that accepted the run — is the inbound ticket's to settle, and `Start` refusing a
taken name is the constraint it inherits.

**The flat-segment rule is now written five times.** `workspace.validSegment`,
`version.ValidateRefName`, `library.validName`, `kv.validSegment` and now this
one. `nrv-e6y` is still open. Writing the fifth copy rather than the extraction
was a scope call, not a judgement that five is fine.
