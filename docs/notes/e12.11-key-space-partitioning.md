# E12.11 — Key-space partitioning for contended structures

Partitioning is **refused**. The mount table's read path takes no lock at all,
so there is no contention left for a key space to divide.

`MountTable` now replaces its mount list wholesale on every `Mount` and hands
readers an `atomic.Pointer` load. Mounts may arrive while the tree is being
read; a reader sees the tree before the mount or the tree after it, waits for
nothing, and shares no writable memory with any other reader.

`internal/core/vfs/mount_contention_test.go` is the measurement, and it is what
this refusal has to be re-argued against.

## What the pattern was

The table is the one structure every verb touches: ten verbs, three accessors
and `Capabilities` all begin with `resolve`. It was also the only structure in
the repo with a concurrency question at all — nothing here synchronised
anything, and the table was plainly racy under a concurrent `Mount`.

Three ways to fix that race, benchmarked against each other with `RunParallel`,
where ns/op is aggregate throughput: more cores should mean a lower number, and
32 cores should ideally mean a thirty-second of it.

| Strategy | 1 | 4 | 16 | 32 | 1 → 32 |
|---|---|---|---|---|---|
| One `RWMutex` over the slice | 60.7n ±5% | 44.7n ±6% | 62.0n ±2% | 69.3n ±2% | **0.9×** |
| Sharded by first path segment, 16 shards | 49.4n ±6% | 30.0n ±11% | 25.7n ±33% | 22.4n ±21% | **2.2×** |
| Copy-on-write `atomic.Pointer` | 54.4n ±3% | 16.1n ±2% | 6.60n ±3% | 5.18n ±1% | **10.5×** |
| The shipped table | 56.8n ±3% | 16.7n ±1% | 6.94n ±1% | 5.66n ±1% | **10.0×** |

Go 1.27.0, 32-core i9-13900HX, `-benchtime 1s -count 6`, summarised with
`benchstat`. All four resolve the same paths through the same longest-prefix
search; only the synchronisation differs.

The single lock does not merely fail to scale, it inverts: thirty-two readers
of a structure nobody is writing to are slower than one, because `RWMutex.RLock`
is a *write* to a shared counter and that cache line bounces between every core
that touches it.

## What surprised me

**Key-space partitioning works, and it is still not worth it.** 2.2× against
copy-on-write's 10.5×, plateauing around 22n while copy-on-write keeps falling
to 5n. Sharding a structure only reduces contention to the extent that *access*
is partitioned too, so that a core keeps returning to one shard. Readers of a
filesystem are not partitioned: any goroutine may ask for any path, so every
core still touches every shard's lock, and the same cache line still bounces —
across sixteen lines now instead of one.

**And the longest-prefix rule taxes the partitioning before it starts.** A
mount at `/` holds every path, so it belongs in every shard: the partitioning
duplicates rather than divides. The shard count then becomes a number to tune
against a mount count nobody knows yet — which is the tuning copy-on-write does
not have, on top of the 5× it wins by.

**The lock was not the last bottleneck — a line of path handling was.** With
the lock gone, the table still allocated 3 times and 64 B **per successful
resolve**. `resolve` opened with

```go
name = path.Clean("/" + name)
```

and every path a caller hands a filesystem already starts with a slash. So the
concatenation built `"//queue/jobs"`, and `path.Clean` — which returns the
string it was given when there is nothing to fix — had to allocate a buffer and
a string to take the doubled slash back out. Three allocations per verb to undo
work the same line had just created. Testing the first byte instead removed all
three.

**I had that diagnosis wrong first.** `go build -gcflags=-m` reported

```
"/" + name escapes to heap
name escapes to heap
```

which is a complete and plausible story: the `fmt.Errorf` in the not-found
branch makes `name` escape, escape analysis carries that back to the
concatenation, so the concatenation is heap-allocated even on the happy path.
Every clause of it is true, and it is not where the cost was. Three probe
benchmarks settled it:

| | allocs | B/op |
|---|---|---|
| concatenate, result escapes | 3 | 64 |
| concatenate, nothing escapes | 2 | 40 |
| no concatenation, escape kept | 0 | 0 |

The escape accounts for one allocation. The doubled slash accounts for the
other two and for the existence of the first. `path.Clean("//a/b/c")` allocates
twice; `path.Clean("/a/b/c")` allocates nothing.

## What I would do differently

Reach for the measurement before the taxonomy. "Key-space partitioning for
contended structures" names a solution, and I began by asking where to apply
it. The benchmark answered the better question — what does this structure cost
under load — and the answer was a category the ticket never mentions.

Check that a comparison is a comparison. For most of this increment the shared
search the three alternatives ran was quietly missing the lexical resolution
step that the shipped table does, so three of the four rows were being credited
for work they never did. Nothing failed; the table just read wrong, and it read
wrong in the direction that flattered my conclusion. What exposed it was an
unexplained 2× between two rows that should have matched — the leftover I had
written down as not understood, rather than chased.

## What I still do not understand

`Mount` copies the whole list per mount, which is quadratic in mount count.
That is right while mounts are tens and arrive at boot, and wrong at some count
I cannot name, because nothing yet mounts at runtime. E2.7's utility plugins
will be the first evidence of what the real count is.

Whether the refusal survives a plugin that is itself sharded. This measured the
table, not what the table dispatches to. `kvfs` (E2.5) holding one map behind
one lock would be a genuinely contended structure, and its access *is*
partitioned by key in a way a mount table's is not. The refusal here is about
this structure, not about the technique.
