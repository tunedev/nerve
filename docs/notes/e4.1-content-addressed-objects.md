# E4.1 — the content-addressed object store

`cas.Store` writes content under the digest of its own bytes, so the same content
from two callers is one object. It is not a plugin. It is a shape over the
`FileSystem` port, and the mount it is handed decides whether the objects are in
memory, on disk or in a bucket.

```
$ go test -count=1 ./internal/core/cas/ -v | grep -c '^--- PASS'
16

$ go test -race -count=1 ./internal/core/cas/
ok      github.com/tunedev/nerve/internal/core/cas      1.019s

$ make lint
0 issues.
```

The acceptance in one assertion, with the dedup check removed to show the test
discriminates:

```
$ go test ./internal/core/cas/ -run TestIdenticalContentIsStoredOnce
--- FAIL: TestIdenticalContentIsStoredOnce (0.00s)
    cas_test.go:82: two puts of identical content made 2 writes, want 1
```

## What the pattern was

**No port, because there is no second implementation to name.** E4.2 gets a
`RefStore` port and this ticket does not, and the difference is the calibration
rule rather than inconsistency. Swapping where objects live is swapping the mount:
`cas.New(memfs.New(), root)` and `cas.New(disk, root)` are the same code doing the
same thing, proved by one test that runs the round trip over both. A port here
would be a second interface over the one the mount table already provides, with
two sets of semantics to keep agreeing and nothing on the other side of it.

That is also why the package sits in `internal/core` rather than in an adapter. It
imports `internal/core/vfs` and nothing else; there is no driver in it to keep out.

`Digest` is also what a ref holds: nrv-30c made `version.ID` this type rather than
a second name for the same idea.

**Content addressing does the concurrency work.** Nothing in `Store` is locked.
Eight writers of one content all find it missing, all write, and all write the same
bytes to the same path — so the outcome is one object with the right content, which
is what `TestConcurrentPutsOfIdenticalContentStoreOneObject` asserts under `-race`.
A name derived from content cannot be raced onto the wrong content. A name chosen
by a caller can, and that is E4.2's problem, not this one's.

**`Get` hashes what it read.** The mount underneath is an ordinary tree that
anything else with the mount can write to, so "the bytes you get back answer to the
digest you asked for" is a promise the store has to keep itself. It costs one hash
per read and it turns a silently different version into `fs.ErrInvalid`.

## What surprised me

**The zero `Digest` is reachable and it had a panic in it.** `cas.Digest{}` is a
legal struct literal — it is what a caller holds after ignoring an error from
`ParseDigest` — and the layout derivation was `hex[:2]`, which panics on it. The
fix was not a check in each verb but making the one function that knows the layout
total: `path` returns an error, every verb propagates it, and the zero digest gets
`fs.ErrInvalid` from `Get`, `Has` and `Remove` alike. The fields are unexported for
the same reason, so `Compute` and `ParseDigest` are the only ways to get a digest
that names anything.

**`Mkdir` before `Write` is the portable order, not a tree-only concession.** The
port says `Write` replaces the content of a path and says nothing about making its
parents, and `memfs` and `localfs` both refuse a write into a directory that is not
there. Over a mount reporting the object-store descriptor `Mkdir` has nothing to
make and returns nil, so one order works everywhere and the fanout costs a bucket
nothing.

**The test imports two adapters, and that is the first time a core package's test
has.** `depguard` denies drivers and transport under `internal/core/**`, not the
reference tree, and `go list -deps` over the non-test core packages stays clean. It
was still a deliberate choice: a hand-written map standing in for a tree would have
been a fake asserting a fake, and the property under test — identical content
stored once — is only visible in a tree that really stores things. The write
counter wraps `memfs` rather than replacing it, so what the store did is counted
while what it stored is still really stored.

## What I chose not to build

**Enumeration.** E4.3's purge has to find objects nothing refers to, which needs a
walk this store does not have. Adding one now would be guessing at whether
reachability is computed from refs or marked on the objects, and the answer belongs
to the ticket that has to sweep. `Remove` is here because a store without it is not
one, and because it maps to a single verb.

**Streaming.** `Put` takes a `[]byte` and `Get` returns one, so an object is
whole in memory twice — once to hash, once to write. Every mount that matters here
answers `AsStreamer`, and a digest can be computed as content passes through, so
this is a real change rather than an impossible one. It is not this ticket: the
versioner's first objects are manifests and small files, and a streaming `Put`
cannot answer "is it already stored" until it has read the whole thing anyway,
which changes what the dedup check can be.

**Wiring.** Nothing in `cmd/nerved` builds a `Store`. It has no caller until E4.3,
and a mount for it with nothing reading it would be a route that answers nothing.

**A second algorithm.** `Compute` is SHA-256 and the algorithm is in every digest's
spelling, so adding one later is a constant and a wider `Compute` rather than a
migration. `ParseDigest` already accepts a spelling it cannot compute, because a
digest recorded before this build started is not this build's to reject — it just
names nothing stored.

## What I still do not understand

Whether `Get` should verify over a mount that already does. A bucket checksums an
object on the way out and `localfs` does not, so the hash here is redundant on one
mount and load-bearing on the other, and the store cannot tell which it is holding:
`Caps` says what the verbs mean at a path, not what the storage guarantees about
bytes at rest. That may be a descriptor that is missing, or it may be that a
content-addressed store verifying its own content is right regardless of what is
underneath it.

Whether the fanout should be the store's decision at all. Two hex digits is right
for a directory tree and meaningless for a prefix keyspace, and `Caps.ObjectStore`
is already the mount saying which one it is. Reading it and laying objects out flat
over a bucket would be one branch — but it would make the same digest name two
different paths depending on the mount, and an object store whose layout moves
under it is a migration waiting to happen.
