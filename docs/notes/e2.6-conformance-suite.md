# E2.6 — The plugin conformance suite

`internal/vfstest`: one test set every storage plugin runs. A plugin hands over a
constructor and the suite drives it through 61 cases, selecting each by what the
plugin claims. `memfs` runs it in four lines and its own package keeps only what
`memfs` alone promises.

```
$ go test ./internal/adapters/outbound/memfs/ -run TestConformance -v | grep -c -- '--- PASS'
57
$ go test ./internal/adapters/outbound/memfs/ -run TestConformance -v | grep -- '--- SKIP'
    --- SKIP: TestConformance/Symlink_makes_one_path_stand_for_another
    --- SKIP: TestConformance/Symlink_to_a_target_that_is_not_there_is_allowed
    --- SKIP: TestConformance/Readlink_of_an_entry_that_is_not_a_link_is_invalid
    --- SKIP: TestConformance/Readlink_of_a_missing_path_does_not_exist
```

## What the pattern was

A case declares what it needs a plugin to claim before it means anything, and
`Run` selects on the `Caps` the plugin answers at its root:

```go
{name: "Write replaces the whole content", when: needs(writable, replacing), run: writeReplacesTheContent}
```

`writable`, `replacing`, `repeatable` and `tree` are the four negatives — not
read-only, not append-only, not read-destructive, not an object store. The
positives select the cases that exist *because* a descriptor is set:
`readOnlyRefusesMutation`, `appendOnlyAddsToTheEnd`, `readDestructiveConsumes`
and the three object-store cases. Optional verb sets are gated differently
again, on the accessor being non-nil, because a refusal there is an answer
rather than a claim.

E2.1's note left two decisions to this ticket, and they are now the suite's:
`Remove` of a directory with entries in it is `fs.ErrExist`, and `RemoveAll` of
the root empties it rather than refusing. Both are asserted for every plugin, so
they are a rule rather than what the first plugin happened to do.

## What surprised me

**A suite that only ever ran against its reference implementation would pass
whatever the reference does.** Every case here was lifted from `memfs`'s tests,
so all 61 passed on the first run — which is evidence of nothing. The suite's
own tests are four mounts that each claim one descriptor over a tree in memory
that claims none, and breaking each one in turn is what says the branch has
teeth:

```
append-only that replaces:   Read after two writes = "second", want "first second"
read-destructive that keeps: the second Read = "work", want it consumed by the first
read-only with a streamer:   OpenWrite on a read-only mount = <nil>, want fs.ErrPermission
object store with a Mkdir:   Stat of a prefix with nothing under it = <nil>, want fs.ErrNotExist
```

**Read-only has to be checked through the accessors too.** A read-only mount
that answers `AsStreamer` and hands back a working `OpenWrite` has a refusal
that is one call away from being bypassed, and the ten verbs all still refuse
correctly. The read-only case collects every mutating verb *including* the
accessor ones, and the read-only fake deliberately answers a streamer so that
path is exercised rather than skipped.

**Extracting the suite deleted four test files and made `memfs` easier to read.**
What is left in `memfs_test` is the tree in memory's own promises: a snapshot
read stream, `fs.ErrClosed` on a write after close, the settings refusal, and
the contention test. Anything that was really about the port had been sitting in
the plugin, where a second plugin could not reach it.

**`path.Join` cleans, which is the work being asserted.** The case for lexical
resolution has to build `//jobs/./audit` by hand: routing it through the helper
that resolves names relative to a plugin's root would clean the path before the
plugin ever saw it, and the case would pass without asserting anything.

## What I would do differently

Put `Root` on `Plugin` later. It is the field that lets a mount whose capability
varies by path run the suite once per path, which is what `Caps` being per-path
is for — but the only plugin today claims nothing anywhere, so it is a mechanism
with no user. It stays because `queuefs` and the object store both need it and
adding it after the fact would change every case's spelling of a path. That is
the calibration rule applied at its edge, and it could have gone the other way.

## What I still do not understand

Whether `Broadcast` can be asserted without a second reader identity in the
port. It separates readers that each receive every entry from readers that
compete for each one, and nothing in `FileSystem` distinguishes two readers: the
suite calls `Read` twice from one goroutine and cannot tell "the second reader
got it too" from "the first read did not consume". The suite says so in its
package comment rather than pretending. E3.1's `queuefs` is where it becomes a
real question.

Whether "the plugin's root" is the right name for what `Remove` and `Rename`
must refuse. For a mount at `/`, the root is the tree's root and refusing is
obvious. For a plugin declaring a root deeper in, the suite is asserting that
the plugin refuses to delete the ground it stands on — which is true of a mount
point, but a plugin could reasonably see that path as an ordinary directory that
its own parent owns.
