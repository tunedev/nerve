# E9.6 — Filesystem passthrough

`files.Tree` is a workspace's own directory tree, as the agent working inside it
walks one. Eleven verbs from the ticket land as twelve methods: `List`, `Stat`,
`Walk`, `Mkdir`, `Copy`, `Rename`, `Find`, `Glob`, `Grep`, `Symlink`, `Delete`
and `DeleteAll`.

## What the pattern was

`kv.Space` and `library.Registry` with one substitution: the scope is a
`workspace.View` rather than a path derived per call with `Scope.Path`.

That substitution is the whole design. Three of these verbs take two paths from
the caller — copy, rename, symlink — and `nrv-rfr` recorded that a symlink target
is the one path nothing beneath the core dispatches: it is clean, inside one
mount and inside the plugin's root, so every layer under the core permits it. A
package deriving its own paths would have to remember to derive both ends of
three verbs. A view derives every path it is handed, so containment here is the
shape of the package rather than a rule each verb repeats.

The rest is thin on purpose. `List`, `Stat`, `Mkdir`, `Rename`, `Delete` and
`DeleteAll` are the port's verbs with the scope in front and nothing else, and
`Walk`, `Find`, `Glob`, `Grep` and `Copy` are walks over them.

## What surprised me

**There is no read and no write, and that is the ticket being right.** A
filesystem passthrough with no way to get bytes in or out reads like an
oversight until you find E6.1 — resource routes: create, upload,
upload-complete, signed download — and E6.5's content escalation. Content
crossing the workspace boundary is a streaming, resumable, signed problem; this
ticket is navigation and structure. `Grep` reads and `Copy` reads, because both
answer about content without carrying it out.

**`find` and `glob` are the same walk and must not be the same question.**
Written naively they overlap enough that a caller cannot predict which to reach
for. Splitting them by what the pattern meets settles it: `Glob` matches the
whole workspace-relative path with `path.Match`, so `*` stops at a separator and
`notes/*.md` says nothing about what is below; `Find` matches the final element
at any depth beneath a directory it is told to start from. The consequence is
that `Glob` takes no starting directory — a pattern carries its own, and a glob
is anchored at the workspace root by what it is.

**A bad pattern has to fail before the walk, not during it.** Matched lazily, a
pattern nobody can parse answers "nothing found" over an empty workspace and
"syntax error" over a full one. One call telling a caller two different things
depending on what happens to be stored is worse than either answer. `compile`
checks once at the top; the discriminating test is a bad pattern over an empty
workspace, which passes under the lazy version.

**One delete verb was not enough, and the argument came from the kv note.**
`nrv-4h9` recorded that `RemoveAll` reaches past a key on a keyspace, where a
key and a prefix can share a name. Here the shapes are trees, so that exact
reach is not the risk — but the same asymmetry is: the failure mode of a
recursive delete is silent and unrecoverable, and the failure mode of a
non-recursive one is a loud error. So `Delete` is `Remove` and refuses a
directory holding anything, and the caller that meant the subtree says
`DeleteAll`. The port has both verbs because they differ; collapsing them here
would be this package choosing a blast radius on the caller's behalf.

**`Walk` should not sort its result.** `library.Registry.Tree` sorts, and copying
that looked obvious until the fixture had both `notes/` and `notes.txt` in it:
sorted lexically, `notes.txt` comes between `notes` and `notes/deep`, because
`.` is 0x2E and `/` is 0x2F. Tree order — every directory's children by name,
each subtree before what follows it — is what a caller reading the result as a
tree wants, and it is deterministic without being sorted.

## What I would do differently

Nothing in the shape. `Grep`'s limit is the one call I would defend rather than
repeat: it is the only walk whose answer grows with the bytes in the workspace
rather than the number of entries, so one common word returns everything. The
precedent is `library.Registry.Search`, which takes a limit for the same reason
and for no other verb.

## What I still do not understand

**Whether `Readlink` belongs here.** `Symlink` is in the ticket and `Readlink` is
not, and the view already answers it correctly — refusing a target that stands
outside the scope. An agent that walks a tree and finds a link has no way to ask
where it points. Left out because the ticket drew the line there, and a second
caller is what should move it.

**Whether an object-store mount should be refused.** The tests run over two tree
kinds, in memory and on a disk, because "walks its workspace as a directory
tree" is a tree's promise. Over `kvfs` a directory exists only because keys are
under it, and `Mkdir` has nothing to make — `Caps.ObjectStore` is exactly how a
mount says so, and nothing here reads it. Whether these verbs should consult it,
degrade, or refuse is a question the first object-backed workspace answers.

**Whether `Copy` should cross scopes.** `library.Registry.Copy` takes a source
scope and a destination scope, which is how a document leaves the workspace it
was written in. This `Copy` takes one scope, because a view is one workspace and
a copy between two of them is two views and a decision about who may ask. Nobody
has asked yet.
