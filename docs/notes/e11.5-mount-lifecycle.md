# E11.5 — What a killed process leaves behind, and what comes for it

A FUSE mount outlives the process serving it. The kernel keeps the mount entry
when the server is gone, and there is no code left in a killed process to
unmount it, so the point stays occupied by something that answers nothing.

Two verbs close it. `Serve` clears a mount left at the point before mounting
there, and `Unmount` no longer leaves one behind when something inside is
holding it.

## The failure, measured

A process mounting `memfs` and then killed with SIGKILL:

```
$ grep $MP /proc/self/mountinfo
1077 29 0:67 / .../mp1 rw,nosuid,nodev,relatime shared:1076 - fuse.nerve nerve rw,user_id=1000,...
$ kill -9 $PID
$ grep $MP /proc/self/mountinfo
1077 29 0:67 / .../mp1 rw,nosuid,nodev,relatime shared:1076 - fuse.nerve nerve rw,user_id=1000,...
$ stat $MP
stat: cannot statx '.../mp1': Transport endpoint is not connected
```

The mount entry is unchanged. Every path through it is `ENOTCONN`, which is the
one condition worth acting on: a live mount answers, and a mount whose server is
wedged rather than gone blocks instead of failing.

It is not merely untidy. The next process cannot mount over it — `fusermount3`
cannot even reach the point:

```
/usr/bin/fusermount3: failed to access mountpoint /tmp/.../001: Permission denied
Serve over the mount the killed process left: mount ".../001": fusermount exited with code 256
```

That is the whole test with `reclaim` removed from `Serve`. One orphan means the
mount point is dead until somebody runs `fusermount3` by hand.

## What the fix is, and what it is not

`reclaim` unmounts the point when, and only when, it answers `ENOTCONN`. It runs
inside `Serve`, because mounting is the only thing that ever comes for a stale
mount: nothing else is scheduled, and a caller that has to remember to call a
cleanup verb first is a caller that will one day not.

**The window is not closed, it is bounded.** Between the kill and the next mount
the entry is still there. A dead process runs nothing, so nothing else is
possible from inside it. What genuinely removes the window is a private mount
namespace: the mount lives and dies with the namespace, and nothing survives the
last process in it. That is the same machinery `nrv-sd43` is already deciding
about for the process boundary, and this is one more argument for it rather than
a second decision.

## The other way a mount is left behind

The process that does get to run its shutdown can still leave one. An ordinary
unmount fails while a descriptor opened through the mount is open:

```
$ sleep 120 < $MP/note &
$ fusermount3 -u $MP
fusermount3: failed to unmount .../mp3: Device or resource busy
rc=1
$ fusermount3 -u -z $MP
rc=0
$ grep $MP /proc/self/mountinfo
(gone from the table)
```

E11.1 made that `EBUSY` visible on the grounds that unmounting is fallible and a
caller ignoring the error leaves a mount behind. It is fallible, and the caller
still leaves a mount behind — because at shutdown there is nothing useful to do
with the answer. Whatever holds the descriptor is *inside* the mount, and the
process that would wait for it is the one about to exit and stop serving it.
Waiting is how you get both an orphan and a slow exit.

So `Unmount` falls back to a lazy detach. The mount leaves the table at once, the
descriptors that blocked it keep answering, and the kernel frees the mount when
the last one closes. The contract is now the outcome rather than the mechanism:
nil means nothing is mounted there.

## What surprised me

**`auto_unmount` cannot be used with go-fuse, and it fails silently.** It is the
obvious prevention — `fusermount3` stays alive and unmounts when the daemon dies
— and it mounts and then hangs:

```
$ grep -c $MP /proc/self/mountinfo
1
$ ls $MP
(hangs; "mounted" never printed)
```

`callFusermount` does `proc.Wait()`, and with `auto_unmount` the helper does not
exit. The mount is made, `fs.Mount` never returns, and nothing answers the
kernel. The mount exists with no server — the exact state the ticket is about,
arrived at by trying to prevent it. Even if the wait were fixed, go-fuse closes
both ends of the `_FUSE_COMMFD` socketpair as soon as it has the descriptor, and
that socket closing is what the helper watches.

**The kernel logs the lazy teardown as an abort.** go-fuse prints
`Failed to read from fuse conn: 103=software caused connection abort` when the
last held descriptor closes after a detach. There is no clean unmount to
observe, so the connection ends by abort. Cosmetic, and worth knowing before
somebody reads it as a bug.

**Counting mount entries is the only assertion that discriminates.** A mount
stacked over another serves exactly as well as one, so "reading a file works"
cannot tell a reclaimed point from a corpse with a fresh mount on top. The test
counts entries in `/proc/self/mountinfo` and requires one.

## What is deliberately not here

**`nerved` still mounts nothing.** E11.1 named E11.5 as the reason it did not,
and that reason is gone — but *what* the composition root should mount is E11.3's
question, not this one, and it is still open (one mount per workspace, or one per
area). Wiring a mountpoint setting now would be answering it by accident.

**Nothing refuses to mount over a live mount.** Stacking is a way to hide a mount
and therefore to lose one, but it is also legitimate, and no caller here does it.

**No `Run(ctx, ...)`.** The lifecycle is `Serve`, `Wait`, `Unmount`, and a
wrapper that calls the third in a `defer` guarantees nothing a `defer` does not.
What a caller cannot do for itself is reclaim a point a dead process left and
unmount one something else is holding, and both of those are where they are
reached.

## What I still do not understand

Whether `reclaim` should say that it fired. A restart that silently clears the
last run's corpse is a restart that never mentions the last run crashed. The
package has no logger and `Serve` returns a `*Mount`, so saying it means widening
one of those, and the operator signal probably belongs to whatever supervises the
process rather than to the mount.
