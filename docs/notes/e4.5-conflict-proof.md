# E4.5 — the conflict proof

A commit reads the ref, walks the tree, stores what it found, and only then moves
the ref. The window between the reading and the moving belongs to a second
process: `localrefs` does its compare-and-set under one mutex, so no second
writer in this process can land inside it. `conflictOnce` in
`internal/core/version/conflict_test.go` is a `RefStore` that runs another
writer's commit once, immediately before the write it was armed for reaches the
store underneath — the only way to put a writer in that window.

It fabricates no error. What the double controls is when the other writer runs;
the refusal comes from the real compare-and-set against the real ref. That is
what "exercised, not asserted around" is asking for, and it is why this is not
the ref store that lied about `Resolve` which E4.4 deleted.

```
$ go test -count=1 -v ./internal/core/version/ | grep -c '^--- PASS'
22

$ go test -race -count=1 ./...
(all packages ok)

$ make lint
0 issues.
```

The test asserts the whole path rather than the error: the loser is told, the
winner's version is still what the ref stands for, the losing copy has not been
moved onto anything, and reconciling is what makes the refused commit land — on
top of the version it never saw.

## What the pattern was

**A double that controls timing, not outcomes.** The fault injected is a
schedule: another writer commits, for real, at a moment nothing else can reach.
Every value the test then asserts on is produced by production code — the
conflict by `localrefs`' compare-and-set, the winning version by a real commit,
the recovery by `Reconcile`. A double that returned `ErrConflict` itself would
have asserted that `errors.Is` works.

**The other writer holds the refs directly, not the double.** It stands in for a
second process, and a second process does not write through this one's
injection point. Wiring it to the double would also have made the hook re-enter
itself.

**Armed once, by dropping the hook when it fires.** `conflictOnce.other` is
nilled before it is called, so the retry after `Reconcile` runs against a store
that has gone back to being the plain one. A `sync.Once` would have said the
same thing and made arming it after construction — which is what the setup
commit needs — a second concern.

## What surprised me

**The assertion that discriminates is the one about the copy, not the one about
the error.** Making `point` swallow the conflict and set the ref from a fresh
read fails this test, and it also fails
`TestCommitFromACopyThatNeverSawTheRefIsAConflict` and
`TestReconcileResolvesDivergenceBetweenTheCopyAndTheRef` — the two tests that
already existed. The break only this test catches is moving `SetBase` above
`point` in `Commit`:

```
--- FAIL: TestACommitThatLosesTheRefInsideItsOwnWindowIsToldSo
    conflict_test.go:77: the losing copy stands at "sha256:bd01e52f..." (<nil>),
        want the "sha256:0fadff3f..." it was taken from
```

with the whole rest of the package still green. A copy recorded as standing on a
version the ref refused is worse than the refusal: its next commit expects a
version the ref has never held, so it cannot win a race it has already lost, and
`Reconcile` is the only way back. The existing conflict tests do not see it
because they reconcile straight afterwards, which overwrites the wrong base.

**The window is real and the store already closes it.** No break inside the
versioner could get a write past `localrefs` in that window, because the
compare-and-set is the store's and not the caller's. The proof is therefore that
the window is not a hole, and the test would begin discriminating the moment a
ref store did its comparing anywhere above its own atomic step — which is the
first thing a Postgres implementation could get wrong.

## What I chose not to build

**A reusable fault-injecting store in a package of its own.** One test injects
faults. `internal/vfstest` is shared because every storage plugin runs it; a
`RefStore` double with one caller is a test helper, and it lives in the test
file that uses it until a second one needs it.

**Injection on `Delete` and `Resolve`.** `Set` is where a race is decided.
Arming the other verbs would be describing a double rather than proving
something about the versioner.

**A concurrency proof over `Purge`.** `Versioner.commits` is per versioner, so
two versioners over one object store exclude nothing — filed as `nrv-1b0`
rather than fixed here. It is the same shape of window and a different ticket's.

## What I still do not understand

Whether the losing commit should clean up after itself. It stores every object
of the tree it was refusing to commit, and those objects survive the refusal
until a sweep collects them, so a copy that keeps losing keeps writing content
no version will ever name. Storing before taking the ref is deliberate — the ref
must never name an object that is not there — but nothing decides how long the
other order's leftovers stay, beyond `Purge` eventually running.
