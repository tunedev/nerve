# E12.2 — Effective config, redacted

`GET /config` on the admin surface answers with every setting under the one name
it is spelled with everywhere else, and with the mount table. Any password
inside a connection string is replaced with `xxxxx` first.

## What the pattern was

The view is built from the same field table E12.1 introduced, so a setting added
to `Config` appears in the answer without anyone remembering to add it. A
reflection test asserts one `Setting` per string field of `Config`, which is the
only way "never requires guessing" stays true after the next setting lands.

Redaction lives in `Config.Effective()` rather than in the handler, and the
handler takes the `Effective` value rather than the `Config` it came from. A
surface therefore has nothing unredacted to leak, and the second surface — a CLI
subcommand, a log line at boot — costs nothing and cannot forget.

## What surprised me

**The endpoint made nerved a process.** Until this ticket the binary printed and
exited. There is no way to serve an endpoint from a program that has already
exited, so E12.2 is where the first inbound adapter, the signal handling and the
drain arrived. That is more than the ticket names, and it is the honest reading
of it: an "endpoint" nobody can call answers nothing.

**One rule beat a list.** The first shape was a `secret bool` on each field.
That is a list to keep in sync, and it cannot reach mount settings, whose keys
are operator-chosen and unknowable here. "Replace the password in anything that
parses as a URL and carries one" needs no list, reaches mount settings for free,
and leaves a value that is not a URL exactly as written — which matters, because
redaction that mangles what it did not have to hide is guesswork of its own.
`url.URL.Redacted` is stdlib and does the replacing.

**`admin-addr` defaults to loopback.** The answer names hosts, ports and the
shape of the mount table. That is for whoever is on the box, not for the
network, and the default is the place to say so.

**Go's `ServeMux` gives 405 for free.** `mux.HandleFunc("GET /config", ...)`
answers `POST /config` with 405 rather than 404, so "read-only" needed no code.

## What I would do differently

Nothing yet. The value-versus-function choice for the handler's config is the
one to revisit: it is a value because config is resolved once at boot, and a
surface that re-read it would be answering a different question from the one the
process booted on. Hot reload (Tenet 6, "where it is safe") would invert that.

## What I still do not understand

Whether the operator surface should be HTTP at all. E12.7 surfaces traffic
accounting "through a server-info mount", which is the same information reached
through the VFS instead of through a port. If that is where operability lands,
this handler is a stepping stone and `/config` eventually becomes a path in the
tree that reads back the same view. E12.10 adds health here first, which will
make the answer clearer than arguing it now.

Whether the timeouts on the admin server should be settings. They are constants
with a comment saying why: the surface answers from memory, so they bound a slow
client rather than a slow answer. An operator who has to tune them has a
different problem from the one this surface solves.
