# E2.8 — the object-backed keyspace

`kvfs.ObjectStore` is the second implementation of `kvfs.Store`: a keyspace where
a key is an object name and a listing is a prefix query. It sits on
`objectfs.Bucket`, so the wire, the signing and the S3 client are the ones E2.4
already shipped, and kvfs is the same plugin over either keyspace.

```
$ go test ./internal/adapters/outbound/kvfs/ -run 'TestConformance$' -v \
    | grep -cE '^        --- PASS'
56                          # the suite selects 28 cases, run once per store

$ make up && make test-store
ok  github.com/tunedev/nerve/internal/adapters/outbound/objectfs  0.321s
ok  github.com/tunedev/nerve/internal/adapters/outbound/kvfs      0.318s
```

## What the pattern was

E2.5 wrote the port and predicted this ticket would have to change it rather than
implement it. That is what happened, and the prediction was the useful part: both
changes it named were already written down before there was a second store to
justify them.

`Head` describes a key without fetching it. `Stat` and the mode a write carries
over both used `Get`, which over a map is free and over a bucket is a GET where a
HEAD would do — on the two verbs a caller uses most.

`Move` replaces the fetch-store-delete `Rename` was doing through the port. Over
a bucket it is a server-side copy and a delete, so a renamed value's content never
travels through this process; over the map it is one lock, so no reader sees the
value at both names or at neither.

The third change was not predicted. `Put` took a `Value` carrying a `ModTime` the
plugin had stamped, and a store on the wire cannot keep one: S3 records the
instant it wrote. So `Put` takes content and a mode, the store stamps the time,
and the port asks only that a write moves it forward. A field the second
implementation would have had to silently ignore is a promise the port was not
keeping.

The port's cases are in `store_test.go` and run three times: over the map, over a
bucket in a map, and — under `make test-store` — over MinIO.

## What surprised me

**MinIO does not list both halves of a key-versus-prefix collision.** Store
`p/c/abc` and `p/c/abc/state` and both `Head` and `Get` answer for both, but
`ListObjectsV2` over `p/c/` returns only `p/c/abc`. The deeper key is not gone,
it is hidden: delete `p/c/abc` and it lists again. A pair at the same two depths
that does not share a name — `p/n/abc` and `p/n/def/state` — lists both.

That is one real store declining what nrv-4pm made the conformance suite ask, and
it has two consequences worth naming. The suite's collision case passes against
MinIO for the wrong reason: it asserts a listing answers with the key, and MinIO
answers with the key because it never offers the prefix. And `RemoveAll` over a
collision leaves the hidden key behind, which is exactly what was found in the
bucket after a run:

```
$ mc ls -r n/nerve
[...] TestConformanceAgainstAnObjectStore-Object-store-lists-a-key-over-a-prefix-of-the-same-name/sessions/abc/state
```

The port's own listing case was written with a colliding pair and had to be
rewritten without one, because the port cannot promise every store something a
store this project ships does not do. The collision stays a plugin-level question,
where the suite asks it. Filed as nrv-dzx rather than solved here.

**A fake that tells the truth where the wire does not is a fake that lies.** The
bucket in a map lists an object's stored mode and its instant to the nanosecond.
A real listing carries neither — `ListObjectsV2` returns a key, a size and a
last-modified to the second, and no user metadata. So the fake here reports the
default mode and a truncated instant on `List` alone, and the same object read
back through `Head` carries the mode a `Chmod` set. Both are true of the wire;
only one of them is convenient.

**Two of the port's promises are kept by the wire for free and one is not.** A
value serialised onto a connection cannot be changed through the caller's slice,
so the copy promise E2.5 put in the port costs `ObjectStore` nothing — which is
what that decision was betting on. But a bucket answers a delete of nothing with
success, and the port promises `fs.ErrNotExist`, so `Delete` looks before it
deletes. A remove of a session that was already removed has to be an error the
caller can act on, and that is a round trip the map does not pay.

**The dependency runs from the key-value store to the object store, and stops at
the port.** `kvfs` imports `objectfs` for its `Bucket` interface and its `Object`
type, not for its `S3`. Declaring a narrower bucket interface here would not have
decoupled anything — Go's structural typing would still need `objectfs.Object` in
the signatures — and it would have been a second port over one wire, with two
sets of semantics to keep agreeing. Adapters already share `synth` this way.

## What I chose not to build

**The composition root still builds only the keyspace in memory.** An operator
cannot mount a durable `kvfs` yet. Wiring it means the process needs a bucket's
endpoint, name, region and two credentials before any mount exists, and the
config layer has no shape for that: `objectfs` carries its credentials as mount
settings because a mount is where its bucket is named, and a `kvfs` mount is a
namespaced part of one shared keyspace instead. Adding both the second store and
a new spelling for a store's connection would put two unknowns in one increment.
Filed as nrv-39e.

**`Chmod` is still a read and a write.** A bucket can replace an object's metadata
without its content moving, and `objectfs.Chmod` does exactly that with `Copy`.
The `Store` port has no verb for it, so `kvfs.Chmod` fetches the value and stores
it back. Adding one would be a third port change in a ticket that already made
two, and `Chmod` is the rare verb — which is the same trade E2.4 recorded from the
other side, where `Write` pays a `Head` so that `Chmod` means something.

## What I still do not understand

Whether the `ObjectStore` descriptor should say which kind of object store. E2.5
left this open and the second implementation sharpens it rather than settling it:
`kvfs` over a map and `kvfs` over a bucket claim exactly the same descriptor and
answer the same verbs, but one of them can hold a value larger than memory and
one cannot, and a caller cannot tell them apart from what the mount says about
itself.

Whether a listing should be held to reporting the mode. `ReadDir` over a bucket
reports `0644` for every key regardless of what `Chmod` set, because the wire's
listing carries no metadata, and `Stat` of the same key reports the real mode.
Nothing in the suite catches the disagreement, and it is not clear whether the
honest fix is a listing that pays a `Head` per key, a `ReadDir` that stops
claiming to know, or leaving it as the cost of listing cheaply.
