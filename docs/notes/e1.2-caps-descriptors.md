# E1.2 — Caps descriptors

Five descriptors — append-only, read-destructive, read-only, broadcast,
object-store — as a struct in `internal/core/vfs`, reached through
`Capabilities(path) Caps` on the port. A queue mount reports read-destructive on
`/jobs/next` and not on `/config`.

## What the pattern was

Descriptors as data, resolved per path. The alternative — a `ReadDestructive`
marker interface a caller type-asserts on — is the move the repo's settled
decision forbids, and this ticket is where the reason becomes concrete rather
than theoretical.

## What surprised me

**Per-path is not a nicety, it is the whole reason descriptors are data.** A type
is a property of the mount. Capability is a property of the path: one queue mount
holds job entries that are consumed by reading and a config entry beside them
that is not. No interface can be half-implemented for one subtree, so the answer
has to be a value the plugin computes from the path it was handed.

**`Capabilities` is not a verb, so it takes no context and cannot fail.** Every
other method on the port takes a `context.Context` because a mount may be remote.
This one answers from the shape the plugin already knows, and giving it a context
and an error would invite a plugin to make a network call to say what it is —
turning a question every caller asks before acting into a second round trip.

**The zero value had to be the boring case.** Descriptors are bools whose false
is "ordinary read-write tree", which is what most storage kinds are. That is what
lets E1.3's `NoCaps` be an embeddable default that returns `Caps{}`: a plugin
declares what is true of it and writes nothing for the rest.

## What I would do differently

Nothing yet. A bitset was the other option and buys nothing here — named fields
read at the call site (`caps.ReadDestructive`), and adding a sixth descriptor is
additive either way.

## What I still do not understand

Whether descriptors stay orthogonal. `Broadcast` and `ReadDestructive` describe
the same read in a queue mount — one says every reader gets every entry, the
other says a reader consumes what it gets — and a fan-out exchange sets both
while a work queue sets only the second. E3.1 and E3.2 are where that either
holds or collapses into one descriptor with three values.

Whether `ObjectStore` belongs in this set at all. The other four constrain what a
verb does; that one says the path namespace is not a tree, which is closer to
E2.4's problem than to a capability. It stays because the roadmap names it, and
the object-store plugin will say whether callers actually branch on it.
