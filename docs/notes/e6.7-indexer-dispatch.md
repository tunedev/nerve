# E6.7 — Indexer dispatch: fan work to handlers

Adding a kind of indexing is a handler handed to `ingest.NewDispatch` at
composition. Dispatch routes by what a handler says about itself and knows no
kinds, so the file is untouched by there being one more.

A dispatcher is a `Stage`, which is how a handler set reaches ingestion without
the pipeline learning that indexers exist. It answers the question E6.2 left
open — whether stages stay a flat ordered list — with: they do, and a fan-out is
one of them.

The acceptance is asserted by mutation, four ways, each caught by a different
test:

```
$ go test ./internal/core/ingest/   # with the Handles gate removed
--- FAIL: TestDispatchFansAResourceToEveryHandlerThatClaimsIt (0.00s)
    dispatch_test.go:108: pdf indexed [transcript.txt], want nothing it did not claim

$ go test ./internal/core/ingest/   # with the fan-out run one handler after another
--- FAIL: TestHandlersRunConcurrently (5.00s)
    dispatch_test.go:176: Run = indexer "meet": context deadline exceeded

$ go test ./internal/core/ingest/   # with a failure ending the run, as a stage list does
--- FAIL: TestAFailingHandlerDoesNotStopTheOthers (0.00s)
    dispatch_test.go:141: text indexed [], want [transcript.txt] despite the failure beside it

$ go test ./internal/core/ingest/   # with only the first failure reported
--- FAIL: TestDispatchReportsEveryHandlerThatFailed (0.00s)
    dispatch_test.go:157: Run = indexer "vectors": the vector store is down, want both ...
```

## What the pattern was

The thesis at the altitude of a handler: one interface, a set given at
composition, and implementations that describe their own applicability.
`Handles(resource.Resource) bool` is the descriptor, and it is a predicate
rather than a list of content types on purpose. A list puts the matching rule in
dispatch, and the first handler that selects on anything else — a size, a digest
already seen, a workspace setting — turns that list into the switch the ticket
forbids. Asking the handler costs nothing and never becomes a table.

Fan-out is Tenet 4's, in its plainest form: a `sync.WaitGroup` started per
claimant, joined before the call returns. Nothing outlives `Run`, so the
caller's deadline is the only thing bounding the handlers and the leak check
over this package stays honest.

## What surprised me

**Independence, not concurrency, is what makes this a second type.** The first
draft was a stage that looped over handlers, and it read as a shorter version of
`Pipeline`. What separates them is the failure rule: a stage that fails ends the
run because the next stage is written expecting it to have happened, and nothing
is written expecting an indexer to have happened. So every claimant runs and
`errors.Join` reports all of them — one vector store being down costs the
embedding and not the full-text index, which is Tenet 2 degrading in parts
rather than a system failing whole. Running them together is then obviously
right, but it is a consequence of independence rather than the reason for it.

**A concurrency test that closes a gate proves nothing.** The first version had
every handler wait on one channel the test then closed, which a serial
dispatcher passes: it blocks on the first handler until the close and then walks
the rest. The test only discriminates with a barrier that releases on the last
arrival — under serial dispatch the first handler waits for a second that will
never start, and a bounded context turns that deadlock into a named failure
instead of a hang.

## What I would do differently

The predicate was nearly a `[]string` of content types, because that is what the
two indexers anyone can name today would return. It would have been the shape
the second case broke.

## What I still do not understand

**Whether a handler that claims nothing should be visible.** A dispatcher with
three handlers and a resource none of them claims returns nil, which is correct
and silent. E6.6 is where a caller learns whether a document became searchable,
and "nothing indexes this format" and "everything indexed it" are the same
answer from here.

**Whether a slow indexer should bound the others.** They share the caller's
deadline and nothing else, so one hanging handler holds the goroutine that is
waiting on all of them for as long as the worker's context allows. A per-handler
timeout is the obvious answer and has no evidence behind it yet; the mount
registry already bounds every remote call it builds, and an indexer that talks
to a mount inherits that.

**Nothing runs this either.** Dispatch is a stage, and the pipeline it is a
stage of is still unwired — the resources root, signing key and observed mount
of nrv-amti and nrv-d4b.
