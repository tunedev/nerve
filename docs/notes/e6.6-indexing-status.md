# E6.6 — Indexing status

`ingest.Ledger` is where the ingestion of every document stands: `Working` when
a worker claims the job, `Indexed` the moment every stage has run, `Failed` with
the stage that stopped it and why, and `Pending` for a document no record has
been written for. `Pipeline` writes it as it runs and `Get` is what a caller
reads.

The acceptance is that a caller can tell *when* a document became searchable,
and both halves of that are asserted rather than described — the moment, and the
answer before there is one:

```
$ go test ./internal/core/ingest/    # with the record unstamped
--- FAIL: TestALedgerSaysWhenADocumentBecameSearchable (0.00s)
    ledger_test.go:51: Get = {Name:transcript.txt Status:indexed Stage: Failure:
    At:0001-01-01 00:00:00 +0000 UTC}, want {Name:transcript.txt Status:indexed
    Stage: Failure: At:2026-08-31 09:30:00 +0000 UTC}

$ go test ./internal/core/ingest/    # with a missing record reported as an error
--- FAIL: TestADocumentNothingHasIngestedIsPending (0.00s)
    ledger_test.go:62: Get: read "/ada/hunt/transcript.txt": file does not exist

$ go test ./internal/core/ingest/    # with the pipeline not recording that it started
--- FAIL: TestADocumentIsSaidToBeWorkingWhileItsStagesRun (0.00s)
    pipeline_test.go:371: indexing during the run = "pending", want "working"
```

## What the pattern was

`thread.Log`, again, and close enough that reading it was most of the design.
Three states, a record file holding what a run said about itself, a `Get` that
answers the cheap question without doing the expensive one. Where this diverges
it diverges on purpose, and each divergence is a fact about ingestion rather
than a preference:

- **A fourth status.** A thread is started before anything can ask about it, so
  its record always exists. An ingestion is asked about by the caller that
  uploaded the document, before any worker has claimed the job, so the absence
  of a record is a state — `Pending` — and not a refusal the caller has to
  translate.
- **No transition rules.** `thread.Log` refuses a second ending, because the
  first ending is the one a reader has acted on. Ingestion is retried: a worker
  that died mid-run leaves a document saying it is working, and the retry that
  claims the job again has to be able to finish it. The latest record stands.

The ledger holds a root of its own rather than writing a file beside the
resource it is about. Two reasons, and the second is the one that would have
bitten: where a resource stands is `resource.Store`'s answer and only its answer
(E6.2 already paid for learning that), and the resources tree is the one wrapped
in the write observer — a status write into it would be published as a job, and
ingestion would be notified of its own bookkeeping.

## What surprised me

**The `Working` record is the only thing that makes a slow ingestion legible,
and it costs one write.** The acceptance asks only for the moment a document
became searchable, which the two terminal statuses answer on their own. Records
of only those leave `Pending` meaning both "no worker has claimed this" and "a
worker claimed it and is still going", which is precisely the distinction a
caller polling a PDF through an LLM summariser needs. It is also what makes a
died-mid-run worker visible at all: without it a crashed ingestion reads exactly
like one that was never claimed.

**A ledger write that fails must not swallow the stage error that preceded it.**
`Ingest` returns `errors.Join(failed, p.ledger.Failed(...))`. Dropping the
recording error the way `Upload` drops its close would leave the document saying
it is working with nothing to ever say otherwise; returning it instead of the
stage error would hide what actually went wrong from the worker. Joining keeps
`errors.Is(err, refused)` true for the caller and loses neither.

## What I would do differently

Nothing structural. The call that took longest was where the read verb goes:
`Pipeline` holds the resource store, so `Pipeline.Get` could refuse a document
that does not exist instead of reporting it `Pending`. It would also make the
caller-side read go through the consuming end of the queue, which is the wrong
half of the system to hand an API server. The ledger answers what the ledger
knows and `resource.Stat` answers whether the document is there; an inbound
handler that wants both asks both. If that turns out to be one round trip too
many for every status poll, this is the seam that moves.

## What I still do not understand

**A deleted resource leaves its record behind.** `resource.Store.Delete` knows
nothing about the ledger, so asking about a deleted document reports the
ingestion of the document that used to be there. E5.3's workspace delete is the
place that sweeps every root at once, and this is one more root for it; a
per-resource cleanup would be a third thing that has to agree about what a
resource is.

**Whether `Stage` survives E6.3.** The failure names one stage from a flat
ordered list. If a per-format processor turns out to be a stage that dispatches,
the useful name is the processor's and not the dispatching stage's, and the
record would be naming the wrapper.

**The flat-segment rule is now written six times.** `workspace.validSegment`,
`version.ValidateRefName`, `library.validName`, `kv.validSegment`,
`resource.validName` and this one. E9.1 filed the extraction and it is still
open; writing the sixth copy was a scope call, the same one E6.1 made about the
fifth.
