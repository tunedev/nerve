# E3.1 — queuefs

`internal/adapters/outbound/queuefs`: a job queue behind the same ten verbs as
every other kind. A message is written by writing a path and consumed by reading
it. The mount holds two places and they mean different things:

```
mount /queue kind queuefs
  /queue/jobs        {ReadDestructive:true  ObjectStore:true  ReadOnly:false}
  /queue/jobs/<key>  {ReadDestructive:true  ObjectStore:true  ReadOnly:false}
  /queue/config      {ReadDestructive:false ObjectStore:false ReadOnly:true}
```

Two ports inside the plugin. `Journal` is where messages live — Postgres in the
shipped stack — and `Broker` is what a recorded message is carried over, which
is RabbitMQ. The record comes first and the carry second, so losing the broker
loses a notification rather than a message.

## What the pattern was

The first plugin the conformance suite runs twice. `devfs` already varies its
descriptor by path — its sink claims nothing where the rest claims read-only —
but the path that differs is one file, so the suite runs once and the sink is
asserted by hand beside it. Here both places are directories a suite can work
under, so `vfstest.Plugin.Root` earns the sentence its doc comment always
made: a mount whose capability varies by path is run once per path, and each
run holds the plugin to what it claims there.

| Run | Cases |
|---|---|
| memfs, a plain tree | 61 |
| queuefs at `/jobs` | 27, plus 12 the accessors skip |
| queuefs at `/` | 6, plus 2 the accessors skip |

Nothing was written twice and nothing was skipped by hand. The `/` run asks for
`Read-only refuses every mutating verb` against the same object the `/jobs` run
asks to queue things, and it caught the case that matters: `Mkdir("/jobs")` has
to refuse, because the queue directory is the mount's shape and not a prefix a
caller can make, while `Mkdir("/jobs/anything")` returns nil because under the
queue there is nothing to make.

The second pattern is the transactional outbox with one table. A message and the
intent to publish it are columns of the same row, written by the same statement,
so no failure exists that leaves one without the other. `carried_at IS NULL` is
the outbox; `claimed_at IS NULL` is the queue; the row itself is the record a
late consumer is backfilled from.

## What surprised me

**The outbox does not need two tables when the message is the business state.**
The pattern exists because a domain row and a message about it are different
rows and a crash can land one without the other. Here they are the same thing,
so the whole ceremony collapses to two nullable timestamps and an `ON CONFLICT`
clause that clears one of them. Recognising that saved a table, a background
pump and a whole class of consistency bug — and it only works because the queue
*is* the storage rather than a projection of it.

**A relay with a goroutine would have been the wrong shape.** The obvious build
is a pump on a ticker, and the composition root would have had to own it because
the plugin registry's `Factory` has no lifetime to hang one on. A write drives
the relay instead: the broker that was down is drained by the next write. No
goroutine, no ticker, nothing for `goleak` to find, and the self-healing is a
consequence rather than a feature.

**A queue is an object store, and saying so removes nineteen tests.** Keys are
flat, a prefix is a directory only while a message is under it, and `Mkdir` has
nothing to make — the `ObjectStore` descriptor already meant exactly that. It
also makes a message key a routing key: `/queue/jobs/index/document/42` publishes
under the AMQP topic `index.document.42`, so a consumer binds to `index.#` and
the queue never learns a consumer exists.

**A descriptor gated a case that a second descriptor made impossible.** The
object-store collision case reads two entries back and then lists them twenty
times, which needs a mount that answers the same read twice. Read-destructive is
exactly the mount that does not. The case now declares `repeatable` alongside
`objectStore`; objectfs and kvfs still run it. A conformance suite that honours
descriptors has to honour them in combination, and this is the first plugin that
claimed two at once.

**A nil slice is not an empty message to a driver.** `Create` writes `nil`, and
pgx sends that as SQL `NULL` against a `NOT NULL` column. Two conformance cases
failed against Postgres having passed against the fake, where `nil` and `[]byte{}`
are the same value. It is the same class of defect as objectfs's coarse S3 clock:
the fake agrees with whatever you built, and only the real store disagrees.

## What I would do differently

Run against Postgres sooner. The whole plugin was green offline before the stack
was started, and the `NULL` defect was sitting in it the entire time — the same
lesson E2.4 wrote down, learned again.

The boot line prints capabilities at the mount's own prefix, so a queue advertises
itself as `ReadOnly:true` in the mount table an operator reads at startup. That is
true of `/queue` and useless as a summary. A mount whose descriptor varies wants a
different line, and that is `cmd/nerved`'s to change rather than this plugin's.

## What I chose not to build

**Consuming from the broker.** A reader claims a row in Postgres; the broker is
told, and never asked. That is what makes losing it survivable and backfill
possible, and it means a remote consumer receiving a notification still has to
come back to the journal to take the work. E3.4's work bus is where the
consuming side belongs.

**A running relay.** `Relay.Carry` drains on write and `Relay.Backfill` replays
history, and nothing calls either on a schedule. A queue that stops being written
to stops carrying, and messages sit recorded until the next write. E3.4 needs a
consumer waiting, which is when a pump has an owner worth giving it.

**Claims that expire.** A message a reader took is claimed forever. There is no
visibility timeout, no redelivery and no dead-letter path, so a consumer that
crashes between claiming and finishing has taken the work with it.

**The link and stream verb sets, and `Truncate`.** All three are refused through
their accessors. Streaming a message would make the journal row a chunked write
for no caller that has one, and a queue has no links.

## What I still do not understand

Whether `Write` should report a broker it could not reach. It does not: the
message is recorded, so the write succeeded, and the refusal is only visible to
whoever calls `Carry` directly. That is right for durability and it means a
mount whose broker has been unreachable for an hour looks perfectly healthy from
the tree. The breaker never opens either — nothing failed. Something has to
surface it, and a descriptor cannot.

Whether one table for every queue survives contact with a second one. The partial
unique index is on `(queue, key)` and every statement carries the mount's name,
so it is correct; whether it is still correct when a queue holds a million rows
and another holds ten is a question for an index, not a design.
