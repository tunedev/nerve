# E4.3 — the versioner

`version.Versioner` is the one thing holding all three parts of E4: the working
tree, the object store that holds what a version says, and the refs that say
where a tree stands. Its verbs are `Status`, `Commit`, `ListVersions`,
`ReadVersion`, `Diff`, `Restore`, `Reconcile` and `Purge`.

```
$ go test -count=1 ./internal/core/version/ -v | grep -c '^--- PASS\|^    --- PASS'
20

$ go test -race -count=1 ./...
(all packages ok)

$ make lint
0 issues.
```

The acceptance — commit, mutate, diff, restore — runs over memfs and over a host
directory, because nothing in the versioner knows which mount it is holding. It
discriminates: with the removal arm of `Restore` skipped,

```
$ go test -count=1 -run TestCommitMutateDiffRestore ./internal/core/version/
--- FAIL: TestCommitMutateDiffRestore/memfs (0.00s)
    versioner_test.go:137: a file the restored version never had is still there: <nil>
    versioner_test.go:144: got 2 changes [{notes/one.md modified} {two.md added}], want 3 [...]
--- FAIL: TestCommitMutateDiffRestore/localfs (0.01s)
    ...
```

## What the pattern was

**A version is one object, and its digest is its ID.** The manifest carries the
parent, the message, the time and the content of every path, sorted; it is
stored through `cas.Store` like anything else, so `ID` is just the spelling of a
digest and `ReadVersion` is a parse, a `Get` and a lookup. There is no separate
version index to keep agreeing with the object store, and nothing had to be
added to `RefStore`: a ref already points at an `ID`.

**Sorted entries make the diff a merge walk.** `changes(from, to)` is a single
pass over two sorted slices, and every comparing verb is built out of it —
`Status` is committed against working, `Diff` is version against version,
`Restore` is working against target and then apply. One function is what makes
those four agree about what "modified" means.

**The zero ID as the empty version settled the shape of five verbs.** E4.2
already said an unset ref resolves to the zero ID; carrying that through means
`Status` on a tree that has never been committed says every file is new,
`ListVersions` of an unset ref is an empty history, and `Diff("", id)` is every
path added — which is also why there is no separate "list the paths at a
version" verb.

**`Restore` is the one place that refuses it.** Comparing against nothing is a
comparison; restoring to nothing would be a deletion of the whole tree wearing a
restore's name. `Reconcile` inherits that refusal through `RefStore.Resolve`, so
reconciling to a ref that stands for nothing is `fs.ErrNotExist` rather than an
emptied tree.

**Commit is idempotent, which Tenet 7 asks of anything automation reruns.** A
tree that has not changed is not committed again: the current ID comes back and
no ref is written. Content addressing makes that cheap — the walk stores every
file first, and every one of them is already there.

## What surprised me

**A sorted walk of a tree does not produce sorted paths.** `ReadDir` sorts each
level, so the walk yields `a/b.txt` before `a.txt` — the directory `a` is listed
before the file `a.txt`, but `.` (0x2E) sorts before `/` (0x2F), so the full
paths come out in the wrong order. The merge walk silently reported spurious
adds and removes until the entries were sorted by path after the walk rather
than during it. Depth-first order and lexicographic order are different orders
and it costs one `slices.SortFunc` to stop pretending they are the same.

**`Status` wanted to store objects and should not.** The obvious implementation
shares one walk with `Commit`, which means asking what changed writes every
file's content into the store. It is harmless — the objects dedupe and the sweep
would collect them — but a question that leaves work for a sweep is a question
with a side effect. Splitting the walk into a visitor with two callers, `hashed`
(compute only) and `stored` (put), costs about ten lines, and
`TestStatusStoresNothing` is the assertion that keeps it true.

**The sweep needed a verb E4.1 deliberately did not build, and it belonged in
`cas`.** `Store.List` walks the three-level layout and skips anything that is
not laid out as an object, because the store shares its mount with whatever else
was handed the same root. Putting the walk in the versioner would have meant the
fanout width living in two packages.

**Purge and commit race, and the honest fix was one `RWMutex`.** A commit stores
its content before the ref that will name it exists, so a sweep running between
those two deletes content a version is about to claim. Commits take the read
lock — they still race each other on the ref, which is the race the
compare-and-set exists to answer — and the sweep takes the write lock. Like
`localrefs`, that is true for this process and for no other, and saying so is the
argument for the Postgres ref store rather than an apology.

## What I chose not to build

**Modes and empty directories.** A version is content at a set of paths. Mode is
not a parameter of creation anywhere in the port and most storage kinds have
none, so recording one would mean inventing it; an empty directory has no
content to record, so it does not survive a restore, and a directory a restore
empties is left where it is. All three are documented on the type rather than
discovered.

**Merging.** `Reconcile` resolves divergence one way — the ref wins, and what
comes back is what the working tree gave up. Resolving it any other way needs a
working copy that remembers which version it was taken from, and there is no
such thing to ask yet. The verb exists and tells the truth about what it does.

**Streaming.** `Commit` reads each file whole and `Restore` writes each file
whole, because `cas.Store` is still `[]byte` in and `[]byte` out. The first
things versioned are notes and manifests. A tree with a file larger than memory
in it will need the store's streaming path first, not the versioner's.

**Wiring.** Nothing in `cmd/nerved` builds a `Versioner`. There is no route that
would call one until the resource surface exists, and a mount for it with
nothing reading it would be a route that answers nothing.

**Recording what a purge removed.** It returns a count. Naming every swept
digest is what an operator wants when a sweep goes wrong, and it is the wrong
shape to decide before there is an operator interface to show it in.

## What I still do not understand

Whether a version should be a tree of manifests rather than one flat manifest. A
flat one re-encodes every path on every commit, so a thousand-file tree with a
one-file change stores a thousand entries again — cheap in bytes, wasteful as a
habit, and exactly the thing git's recursive trees exist to avoid. It also means
two versions sharing a subtree share no object for it. The flat one is right
while trees are small and I do not know where "small" ends.

Whether `Purge` should sweep at all, or mark. Reachability is computed from
every ref on every sweep, which is a full walk of every history to delete
whatever is usually nothing. A generation marked on the object at commit time
would make the sweep proportional to what is garbage rather than to what is
kept — but it would put versioning's bookkeeping inside a store whose whole
argument is that it knows nothing about who refers to what.

Whether the working tree should be behind a port already. `Versioner` takes a
`vfs.FileSystem` and a root, which is the mount table's vocabulary rather than
the domain's, and every verb here says "walk the tree, read a path, write a
path". If the working copy turns out to need state of its own — the version it
was taken from, most obviously — that is a port, and the versioner should have
been taking it from the start.
