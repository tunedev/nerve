# E1.4 — the mount table

`MountTable` in `internal/core/vfs`: prefixes mapped onto plugins, longest
prefix wins, and the table itself satisfies `FileSystem`. Every verb, the
descriptors and all three accessors forward to the resolved plugin.

## What the pattern was

The dispatcher the settled decision was written for. Callers hold this type and
never a plugin, so `Capabilities` and `As*` exist on the port precisely so this
type has to forward them.

## What surprised me

**A prefix names a subtree, and string matching gets that wrong.** `/queue` must
not hold `/queuebase`, so a match only counts when what follows the prefix is
empty or begins with a separator. The empty case is the mount point itself, and
it resolves to the plugin's root — `/queue` is `/` to the plugin mounted there.

**Paths make the trip in both directions.** Translating on the way in is
obvious; `Readlink` is where it bites, because the plugin answers with a path in
its own vocabulary and the caller only ever speaks the table's. A target that
came back unprefixed would name a real path in the wrong mount rather than
failing.

**Resolution has to be lexical before it is a match.** `/queue/../store/thing`
names an entry in the store mount. Matching the raw string hands it to `/queue`,
which then receives a path that climbs out of itself. `path.Clean` on the way in
makes the prefix comparison mean what it says.

**Comparing two resolved plugins to reject a cross-mount rename is a trap.** A
plugin holding a map is not comparable, and `from != to` on the interface values
panics at run time. Comparing the mount prefixes instead is both safe and the
thing actually being asked.

**The accessors could not stay as truthful as they are on a plugin.** An
accessor takes no path, and a table's answer varies by path — the same reason
descriptors are data. `AsSymlinker` returns nil when no mount answers, which
keeps `if s := fsys.AsSymlinker(); s != nil` worth writing, and a mount that
refuses the verbs inside a table where others answer says so per path, as
`fs.ErrInvalid`.

## What I would do differently

Nothing yet. Sorting the mounts by descending prefix length at `Mount` makes
resolution a first-match scan and keeps the loop with no comparison in it;
mounts are added at composition and read for the process lifetime, so the cost
sits in the right place.

## What I still do not understand

Whether a cross-mount rename stays refused. It is `fs.ErrInvalid` because no
plugin holds both entries, and copy-then-delete is a different operation with
different failure modes that a caller should have to ask for. E5 moves data
between scopes and is where a caller either wants that or does not.

Whether the accessor guard survives contact with a real caller. It answers
"could any path here", and the honest per-path answer is an error one call
later. If callers end up branching on it the way they branch on `Caps`, the
accessor set wants a descriptor beside it — which would be the fourth time this
repo concluded capability is data.
