# E11.1 — Mounting the tree, and the two entries it will not serve

`internal/adapters/inbound/fusefs` serves a `vfs.FileSystem` to the kernel over
`github.com/hanwen/go-fuse/v2`, which `nrv-ek9` chose and which enters `go.mod`
here. `Serve(dir, fsys)` mounts and answers until `Unmount`; a node holds
nothing but the tree it stands over, and where it stands is the inode
hierarchy's answer rather than a path it remembered.

It is an inbound adapter in the ordinary sense: the kernel is the caller, every
request arrives as a FUSE opcode and leaves as a port verb, and the mapper at
the boundary is `attr.go` — `io/fs` sentinels in, errnos out.

## The open question E11.2 left, answered

`nrv-ek9` did not know whether the node should serve `vfs.FileSystem` or
`files.Tree`. It is the port. `files.Tree` has `Walk`, `Glob`, `Grep` and
`Find`, and the kernel can ask for none of them; what it does ask for is
`LOOKUP`, `GETATTR`, `READDIR`, `READ`, `WRITE`, `SETATTR`, and every one of
those is a port verb or nothing. The mount is handed whatever `FileSystem` the
caller has, which for a workspace is what `workspace.Scope.View` returns, so
containment stays where E5.1 put it and the mount derives no path of its own.

## What the mount refuses, and why the two refusals are different

**A hard link, because two paths to one entry is a second spelling of a
location.** That is `nrv-ek9`'s item 9 and it is a decision. Not implementing
`NodeLinker` is how it is spelled: go-fuse answers `ENOTSUP` for a verb the
node does not have.

**A symbolic link, because the port cannot describe one.** This is not a
decision, it is a finding, and it is the opposite of what E11.2 expected. `Stat`
follows a link and reports the entry it stands for; `ReadDir` does not. The same
entry, through the same plugin:

```
Stat  /link -> mode=-rw-r--r-- size=9 err=<nil>
ReadDir /
  "link" mode=Lrwxrwxrwx
  "note" mode=-rw-r--r--
host Lstat -> mode=Lrwxrwxrwx
```

`Lookup` and `Getattr` have only `Stat`, so the kernel is told a link is a
regular file. Creating one through the mount then fails, because `symlink(2)`
asks for a link and is handed a file:

```
os.Symlink -> input/output error
```

Claiming `S_IFLNK` at creation gets past that and no further. The kernel takes
the link, then looks the path up again — there is no attribute caching here —
and the lookup goes back through `Stat`, which says regular file:

```
Symlink: <nil>
Readlink right after: "" err=readlink .../link: invalid argument
Readlink after a fresh lookup: "" err=readlink .../link: invalid argument
```

So the mount serves two kinds of entry, a directory and a file. A link planted
behind it is served as the entry it stands for, which is what `Stat` and `Read`
already do; it is not hidden and it is not an error.

**This removes escape item 1 for now, rather than solving it.** `nrv-ek9` named
the symlink target as the only escape Nerve emits, because the kernel resolves
`Readlink` bytes in host vocabulary. A mount that never answers `Readlink` never
emits it. It comes back the day the port grows a verb that describes an entry
without following it, and that verb is filed as `nrv-b4jn`.

## The read and write shape, and the bug in the obvious version

The port moves whole contents, so a descriptor keeps the entry in memory and
serves every offset from that copy. A write lands in the copy and reaches the
plugin at `Flush`, which is `close(2)`.

The copy is taken at the **first read or write**, not at the open. The obvious
version takes it at the open and is wrong, because the kernel opens a descriptor
before it truncates one. `os.WriteFile` over a longer existing file left this:

```
read "shortg first line", want "short"
```

The trace says why. `O_TRUNC` is not in the open flags — go-fuse does not
negotiate `ATOMIC_O_TRUNC`, so the kernel strips it — and the truncate arrives
afterwards as a bare `SETATTR`:

```
OPEN /note flags 32769 O_TRUNC? 0
SETATTR /note valid 520 fh 0 hasFh false
  size branch: size 0 held? false f nil? true
  WRITE off 0 n 5 -> len 17
  FLUSH /note len 17
```

`valid 520` is `FATTR_SIZE|FATTR_LOCKOWNER`. `FATTR_FH` is not set, so there is
no file handle in the request and the descriptor's copy cannot be reached from
`Setattr` at all: the path was cut and the copy still held seventeen bytes,
which `Flush` then wrote back over the top. Taking the copy lazily fixes it
because by the first write the path is already empty, and it also means the
common overwrite never reads the content it is about to replace.

What the shape costs: the entry's length in memory per open descriptor, and
close-to-open semantics between two descriptors on one path. What it buys: every
storage kind behaves the same through a mount, including the ones with no notion
of an offset. `AsStreamer` is the answer for entries that outgrow memory, and it
is a later ticket than making the tree real.

## What is deliberately not here

**`nerved` does not mount anything.** Wiring a mount into the composition root
without E11.5 would leave an orphaned mount at every restart, which is the exact
failure E11.5 exists to prevent. `Serve` returns a `*Mount` with `Unmount` and
`Wait` and stops there.

**No entry or attribute timeout.** `nrv-ek9`'s item 8 measured that passing any
`Options` leaves both nil and the kernel caches nothing. That is the safe
direction and the slow one, and it is left alone: a timeout is a window in which
a revoked path still answers, and nothing has measured that the speed is needed.

**No `AllowOther`, no `DirectMount`, no xattrs, no locks.** The kernel's default
for an unprivileged mount is uid-scoped with `nosuid,nodev`, which is the only
mount option here that is a boundary.

**Mode is not passed to `Create` or `Mkdir`.** Mode is not a parameter of
creation anywhere in the port, because most storage kinds have none. A caller
that wants different bits chmods, which arrives as `SETATTR` and reaches
`Chmod`.

## What surprised me

**The escape E11.2 called the only one Nerve emits is one the mount cannot
emit.** I went in expecting `Readlink` to be the careful part — go through the
view, never around it. It turned out the mount cannot serve a link at all, and
the reason is one layer further in than the adapter: a port with `Stat` and no
`Lstat` has already decided that a link is not a kind of entry. The containment
question was answered by a missing verb rather than by careful code.

**`FATTR_SIZE` arrives with no file handle.** I wrote `Setattr` to catch the
descriptor's copy up and it type-asserted its way to nil every time, silently,
because a failed assertion is just a false. Printing `hasFh` was what found it;
the version that only printed the outcome would have had me looking at the
truncate.

**`READDIRPLUS` decides the answer, so a wrong `d_type` costs nothing.**
`Readdir` reported `S_IFLNK` for the planted link and `ls` showed an ordinary
file anyway, because the kernel does the lookup and the lookup wins. A mount can
be inconsistent between those two and never find out — which is a reason to make
`kind` the one function both go through, not a reason to relax.

## What I would do differently

Print the request before the reaction. Three of the four findings here came from
one `println` of the opcode and its flag word, and I wrote two rounds of
plausible fixes first. A FUSE filesystem is a protocol endpoint; the first
question is always what the kernel actually sent, and it is one line to answer.

## What I still do not understand

**Whether a workspace gets one mount or one per area.** `nrv-ek9` raised it and
nothing here settles it. Files, key space, queue and stream all reach through
one `Scope`, and one mount presenting them as sibling directories needs a
`FileSystem` that composes four mounts — which the mount table already is. That
is likely the answer, and it is E11.3's to make.

**What `Getattr` should say while a descriptor is dirty.** It reports the path,
so a caller that writes and then `fstat`s its own descriptor sees the old
length until it closes. Every network filesystem has a version of this and I do
not know whether the ordinary tools care.

**Whether a read-destructive path should be openable at all.** One descriptor
takes one entry, which is what a queue means by a file, but nothing stops a
caller opening it twice and getting two different jobs at the same path. `Caps`
says the path is read-destructive; the mount does not read `Caps` anywhere yet.
