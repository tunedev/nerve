# E8.1 — Sessions

`session.Store` is a workspace's conversations: `Create`, `List`, `Get`, `Delete`,
`Append` on the one FileSystem the mount table presents. A session is a directory
holding a `SESSION` record — the caller's key/value metadata and when it opened —
and one file per appended message.

The ticket's acceptance is five verbs, and it is one test:

```
$ go test ./internal/core/session/ -run ASessionIs -v -count=1 | grep '^ *--- '
--- PASS: TestASessionIsItsMetadataAndItsTranscript (0.00s)
    --- PASS: TestASessionIsItsMetadataAndItsTranscript/tree (0.00s)
    --- PASS: TestASessionIsItsMetadataAndItsTranscript/keyspace (0.00s)
```

A session is created carrying metadata, listed, talked into twice, read back with
both halves, deleted, and gone from the listing.

## What the pattern was

`kv.Space`, `ingest.Ledger` and `thread.Log` again: hold the tree and a root, take
a `workspace.Scope` per call, derive every path through `Scope.Path`, know no
plugin, refuse user scope. The clock is injected as `func() time.Time`, which is
`NewLedger`'s signature and is what lets a test say which write produced a stamp.
Every verb is asked over `memfs` and over `kvfs`, because a session is a directory
on one and a prefix on the other.

`Get` answers with the session and the messages in one value and never with the
messages alone, for the reason `thread.Read` does: a caller holding a transcript
with no idea which session it came from is one mix-up away from attributing one
user's conversation to another, and cross-user isolation is a correctness
requirement here rather than hardening.

## What surprised me

**The metadata and the transcript change at different rates, and that decided the
file layout.** The obvious shape is one record per session holding the metadata and
the messages, which is one file to read and one to write. It is also a file that
every append rewrites — a hundred-turn conversation rewrites the whole transcript a
hundred times, and an interrupted append loses every turn before it, not the one
being made. Metadata written once at creation and one file per message means
nothing already written is ever read back and rewritten, which is what makes
"append-only" a property of the store rather than a promise in a comment.

**`Get` returning everything is what keeps the verb set at five.** The instinct was
`thread`'s split: a cheap `Get` for the record and a `Read` for the record plus the
output. `thread` earns that split because its cheap question is real — is more
output coming — and a reader asks it repeatedly while a run works. A session has no
such question: the caller that names one session wants the conversation, and the
caller that wants metadata alone is asking about all of them, which is `List`. The
split would have been a sixth verb whose only consumer was the test for it.

**Refusing an empty role is not defensive programming, it is the transcript's
contract.** Everything E8 derives from a session — extracted facts, a compression
that keeps what is worth keeping, a reconciliation against a contradicting memory —
turns on who said what. A turn with no speaker is one that every derivation has to
guess at, and a guess about which side of a conversation asserted a fact is how a
model's own output comes back as something the user said. It is refused at `Append`
and again at decode, because a file written by something other than this store
reaches the same readers.

## What I would do differently

The record holds metadata fixed at creation and there is no verb that changes it.
That is exactly the acceptance and no more, but E8.10 wants to retain a summary on
a session whose transcript it archives, and that is a metadata write. When it lands
it should be a `Put`-shaped verb over the metadata alone — the record is its own
file precisely so that writing it does not touch the transcript — and not a
`Create` that reopens.

## What I chose not to build

No paging over a transcript. `Get` reads every message, which is right for a
conversation and wrong for the cold hundred-thousand-turn log E8.10 exists to move
aside. The sequences are the message names, so a `Since(seq)` is a filter over the
listing `readDir` already does rather than a new layout; it lands when a caller
needs it.

No route. E8.2 is the `context` route and is where a transport first sees any of
this.

## What I still do not understand

Whether the metadata belongs in this record at all, or in `kv.Space` under a
namespace the session owns. The ticket reads "KV metadata plus append-only message
log", and `kv.Space` is already the workspace's key/value store — but it has `Get`,
`Put` and `Delete` and no listing verb, so `List` could not be built on it, and a
store that keeps half a session in one mount and half in another has two ways to
be half-deleted. Keeping both halves under one name was the call; what would change
it is a caller that wants a session's metadata to live on a different mount from its
transcript, and I do not know yet whether that caller exists.
