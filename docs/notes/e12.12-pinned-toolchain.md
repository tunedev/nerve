# nrv-ejl — A pinned toolchain and a reproducible build

`go.mod` carries `toolchain go1.27.0`. `make build` is
`CGO_ENABLED=0 go build -trimpath`. `make repro` clones HEAD twice, builds both
through that target, and requires the two binaries to be byte identical. It runs
in `make check` and in CI.

## What the pattern was

The claim to test is the acceptance line: same source, clean checkout, same
binary. It was false before anything was pinned — two clones of the same commit,
built with the same compiler:

```
$ sha256sum a/nerved b/nerved
255d797578b869c09f0b5cd3a46f8d18e66528913bcaff55705beb306a38e026  a/nerved
b5587e9b2437559c977cf040ec897fcd276f524f732a0a808b0c5df296e223ce  b/nerved
```

`go version -m` on the two was identical, so the difference was not in the
recorded build settings — it was the absolute source path compiled into the
debug info. `-trimpath` alone made them equal. `CGO_ENABLED=0` is the second
pin: with cgo left on auto, the presence of a C toolchain on the build machine
changes the binary (`ead2b15c…` against `f5d68487…` for the same source), and
whether a machine has gcc is not a property of the source.

The toolchain line is the third. `go 1.27` is a floor, not a pin — a machine
with go1.28 satisfies it and produces a different binary. `toolchain go1.27.0`
makes `GOTOOLCHAIN=auto` select exactly that version and download it if absent,
so the compiler is a versioned input like any other. CI already reads the
version out of `go.mod` via `setup-go`, so the pin reaches CI with no second
place to state it.

## What surprised me

**The gate proved itself by failing.** `make repro` clones HEAD, so the first
run after writing it built the *unpinned* source that was still committed:

```
$ make repro
/tmp/tmp.Dodttbc4uB/one/bin/nerved /tmp/tmp.Dodttbc4uB/two/bin/nerved differ: byte 3949, line 1
make: *** [Makefile:50: repro] Error 1
```

Then, on the commit that pins:

```
$ make repro
reproducible: f85f1f7525135a79878c8cbbe0ba968e1a9e46d8c34ddddda59577c60947e475
```

Cloning HEAD rather than copying the working tree is deliberate: reproducibility
is a property of a commit. The cost is that `make check` on a dirty tree tests
the last commit, not what you are about to commit.

**A dirty tree is a different binary, by design.** `go build` stamps
`vcs.modified`, so one whitespace change in `README.md` moves the hash of a
binary whose Go source did not change:

```
	build	vcs.revision=48684b9d5b2e48b16b59bff0e61e125e435f216f
	build	vcs.modified=true
f85f1f7525135a79878c8cbbe0ba968e1a9e46d8c34ddddda59577c60947e475  clean
4bc105ac89892185293732c2d138b5df8ece479ce9f025cde52a126313242573  dirty
```

That is the stamp doing its job — the binary is honest about being built from
something that is not a commit.

## What I would do differently

Decide what the gate is made of, which is what nrv-tju's note asked this ticket
to do, and pin the linter in the same breath. `make fmt-check`, `make race` and
`make repro` are the CI steps verbatim, so those definitions exist once. Lint
was left out and had to be closed separately by nrv-9hz, which made
`golangci-lint` a `go.mod` tool dependency so CI and `make lint` run one pinned
binary — the same pin this ticket applied to the compiler, one ticket late.
`go build ./...` is the one step still CI-only.

A pinned compiler with a floating linter is only half a pinned toolchain: the
build agrees byte for byte while two machines still disagree about whether the
source passes lint. Pin everything the gate shells out to, not just the
compiler.

## What I still do not understand

Whether the VCS stamp is worth what it costs. A `git archive` checkout has no
`.git`, so it gets no stamp and hashes differently from a clone of the same
commit — reproducibility here holds for a git checkout, not for source alone.
`-buildvcs=false` would close that gap and take with it the only way to ask a
binary which commit it came from, since `main.version` is still `dev` and
nothing stamps it. Provenance won for now; if binaries ever ship as tarball
builds, that is the trade to revisit.
