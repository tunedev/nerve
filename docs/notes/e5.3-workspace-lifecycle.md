# E5.3 — workspace lifecycle

`workspace.Lifecycle` creates, lists and deletes a workspace across every area
it occupies. An area is a root in the tree that holds part of a workspace — the
files mount, the vector index, the graph, the key space, the queue — and the
list of them is the deliverable as much as the three verbs are.

## What the pattern was

The uniform interface doing the work it exists for. Create is `Mkdir` at
`Scope.Path(area, "")` under every area, Delete is `RemoveAll` at the same
paths, and neither knows what an area stores. A vector index and a keyspace are
deleted by the same call as a disk directory because all of them are paths, so
"delete removes files, vectors, graph nodes, KV keys and queue entries" is one
loop rather than five adapters, and a kind added later joins by being mounted
and named as an area.

Idempotence is not implemented here either. `Mkdir` of a directory already there
is not an error and `RemoveAll` of a path that is not there is not an error —
both are port promises the conformance suite already holds every plugin to — so
Create and Delete inherit it. A delete that failed halfway is completed by
running it again.

## What surprised me

**A mutation and a query want opposite answers about a partial failure.** Delete
attempts every area and joins what all of them said, because abandoning the rest
on the first refusal is how a deleted workspace stays readable in the three
areas the loop never reached. List does the reverse: one area failing means it
returns nothing, because a short list of workspaces is indistinguishable from a
correct one, and the caller is usually about to act on the workspaces it was not
told about. The same "be honest about partial results" instinct produces
join-and-continue in one and fail-fast in the other.

The test for this only discriminates with the refusing area **first** in the
list. With it second, a fail-fast implementation had already cleared the area
the assertion read, and the test passed against the mutation.

**`Mkdir` on a keyspace makes nothing, and that is correct.** kvfs claims
`ObjectStore`, where a name is a prefix and nothing has to be made before
something is written under one, so a created workspace does not exist in the key
area until something is put there. Create had to accept that rather than treat
it as a failure — the descriptor is the plugin saying what the verb means, which
is the settled decision working exactly as intended, but it does mean "created"
is not a single observable fact across areas.

**`List` needs the directory bit, and gets it from a kind that has no
directories.** User scope holds workspaces, but the layout also permits a key
written directly in user scope beside them. A keyspace answers for a prefix with
the directory bit set and for a key without it, so the same `IsDir` filter that
separates a workspace from a file in a tree separates a workspace from a key
there.

## What I would do differently

Refuse user scope from the start. `Create` and `Delete` take a `Scope`, and a
scope with no workspace is a perfectly valid value that means "everything this
user has" — `Delete` would have removed every workspace they own under a verb
named for one. That is a footgun the type invites, and it was noticed while
writing the doc comment rather than while designing the signature.

## What I still do not understand

Where the area list comes from at composition. It is a constructor argument
here, which keeps the core ignorant of concrete mounts, but nothing has wired it
yet and an area named in config with no mount behind it fails a delete with
`fs.ErrNotExist` — the same sentinel a missing workspace would produce inside a
mount that does exist. Create and Delete are loud about it because a mount table
that holds nothing at a path reports it; `List` cannot be, because a user with
no workspaces in an area reports the same thing. Whether the areas should
instead be derived from the mount table, so an area that is not mounted is not
an area, is the question E5.4 or the first inbound caller should answer.

Whether a queue area can really be emptied by `RemoveAll`. The tests mount a
tree for it, because what is being read here is the path a delete reaches rather
than what a broker does with the messages already handed out. A queue holds
state in a journal and in a broker, and a workspace deleted while one of its
messages is in flight is not covered by anything written here.
