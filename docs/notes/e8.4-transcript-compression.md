# E8.4 — Commit: transcript compression

A committed conversation keeps its most recent turns and one summary standing for
everything before them. The reduction is not a new mechanism: E8.10 already moves
cold messages into the session's `ARCHIVE` and retains the summary on the `SESSION`
record, and `internal/core/archive` already composes that store with
`llm.Summariser`. What this ticket adds is the pipeline that calls it.

- `commit.Committer` holds an `*archive.Archiver` and how many turns to keep hot.
- `Commit` answers with a `Result` — the memories it wrote and the session as it
  stands afterwards — rather than the memories alone.
- A build with no summarising endpoint has no archiver and therefore no committer,
  the same refusal `New` already made for a nil extractor.

The acceptance is one test, plus the one that pins the stage order:

```
$ go test ./internal/core/commit/ \
    -run "ACommitReducesTheColdTranscriptToASummaryTheSessionKeeps|TheExtractorSeesTheColdHalfBeforeItGoesCold" \
    -v -count=1 | grep -E '^(--- |ok|FAIL)'
--- PASS: TestACommitReducesTheColdTranscriptToASummaryTheSessionKeeps (0.00s)
--- PASS: TestTheExtractorSeesTheColdHalfBeforeItGoesCold (0.00s)
ok  	github.com/tunedev/nerve/internal/core/commit	0.003s
```

## What the pattern was

A stage that composes another stage rather than reaching past it. `Committer` could
have held `llm.Summariser` and called `sessions.Archive` itself — the store verb is
public and the call is four lines. It would also have been a second implementation
of three rules `archive` already owns: which turns are cold, that the summariser is
shown the summary the session already carried alongside them, and that `through` is
the last cold sequence. Two implementations of "what the session's summary stands
for" is precisely the outcome the first attempt at this ticket was rejected for, in
a different spelling.

So the committer holds the archiver, and the only thing it adds is the policy
number: how many turns stay hot. The sentence budget stays on the archiver, because
that is where the summariser is.

## What surprised me

**The order of the two stages is not the order the first attempt argued for, and
the mechanism is why.** That branch put both model calls first, then the digest,
then the memories, reasoning that a digest written twice converges and a memory
written twice does not. That is correct when compression writes a summary *beside* a
transcript nothing removes from. It is wrong once compression *narrows* the
transcript: archive first and a re-run extracts from a conversation whose cold half
it can no longer see, so the facts in that half are never written by this run or by
any later one. The duplicate memories a re-run writes are E8.5's job and recoverable
by definition; a fact never extracted is not recoverable at all. Archival runs last.

**The stage order is a testable property, not a comment.** Swapping the two stages
in `Commit` and re-running the package fails four tests, not one — the extractor
stops seeing the cold half, a failed extraction leaves the transcript already
narrowed, a failed summarisation loses the memories, and a refused priority archives
anyway. That is what makes the ordering an invariant rather than a preference: every
symptom of getting it wrong has a case standing on it.

**Reduction is idempotent for free, and only because `keep` is a count of hot
turns.** A second commit over a conversation that has not grown reads a transcript
already within the policy, and `Archiver.Archive` returns without a model call. If
the policy had been expressed as "archive through sequence N" the caller would have
had to remember what it archived last time, and every scheduled commit would have
paid an endpoint for an idle session.

## What I chose not to build

No `Compression` struct. The first attempt had `{Keep, Sentences}`; the sentence
budget now belongs to the archiver, so what is left is one integer and a struct
around it would be a type that exists to be a type.

No check that the committer's session store is the archiver's. It is the composition
root's business and asserting it would need an accessor on `Archiver` that exists
for the assertion.

No route and no wiring in `main`, for the reason `session.Store`, `commit.Committer`
and `archive.Archiver` are all still unwired: E8.2 is where a transport first sees
any of this.

## What I still do not understand

Whether `Result.Session` is the right answer or whether a caller wants to know what
*this* commit did. It currently reports the session's state, so a commit that
reduced nothing and one that reduced three turns answer identically when the session
was already archived through the same sequence. A caller driving a UI probably wants
"nothing changed"; a caller deciding whether to commit again wants the state. I chose
the state because it is the statement that stays true after the call.

Whether the extractor should see the archive. It is handed the hot transcript, which
after the first commit is a few turns — so the second commit's extraction reads much
less conversation than the first's, and no note anywhere says whether that is the
intent or an accident of the two stages sharing a session. E8.5 through E8.7 all read
prior memories, so possibly the archive is exactly what should not be re-read; I do
not know that, I inferred it.
